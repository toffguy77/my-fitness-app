# notification-delivery Specification

## Purpose
Добавляется доставка через APNs наравне с Web Push; доставка push разбивается на задания по адресатам; сообщение чата пушится без записи уведомления. Возможность введена изменением `ios-push-notifications` (архив `openspec/changes/archive/2026-10-24-notifications-delivery-channels`).

## Requirements

### Requirement: Доменное событие порождает доставку по каналам

Создание уведомления SHALL порождать задания на доставку во все каналы, разрешённые предпочтениями получателя. Уведомление в приложении MUST создаваться всегда независимо от предпочтений по остальным каналам. Сообщение чата MUST NOT считаться уведомлением: о нём сообщает пуш `chat_message` без записи в списке уведомлений.

#### Scenario: Событие с разрешённым push

- **WHEN** создаётся уведомление для пользователя, у которого для этого типа события разрешён push
- **THEN** создаётся запись уведомления в приложении
- **AND** создаётся задание на доставку через push

#### Scenario: Событие с запрещёнными внешними каналами

- **WHEN** создаётся уведомление для пользователя, отключившего для этого типа события все внешние каналы
- **THEN** создаётся только запись уведомления в приложении
- **AND** заданий на внешнюю доставку не создаётся

#### Scenario: Отправка не задерживает запрос

- **WHEN** действие куратора порождает уведомление клиенту
- **THEN** ответ на запрос куратора не ожидает завершения внешней доставки

#### Scenario: Сообщение чата

- **WHEN** куратор отправляет сообщение клиенту без открытого соединения
- **THEN** запись уведомления не создаётся
- **AND** создаётся задание push `chat_message`

### Requirement: Доставка через web push

Система SHALL доставлять срочные уведомления на подписанные устройства пользователя по протоколу Web Push. Подписка, на которую сервис доставки ответил признаком недействительности, MUST удаляться.

#### Scenario: Доставка на подписанное устройство

- **WHEN** выполняется доставка push пользователю с действующей подпиской
- **THEN** сообщение отправляется на адрес доставки этой подписки
- **AND** результат доставки фиксируется

#### Scenario: Недействительная подписка

- **WHEN** сервис доставки отвечает признаком недействительности подписки
- **THEN** подписка удаляется
- **AND** повторные попытки доставки на неё не выполняются

#### Scenario: Push выключен в конфигурации

- **WHEN** ключи для web push не заданы в конфигурации
- **THEN** сервис стартует с предупреждением о выключенном канале
- **AND** интерфейс не предлагает пользователю подписку на push

### Requirement: Догоняющая доставка почтой

Уведомление SHALL доставляться письмом, только если оно не было прочитано в приложении в течение установленного для его типа времени ожидания. Письма о накопившихся событиях MUST объединяться в одно сводное письмо.

#### Scenario: Уведомление прочитано вовремя

- **WHEN** пользователь прочитал уведомление в приложении до истечения времени ожидания
- **THEN** письмо по этому уведомлению не отправляется

#### Scenario: Уведомление не прочитано

- **WHEN** время ожидания истекло, а уведомление не прочитано
- **AND** для этого типа события разрешён почтовый канал
- **THEN** уведомление включается в ближайшее сводное письмо

#### Scenario: Объединение событий в одно письмо

- **WHEN** у пользователя накопилось несколько непрочитанных уведомлений, подлежащих отправке почтой
- **THEN** отправляется одно письмо, содержащее все эти события
- **AND** отдельные письма по каждому событию не отправляются

#### Scenario: Транзакционные письма не задерживаются

- **WHEN** отправляется письмо подтверждения адреса или восстановления пароля
- **THEN** оно отправляется немедленно и не включается в сводное письмо

### Requirement: Учёт результата доставки

По каждому уведомлению SHALL сохраняться результат доставки в каждый канал: канал, статус, время попытки и причина неуспеха.

#### Scenario: Неуспешная доставка

- **WHEN** доставка в канал завершилась ошибкой
- **THEN** сохраняется запись со статусом неуспеха и причиной

#### Scenario: Куратор видит факт оповещения

- **WHEN** куратор просматривает отправленное клиенту уведомление
- **THEN** отображается, в какие каналы оно было доставлено успешно

### Requirement: Доставка на iPhone через APNs

Канал `push` SHALL доставлять уведомление на все активные устройства iOS пользователя через APNs в дополнение к Web Push-подпискам, создавая отдельное задание на каждую подписку и каждое устройство. Каждое устройство MUST получать отправку на хост своего окружения (`sandbox` или `production`); повтор MUST выполняться только для адресатов, которым доставка не удалась.

#### Scenario: Пользователь с браузером и телефоном

- **WHEN** выполняется доставка push пользователю с одной Web Push-подпиской и одним устройством iOS
- **THEN** отправлено одно сообщение Web Push и одно сообщение APNs
- **AND** результат каждой отправки зафиксирован

#### Scenario: Устройство сборки из Xcode

- **WHEN** устройство зарегистрировано с `environment=sandbox`
- **THEN** отправка идёт на `api.sandbox.push.apple.com`

#### Scenario: Частичный сбой

- **WHEN** Web Push доставлен, а APNs ответил `503`
- **THEN** повторяется только задание APNs
- **AND** браузер не получает пуш второй раз

#### Scenario: APNs временно недоступен

- **WHEN** APNs отвечает `503` или соединение разорвано
- **THEN** доставка повторяется не более трёх попыток, как для прочих каналов

#### Scenario: Ключ APNs есть, VAPID нет

- **WHEN** в окружении настроен только APNs
- **THEN** задания push всё равно отправляются
