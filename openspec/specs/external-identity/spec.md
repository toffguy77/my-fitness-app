# external-identity Specification

## Purpose
Добавляется провайдер Apple и нативное завершение потока; общий поток создания аккаунта и выпуска токенов не меняется. Возможность введена изменением `ios-native-session` (архив `openspec/changes/archive/2026-10-24-external-oauth-providers`).

## Requirements

### Requirement: Регистрация через внешнего провайдера

Посетитель SHALL иметь возможность создать аккаунт через внешнего провайдера входа без ввода пароля. Адрес почты, полученный от провайдера, MUST считаться подтверждённым, и отдельное письмо подтверждения MUST NOT отправляться.

#### Scenario: Первый вход через провайдера

- **WHEN** посетитель, чья внешняя учётная запись не связана ни с одним аккаунтом и чей адрес не зарегистрирован в системе, завершает авторизацию у провайдера
- **THEN** создаётся аккаунт без пароля
- **AND** адрес помечен подтверждённым
- **AND** пользователь входит в приложение

#### Scenario: Провайдер не вернул адрес почты

- **WHEN** провайдер не предоставил адрес почты
- **THEN** после создания аккаунта пользователю предлагается указать адрес
- **AND** до подтверждения адреса аккаунт ограничен так же, как при обычной регистрации без подтверждения

#### Scenario: Перенос данных гостевого онбординга

- **WHEN** посетитель, прошедший гостевой онбординг, регистрируется через провайдера
- **THEN** введённые им параметры и цель переносятся в созданный профиль

### Requirement: Повторный вход через привязанного провайдера

Вход SHALL выполняться по паре «провайдер и идентификатор пользователя у этого провайдера», а не по адресу почты.

#### Scenario: Повторный вход

- **WHEN** пользователь с существующей привязкой завершает авторизацию у того же провайдера
- **THEN** он входит в свой аккаунт
- **AND** новый аккаунт не создаётся

#### Scenario: Смена адреса почты на стороне провайдера

- **WHEN** пользователь изменил адрес почты у провайдера и выполняет вход
- **THEN** он входит в тот же аккаунт

### Requirement: Совпадение адреса требует подтверждения владения

Если внешняя учётная запись приносит адрес почты, уже зарегистрированный в системе, вход в существующий аккаунт MUST NOT выполняться автоматически. Система SHALL требовать подтверждения владения аккаунтом: ввод текущего пароля либо переход по ссылке, отправленной на этот адрес.

#### Scenario: Адрес совпадает с существующим аккаунтом

- **WHEN** посетитель авторизуется у провайдера, который сообщает адрес, уже зарегистрированный в системе
- **AND** привязки между этой внешней учётной записью и аккаунтом нет
- **THEN** вход не выполняется
- **AND** предлагается подтвердить владение аккаунтом

#### Scenario: Подтверждение владения паролем

- **WHEN** пользователь вводит корректный текущий пароль на экране подтверждения владения
- **THEN** создаётся привязка внешней учётной записи к аккаунту
- **AND** пользователь входит в приложение

#### Scenario: Отказ от подтверждения владения

- **WHEN** пользователь не подтверждает владение аккаунтом
- **THEN** привязка не создаётся
- **AND** новый аккаунт с этим адресом не создаётся

### Requirement: Безопасность потока авторизации

Поток авторизации SHALL использовать Authorization Code с PKCE и проверкой параметра состояния. Обратный вызов с несовпадающим или отсутствующим параметром состояния MUST отклоняться.

#### Scenario: Обратный вызов с чужим параметром состояния

- **WHEN** приходит обратный вызов с параметром состояния, не соответствующим сохранённому в браузере
- **THEN** авторизация отклоняется
- **AND** токены не выпускаются

#### Scenario: Повторное использование кода авторизации

- **WHEN** обратный вызов приходит повторно с уже использованным кодом
- **THEN** авторизация отклоняется

#### Scenario: Отказ пользователя на стороне провайдера

- **WHEN** пользователь отказывает в доступе на стороне провайдера
- **THEN** приложение отображает сообщение об отмене входа на русском языке
- **AND** не создаёт аккаунт

### Requirement: Управление привязками

Пользователь SHALL видеть список привязанных провайдеров и иметь возможность привязать дополнительного провайдера и отвязать существующего. Отвязка последнего доступного способа входа MUST быть запрещена.

#### Scenario: Привязка второго провайдера

- **WHEN** аутентифицированный пользователь проходит авторизацию у ещё не привязанного провайдера из настроек
- **THEN** привязка создаётся
- **AND** оба провайдера отображаются в списке

#### Scenario: Отвязка при наличии другого способа входа

- **WHEN** пользователь с установленным паролем отвязывает провайдера
- **THEN** привязка удаляется
- **AND** вход по паролю продолжает работать

#### Scenario: Отвязка последнего способа входа

- **WHEN** пользователь без установленного пароля пытается отвязать единственного привязанного провайдера
- **THEN** запрос отклоняется со статусом `409`
- **AND** отображается объяснение, что сначала нужно задать пароль

#### Scenario: Привязка уже занятой внешней учётной записи

- **WHEN** пользователь пытается привязать внешнюю учётную запись, уже связанную с другим аккаунтом
- **THEN** запрос отклоняется со статусом `409`

### Requirement: Установка пароля пользователем без пароля

Пользователь, зарегистрировавшийся через провайдера и не имеющий пароля, SHALL иметь возможность задать пароль через существующий поток восстановления доступа. Попытка входа по паролю для такого пользователя MUST завершаться штатным отказом.

#### Scenario: Установка пароля через восстановление

- **WHEN** пользователь без пароля запрашивает восстановление доступа на свой подтверждённый адрес и переходит по ссылке
- **THEN** он может задать пароль
- **AND** после этого вход по паролю работает

#### Scenario: Вход по паролю без установленного пароля

- **WHEN** выполняется попытка входа по паролю для пользователя, у которого пароль не установлен
- **THEN** возвращается тот же отказ, что и при неверных учётных данных, без раскрытия факта отсутствия пароля

### Requirement: Провайдер как опциональная возможность

Провайдер, для которого не заданы параметры приложения, SHALL считаться выключенным. Интерфейс MUST NOT предлагать вход через выключенного провайдера.

#### Scenario: Провайдер не настроен

- **WHEN** параметры приложения провайдера не заданы в конфигурации
- **THEN** кнопка входа через этого провайдера не отображается
- **AND** обращение к его эндпоинту авторизации возвращает статус `503`

### Requirement: Добавление провайдера не меняет поток аутентификации

Подключение нового провайдера SHALL сводиться к реализации интерфейса адаптера и его регистрации. Общий поток авторизации, создания аккаунта и выпуска токенов MUST оставаться неизменным.

#### Scenario: Реализация нового адаптера

- **WHEN** добавлен адаптер нового провайдера, возвращающий нормализованный профиль
- **THEN** вход и регистрация через него работают без изменений в коде потока аутентификации

### Requirement: Аккаунт через провайдера создаётся после согласий

Вход через внешнего провайдера, который создал бы новый аккаунт, SHALL не создавать аккаунт, а уводить на `/auth/consents` с одноразовым ожидающим входом; `POST /api/v1/auth/oauth/consents {consents}` с обязательными согласиями (оферта, политика, обработка персональных данных включая данные о здоровье) MUST создавать аккаунт, сохранять согласия в `user_consents` тем же кодом, что регистрация по паролю, и выдавать сессию. Куратора аккаунт получает по общему правилу `curator-access` («Регистрация не даёт права на куратора»): живому клиенту — нет, служебной учётной записи — служебный куратор.

#### Scenario: Новый пользователь через Яндекс

- **WHEN** колбэк Яндекса возвращает адрес, которого нет среди аккаунтов
- **THEN** аккаунт не создан, браузер уведён на `/auth/consents`
- **AND** после отправки обязательных согласий аккаунт создан, в `user_consents` есть три обязательных согласия

#### Scenario: Без согласия на обработку данных

- **WHEN** на `/auth/consents` отправлены оферта и политика без согласия на обработку ПДн
- **THEN** ответ `400` с кодом `validation`, аккаунт не создан

#### Scenario: Повторный вход привязанного пользователя

- **WHEN** входит пользователь, уже привязанный к провайдеру
- **THEN** экрана согласий нет, сессия выдаётся сразу

### Requirement: Apple — провайдер общего потока

Провайдер `apple` SHALL отдавать тот же нормализованный профиль, что Яндекс
и VK, но получает его не переходом браузера и колбэком, а identity token'ом в
теле `POST /api/v1/auth/native/apple` (адаптер `oauth.Apple`: `Name` и
`Authenticate` вместо `AuthorizationURL` и `Exchange`, — вход через Apple в
вебе в это изменение не входит). Регистрация через согласия, привязка,
отвязка, правило подтверждения владения адресом и выпуск токенов MUST
проходить через общий поток без отдельных веток для Apple. Привязка к
аккаунту, в который уже вошли, — `POST /api/v1/auth/native/apple/link` с
access-токеном; отвязка — общий `DELETE /api/v1/auth/providers/apple`.
Провайдер без `APPLE_TEAM_ID`, `APPLE_BUNDLE_ID`, `APPLE_KEY_ID`,
`APPLE_PRIVATE_KEY` и `APPLE_TOKEN_ENCRYPTION_KEY` MUST считаться выключенным;
настроенный провайдер `GET /api/v1/auth/providers` SHALL перечислять, а
веб-кнопки входа и привязки для него MUST NOT показываться.

#### Scenario: Привязка Apple к существующему аккаунту

- **WHEN** пользователь с паролем привязывает Apple в «Способах входа»
- **THEN** `GET /api/v1/auth/providers/linked` перечисляет `apple`

#### Scenario: Отвязка последнего способа входа

- **WHEN** пользователь без пароля, у которого привязан только Apple, отвязывает Apple
- **THEN** ответ `409` с кодом `provider_only_way_in`, привязка сохраняется

#### Scenario: Провайдер не настроен

- **WHEN** ключи Apple не заданы
- **THEN** `GET /api/v1/auth/providers` не перечисляет `apple`
- **AND** `POST /api/v1/auth/native/apple` отвечает `503` с кодом `feature_unavailable`

### Requirement: Нативное завершение не меняет веб-поток

Поток OAuth без `client=ios` SHALL завершаться как прежде: refresh-cookie и
302 на `/auth/complete`.

#### Scenario: Вход через Яндекс в браузере

- **WHEN** колбэк Яндекса завершается для потока без `client`
- **THEN** ответ ставит refresh-cookie и уводит на `/auth/complete`
