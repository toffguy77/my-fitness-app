# role-aware-shell Specification

## Purpose
Определяет, какая оболочка приложения — клиентская, кураторская или
административная — достаётся человеку на каждом экране и откуда берётся роль, по
которой этот выбор делается.

## Requirements

### Requirement: Оболочку выбирает роль из сессии

Оболочка любого экрана SHALL выбираться по роли, полученной от сервера для
текущей сессии. Значение роли из локального хранилища браузера MUST NOT влиять на
этот выбор.

#### Scenario: Куратор открывает профиль

- **WHEN** человек с ролью куратора открывает профиль
- **THEN** он видит кураторскую оболочку с кураторской навигацией

#### Scenario: Администратор открывает профиль

- **WHEN** человек с ролью супер-администратора открывает профиль
- **THEN** он видит административную оболочку

#### Scenario: Куратор открывает настройки

- **WHEN** человек с ролью куратора открывает любой экран настроек
- **THEN** он видит кураторскую оболочку, а не клиентскую

#### Scenario: Клиент открывает профиль и настройки

- **WHEN** человек с ролью клиента открывает профиль или настройки
- **THEN** он видит клиентскую оболочку

#### Scenario: Локальный слепок противоречит сессии

- **WHEN** в локальном хранилище лежит роль клиента, а сессия принадлежит куратору
- **THEN** показана кураторская оболочка

### Requirement: Неизвестная роль не подменяется клиентской

Пока роль текущей сессии неизвестна, экран MUST NOT показывать оболочку ни одной
роли. Роль клиента MUST NOT использоваться как значение по умолчанию.

#### Scenario: Сессия поднята из cookie, локального слепка нет

- **WHEN** куратор открывает профиль в браузере, где локальное хранилище пусто
- **THEN** до ответа сервера оболочка не показана
- **AND** после ответа показана кураторская оболочка
- **AND** клиентская оболочка не показана ни в один момент

#### Scenario: Локальный слепок испорчен

- **WHEN** значение в локальном хранилище не читается как профиль
- **THEN** роль запрашивается у сервера
- **AND** оболочка выбирается по ответу

#### Scenario: Сервер не ответил, а слепок есть

- **WHEN** запрос роли завершился отказом, но локальный слепок профиля сохранился
- **THEN** показана оболочка по роли из слепка, а не пустой экран

#### Scenario: Сессии нет вовсе

- **WHEN** запрос роли показал, что человек не аутентифицирован
- **THEN** он отправляется на экран входа, и оболочка не показана

### Requirement: Имя в заголовке берётся из того же источника

Имя и почта, показанные в оболочке, SHALL приходить из того же источника, что и
роль.

#### Scenario: Имя при пустом локальном хранилище

- **WHEN** экран открыт в браузере с пустым локальным хранилищем
- **THEN** в заголовке показано имя из ответа сервера, а не пустая строка

### Requirement: Чтение роли из локального хранилища не проходит сборку

Сборка MUST падать, если экран приложения выбирает оболочку или показывает роль по
значению из локального хранилища браузера.

#### Scenario: Новое чтение роли из хранилища

- **WHEN** в код экрана добавлено чтение роли из локального хранилища
- **THEN** проверка целостности кодовой базы завершается отказом
- **AND** в сообщении назван файл и строка

#### Scenario: Кодовая база после изменения

- **WHEN** проверка запущена на кодовой базе с внесёнными правками
- **THEN** она проходит

### Requirement: Пункт «Меню» в навигации клиента

Нижняя навигация клиента SHALL содержать активный пункт «Меню», ведущий на
`/menu`, на месте прежнего выключенного пункта «Тренировка». Пункта «Тренировка»
в навигации клиента MUST NOT быть.

#### Scenario: Клиент открывает «Меню»

- **WHEN** клиент нажимает «Меню» в нижней навигации
- **THEN** открывается `/menu` и пункт отмечен как активный

#### Scenario: Заглушки больше нет

- **WHEN** клиент открывает любой экран с нижней навигацией
- **THEN** пункта «Тренировка» в ней нет
