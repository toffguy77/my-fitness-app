## Requirements
### Requirement: Доступ куратора к данным клиента ограничен активной связью

Любой эндпоинт, принимающий идентификатор клиента в пути и возвращающий или изменяющий данные этого клиента, SHALL выдавать данные только тому куратору, у которого есть активная запись связи с этим клиентом в `curator_client_relationships` со статусом `active`. Требование распространяется на все роуты группы `/api/v1/curator/clients/:id/*` независимо от того, в каком модуле реализован обработчик.

#### Scenario: Куратор запрашивает историю целей чужого клиента

- **WHEN** куратор с ролью `coordinator` вызывает `GET /api/v1/curator/clients/{id}/targets/history`, где `{id}` — клиент, не связанный с этим куратором
- **THEN** API отвечает статусом `403`
- **AND** тело ответа не содержит данных клиента

#### Scenario: Куратор запрашивает историю целей своего клиента

- **WHEN** куратор вызывает `GET /api/v1/curator/clients/{id}/targets/history` для клиента с активной связью
- **THEN** API отвечает статусом `200` и возвращает историю целей

#### Scenario: Связь переведена в неактивный статус

- **WHEN** куратор вызывает любой роут `/api/v1/curator/clients/{id}/*` для клиента, связь с которым имеет статус, отличный от `active`
- **THEN** API отвечает статусом `403`

### Requirement: Проверка связи выполняется до обработчика

Проверка связи куратор↔клиент SHALL выполняться middleware на группе маршрутов `/api/v1/curator/clients/:id`, до вызова обработчика. Обработчик MUST получать проверенный идентификатор клиента из контекста запроса.

#### Scenario: Обработчик не вызывается при отказе

- **WHEN** запрос к роуту группы отклонён проверкой связи
- **THEN** обработчик маршрута не вызывается
- **AND** в базу данных не выполняется ни одного запроса на чтение данных клиента

### Requirement: Реестр защищаемых маршрутов

Каждый зарегистрированный маршрут, содержащий в пути параметр идентификатора чужого ресурса, SHALL присутствовать в явном реестре защищаемых маршрутов с указанием применяемого способа проверки. Автоматический тест MUST падать, если в собранном роутере есть маршрут с таким параметром, отсутствующий в реестре.

#### Scenario: Добавлен новый маршрут без записи в реестре

- **WHEN** в роутер добавлен маршрут с параметром идентификатора чужого ресурса и он не внесён в реестр защищаемых маршрутов
- **THEN** тест реестра завершается с ошибкой, называющей метод и путь этого маршрута

#### Scenario: Все маршруты внесены в реестр

- **WHEN** все маршруты с параметрами чужих идентификаторов внесены в реестр
- **THEN** тест реестра проходит успешно

### Requirement: Негативное покрытие доступа к чужим ресурсам

Для каждого маршрута из реестра защищаемых маршрутов SHALL существовать автоматический тест, проверяющий, что обращение от лица пользователя без прав на ресурс возвращает `403`.

#### Scenario: Прогон негативных тестов

- **WHEN** запускается набор тестов авторизации
- **THEN** для каждой записи реестра выполняется проверка отказа доступа
- **AND** все проверки завершаются успешно

### Requirement: Авторизационные ошибки различаются по типу, а не по тексту

Код SHALL определять тип авторизационной ошибки через `errors.Is` с типизированными ошибками пакета `apperrors`. Сравнение текста ошибки подстрокой для принятия авторизационных решений MUST отсутствовать в кодовой базе.

#### Scenario: Отказ в создании записи о еде из чата

- **WHEN** участник чата, не являющийся куратором в этой связи, вызывает создание записи о еде
- **THEN** сервис возвращает ошибку, для которой `errors.Is(err, apperrors.ErrForbidden)` истинно
- **AND** обработчик отвечает статусом `403`

#### Scenario: Отсутствие сравнения ошибок по тексту

- **WHEN** выполняется поиск по исходному коду `apps/api` на предмет сравнения текста ошибки подстрокой для выбора HTTP-статуса
- **THEN** совпадений не найдено

### Requirement: Отсутствие неиспользуемого механизма изоляции строк

Кодовая база SHALL не содержать неиспользуемых компонентов Row Level Security, создающих ложное представление о наличии изоляции на уровне БД.

#### Scenario: Проверка отсутствия мёртвого RLS-кода

- **WHEN** выполняется поиск по `apps/api/internal` идентификаторов `RLSContext`, `WithRLSConn`, `rlsConnFromContext`
- **THEN** совпадений не найдено
- **AND** проект компилируется и все тесты проходят

### Requirement: Доступ к заявкам

Заявки незавершивших регистрацию SHALL быть доступны ролям куратора и супер-администратора. Пользователь без одной из этих ролей MUST NOT получать к ним доступ.

#### Scenario: Куратор получает доступ

- **WHEN** пользователь с ролью куратора обращается к заявкам
- **THEN** доступ предоставляется

#### Scenario: Супер-администратор сохраняет доступ

- **WHEN** пользователь с ролью супер-администратора обращается к заявкам
- **THEN** доступ предоставляется

#### Scenario: Обычный пользователь

- **WHEN** пользователь без привилегированной роли обращается к заявкам
- **THEN** доступ не предоставляется

#### Scenario: Без аутентификации

- **WHEN** к заявкам обращаются без действующей сессии
- **THEN** доступ не предоставляется

### Requirement: Доступ к разговорам поддержки

Разговоры поддержки SHALL быть доступны ролям куратора и супер-администратора.

#### Scenario: Куратор разбирает очередь разговоров

- **WHEN** пользователь с ролью куратора обращается к списку разговоров
- **THEN** доступ предоставляется

#### Scenario: Обычный пользователь

- **WHEN** пользователь без привилегированной роли обращается к разговорам
- **THEN** доступ не предоставляется

### Requirement: Заявки и разговоры вне группы клиентских маршрутов

Маршруты заявок и разговоров поддержки MUST NOT находиться внутри группы маршрутов, охраняемой проверкой отношения куратора и клиента.

#### Scenario: Заявка не имеет отношения к куратору

- **WHEN** маршрут заявки размещается в группе, требующей отношения куратора и клиента
- **THEN** доступ к нему невозможен, поскольку у заявки нет клиента
- **AND** такое размещение считается ошибкой

#### Scenario: Механизм защиты объявлен явно

- **WHEN** маршрут заявки или разговора несёт идентификатор в пути
- **THEN** он присутствует в реестре защищаемых маршрутов с механизмом «роль»

#### Scenario: Маршрут отсутствует в реестре

- **WHEN** маршрут с идентификатором в пути отсутствует в реестре защищаемых маршрутов
- **THEN** сборка завершается ошибкой

### Requirement: Единственный путь к заявкам и разговорам

После переноса SHALL существовать ровно один путь к заявкам и ровно один к разговорам поддержки. Прежние административные пути MUST NOT оставаться доступны.

#### Scenario: Прежний путь удалён

- **WHEN** выполняется обращение по прежнему административному пути к заявкам
- **THEN** маршрут не найден

#### Scenario: Фронтенд обращается к существующему пути

- **WHEN** проверка контракта сопоставляет вызовы фронтенда с таблицей маршрутов
- **THEN** каждый вызываемый путь присутствует в таблице
