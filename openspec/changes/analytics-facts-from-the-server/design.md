# Design

## Context

Мотивация — в `proposal.md`, раздел Why. Здесь только то, что определяет подход.

`Validate` (`analytics/service.go:92`) отвергает свойство, не объявленное для
имени события. `Record` (строка 150) проверяет **все** события пакета и
возвращает отказ на первом негодном — до единой вставки. Ручка отвечает
`400`, и на этом след теряется: `flush()` очищает очередь до отправки
(`client.ts:103`), а `sendBeacon` кода ответа не сообщает по устройству.

`ServerOnly` в словаре уже существует и применён к шести событиям
(`dictionary.go:102`), а `RecordServerEvent` (строка 175) уже умеет писать факт
от имени учётной записи. То есть механизм есть — нужно применить его ещё к двум
именам и добавить одну разновидность: факт, случающийся однажды.

`analytics_identities` наполняется с 2026-09-26 (`e33838aa`), и связка
проверена. Значит серверное событие получит настоящий идентификатор браузера
там, где человек пришёл по рекламе, — это условие рекламной выгрузки.

## Goals / Non-Goals

**Goals:**

- Ни одно годное событие не теряется из-за негодного соседа.
- Об отказе можно узнать, не имея доступа к браузеру.
- «Первый раз» определяется тем, что человек сделал, а не тем, что помнит его
  браузер.

**Non-Goals:**

- Сверка клиентских вызовов `track()` со словарём — отдельное изменение.
- Перенос остальных клиентских событий на сервер: они несут контекст, который
  знает только браузер.
- Повторная отправка отклонённых событий и любая очередь на клиенте.
- Изменение состава рекламных конверсий.

## Decisions

### Приём пакета частичный, отказ — в журнал

Каждое событие проверяется отдельно; годные вставляются одной транзакцией;
отклонённые записываются в журнал уровня `WARN` с именем и причиной. Ответ —
`202 {"recorded": N, "refused": M}`.

Отвергнуто: **оставить всепакетный отказ, добавив громкость** — цена одной
опечатки в свойстве остаётся «потерян весь пакет», а пакет собирает события
разных мест: заявка гибла вместе с захватом контакта, первая запись о еде —
вместе с записью о еде. Отвергнуто: **уронить сборку на несовпадении** —
правильная мера, но она про все события сразу и делается отдельным изменением;
здесь она не помогла бы уже выпущенным клиентам.

Уровень `WARN`, а не `ERROR`: сразу после выкатки уже открытые вкладки старой
сборки продолжат присылать перенесённые имена и получать законный отказ. `ERROR`
на предсказуемом переходном шуме обесценил бы уровень, а условие восстановимое —
пакет больше не гибнет.

Требование 1 спеки `product-analytics` говорит «**событие** с несоответствующими
свойствами MUST отклоняться». Код делал больше обещанного; изменение приводит
его в соответствие, а не ослабляет.

### «Первый раз» — примитив в аналитике

`RecordFirstTimeEvent(ctx, name, userID)` вставляет событие одним оператором,
если события с этим именем у этого пользователя ещё нет:

```sql
INSERT INTO analytics_events (name, visitor_id, user_id, platform, properties)
SELECT $1, COALESCE((SELECT visitor_id FROM analytics_identities WHERE user_id = $2 LIMIT 1),
                    gen_random_uuid()), $2, 'server', '{}'::jsonb
WHERE NOT EXISTS (SELECT 1 FROM analytics_events WHERE user_id = $2 AND name = $1)
```

Знание «это бывает однажды» живёт в аналитике, а не в трекере еды и не в чате.

Отвергнуто: **выводить из данных предметной области** («у него ровно одна своя
запись») — человек, удаливший записи и добавивший новую, получил бы событие
второй раз. Отвергнуто: **столбец-флаг у пользователя** — миграция и новое
состояние, способное разойтись с действительностью.

Индекса хватает существующего — `idx_analytics_events_user` по
`(user_id, occurred_at)`, записей на человека единицы.

### Отправка — из служб, а не из обработчиков

`first_food_entry` отправляет `food-tracker/service.go` `CreateEntry`. Это
единственный путь, которым человек записывает еду сам: путь куратора через чат
пишет в `food_entries` своим запросом (`chat/service.go:660`) и сюда не заходит.
Поэтому проверки на `created_by` нет — принадлежность действия человеку
обеспечена местом вызова, а не условием, которое можно забыть.

`first_curator_message` отправляет `chat/service.go` `SendMessage` при условии,
что отправитель — клиент этой переписки. Условие в службе, потому что она
держит строку переписки; обработчик знает только «другого участника».

Отвергнуто: **отправлять из обработчиков** — обработчик чата не знает, кто в
переписке клиент, и пришлось бы либо задавать лишний вопрос базе, либо
повторить знание о переписке во втором месте.

### `method` у `first_food_entry` убирается

Сервер способа записи не знает: в `CreateEntryRequest` его нет. Свойство при
этом отправлялось **ноль раз** — клиент всё время посылал `meal_type`. Разбивка
по способу остаётся у `food_entry_created`, который остаётся клиентским.

Отвергнуто: **передавать способ в запрос создания записи** — поле в контракте
API ради разбивки, которая уже есть в соседнем событии.

### `lead_saved` получает `capture_source` с ограничением значений

Набор — `result | contact_step | bot`, те три, что задокументированы в
комментарии к столбцу `leads.capture_source` (миграция 077).

Отвергнуто: **объявить свойство без ограничения** — опечатка в значении дала бы
строку, по которой не сойдётся ни один запрос; ровно поэтому ограничение уже
стоит у `depth`.

### Имена удаляются из клиентского словаря

В `events.ts` серверные факты не объявлены — ни `registered`, ни `signed_in`, ни
остальные четыре. Два перенесённых имени уходят туда же, а `dictionary_test.go`
остаётся зелёным: он намеренно пропускает `ServerOnly` при сверке с клиентом
(строка 29).

Отвергнуто: **оставить имена на клиенте** — объявление, которым никто не
пользуется и пользоваться не может, вводит в заблуждение следующего читателя.

## Risks / Trade-offs

- **Частичный приём делает потерю отдельного события тише.** Раньше терялся
  пакет — заметно по дыре в данных; теперь теряется одно событие → отказ пишется
  в журнал с именем и свойством, а систематическая сверка вызовов со словарём
  идёт отдельным изменением. До неё возможность завести третье несовпадение
  остаётся.

- **Два одновременных первых действия могут дать два события.** `NOT EXISTS` не
  сериализует вставки → последствие безвредно, отчёты считают различных людей.
  Уникальный частичный индекс закрыл бы это, но потребовал бы миграции; если
  однажды понадобится считать события, а не людей, его придётся завести.

- **Переходный шум в журнале.** Уже открытые вкладки будут получать отказ
  «серверный факт из браузера» → уровень `WARN`, формулировка отличима от
  настоящего несовпадения свойства, живёт до закрытия вкладок.

- **Обоснование в активном change устаревает.** В
  `openspec/changes/metrika-ads-bridge/whitelist.md:34` записано, что
  `first_food_entry` — исключение в списке рекламных конверсий, потому что
  событие клиентское → после переноса это перестаёт быть правдой, и документ
  обновляется здесь же: событие становится таким же серверным фактом, как
  остальные три в списке, а условие выгрузки по идентификатору браузера
  выполняется через `analytics_identities`.

## Migration Plan

Миграций базы данных нет.

Порядок выкатки: API и веб в одной поставке. Разнобой безопасен в обе стороны —
новый API с прежним вебом отклонит присланные браузером факты и запишет свои;
прежний API с новым вебом просто не получит этих событий ни от кого, как и
сейчас.

Откат: возврат кода возвращает прежнее поведение. Записанные серверные события
остаются в таблице и корректны; клиентских записей этих имён не появлялось
никогда, так что смешения не будет.

Проверка после выкатки — по данным: зарегистрироваться, записать еду, написать
куратору, оставить заявку и убедиться, что в `analytics_events` появились
`first_food_entry`, `first_curator_message`, `lead_saved`, `contact_captured`.
Для последних двух это будут первые записи за всё время.
