## Context

Бот поддержки при эскалации уведомляет всех суперадминов. На проде их двое, и
ни один не ведёт клиента, задавшего вопрос. Куратор ведёт — у него дневник,
переписка и история этого человека.

Ограничение, вокруг которого строится половина этого изменения: **Telegram-бот
не может написать первым**. Bot API принимает только числовой `chat_id`, и
получить его можно единственным способом — человек сам открыл бота. В профиле
сегодня хранится `user_settings.telegram_username`, то есть имя, по которому
отправить нельзя. Числового идентификатора пользователя в базе нет нигде.

Существующее, на что опираемся:

- `curator_client_relationships(curator_id, client_id, status)` — связь клиента
  с куратором, активная при `status = 'active'`.
- `notifications` + `notification_preferences(channel IN ('app','email','push'))`
  — доставка по настройкам получателя.
- `telegram.Client.SendMessage(ctx, chatID int64, text)` — отправка уже есть.
- `ws_tickets(token_hash PK, user_id, expires_at, used_at)` и
  `RedeemWSTicket` — рабочий образец одноразового билета в этом же коде.

## Goals / Non-Goals

**Goals:**

- Эскалацию получает тот, кто знает клиента.
- Суперадмины остаются страховкой, а не адресатом по умолчанию.
- Оператора можно достать в Telegram, если он этого захотел.
- Отсутствие привязки ничего не ломает.

**Non-Goals:**

- Не делаем Telegram настраиваемым каналом в предпочтениях. Просили «добавить к
  тому, что уже настроено», а не «дать ещё один переключатель».
- Не переносим в Telegram ответы оператора клиенту — отвечают по-прежнему через
  `/admin/support`.
- Не трогаем маршрутизацию обычных уведомлений, не связанных с поддержкой.
- Не переносим очередь операторов куратору: доступ к `/admin/support` остаётся
  за суперадмином. Куратор получает уведомление, а не новый экран.

## Decisions

### Одноразовый случайный билет, а не подписанный токен

Берём образец `ws_tickets`: случайные 32 байта, в базе хранится хэш, redeem —
пометка и чтение **одним** запросом (`UPDATE ... WHERE used_at IS NULL AND
expires_at > NOW() RETURNING user_id`).

Почему не HMAC, как у лидов: одноразовость всё равно требует состояния в базе,
а раз состояние есть, подпись не добавляет ничего. Токен лида намеренно
_повторно используемый_ в пределах срока — здесь нужно ровно обратное.

Отдельная причина держаться этого образца: пометка и чтение одним запросом
закрывают гонку, когда по ссылке переходят дважды подряд. Разнесённые проверка
и пометка дали бы две успешные привязки.

**Ограничение Telegram:** параметр `start` — до 64 символов из `A-Za-z0-9_-`.
32 байта в base64url дают 43 символа и проходят. Это ограничение стоит держать
в голове при любой правке формата билета.

### Хранение: отдельная таблица, а не столбец в user_settings

```
telegram_links(
  user_id   BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  chat_id   BIGINT NOT NULL UNIQUE,
  username  TEXT,
  linked_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
)
```

`UNIQUE(chat_id)` — то самое требование «один Telegram не может быть двумя
кураторами». В столбце `user_settings` этого не выразить так же прямо.
`username` хранится справочно, для показа в профиле; решения по нему не
принимаются никогда.

### Стирание аккаунта: обе новые таблицы получают стратегию

`telegram_links` и таблица билетов — обе `StrategyDelete`. Это не
предусмотрительность, а обязанность: `TestErasureCoversSchema` роняет сборку на
таблице с `user_id` без стратегии, и правильно делает. `ON DELETE CASCADE` тут
не спасает — стирание обезличивает строку пользователя, а не удаляет её.

### Выбор получателей

```sql
SELECT curator_id FROM curator_client_relationships
 WHERE client_id = $1 AND status = 'active'
```

Пусто или обращение без `user_id` → действующие суперадмины (не удалённые и не
ожидающие удаления), как сейчас.

Решение принимается **в момент эскалации**, а не при создании обращения: между
первым вопросом и эскалацией куратор может смениться.

### Telegram — дополнительная доставка, не канал предпочтений

`CHECK (channel IN ('app','email','push'))` не трогаем. Telegram отправляется
поверх, сразу после создания уведомления, если привязка есть.

Альтернатива — добавить `'telegram'` в каналы — отклонена: тогда сообщения не
пойдут, пока человек не включит канал в настройках, а просили обратного. Плюс
это миграция `CHECK` на двух таблицах ради поведения, которого не просили.

### `/start` обрабатывается до логики поддержки

Команда привязки перехватывается в вебхуке раньше, чем сообщение станет
вопросом: не создаёт обращение, не идёт в модель, не тратит дневной лимит.
`/start` без параметра остаётся обычным приветствием бота.

### Отказ Telegram не отменяет уведомление

Отправка в Telegram — после создания уведомления и в отдельной ветке ошибок.
Логика та же, что у `notifyOperators` сегодня: эскалация уже произошла, человек
в Telegram уже услышал «сейчас подключится человек», и откатывать это из-за
недоставленного сообщения — неверный размен.

## Risks / Trade-offs

- **Суперадмин перестаёт видеть обращения клиентов с куратором** → очередь
  `/admin/support` по-прежнему показывает всё; меняется только адресат
  уведомления. Требует правки `docs/curator-guide/11-бот-поддержки.md`, где
  сейчас написано, что зовут администратора.
- **Ссылка привязки — это право получать чужие обращения** → короткий срок,
  одноразовость, в базе хэш, а не сам билет; отказ пишется в журнал.
- **Куратор не привязал Telegram или отключил бота** → уведомление всё равно
  уходит обычными каналами. Молчание Telegram не должно выглядеть как молчание
  системы.
- **Бот заблокирован получателем** → Telegram отвечает ошибкой; пишем в журнал
  и не повторяем. Повторы здесь ничего не чинят.
- **Куратор один и он недоступен** → раньше тревогу видели двое суперадминов,
  теперь один куратор. Это осознанный размен: адресность против подстраховки.
  Наблюдать по времени ответа на эскалации.
- **Клиент сменил куратора между вопросом и эскалацией** → выбор в момент
  эскалации даёт нового, что и правильно.

## Migration Plan

1. Миграция: `telegram_links` и таблица билетов.
2. Стратегии стирания для обеих таблиц (иначе сборка не пройдёт).
3. Выкатка: маршрутизация меняется сразу, Telegram-канал молчит, пока никто не
   привязался — деградация мягкая, отдельного этапа не требует.
4. Откат: обратная миграция удаляет таблицы; маршрутизация возвращается
   откатом кода. Данных, которые жалко потерять, в этих таблицах нет.

## Open Questions

- Нужно ли уведомлять куратора, когда обращение **закрыто** другим оператором?
  Сейчас нет, и это кажется правильным, но проверить на первых живых
  обращениях.
- Показывать ли в `/admin/support`, кому именно ушло уведомление? Полезно при
  разборе «почему никто не ответил», но это отдельная задача.
