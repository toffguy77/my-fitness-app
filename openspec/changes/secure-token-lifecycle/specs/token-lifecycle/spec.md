## ADDED Requirements

### Requirement: Refresh-токен недоступен из JavaScript

Сервер SHALL передавать refresh-токен исключительно в cookie с атрибутами `HttpOnly`, `Secure`, `SameSite=Strict` и `Path=/api/v1/auth`. Тело ответов эндпоинтов входа, регистрации и обновления токена MUST NOT содержать refresh-токен.

#### Scenario: Успешный вход

- **WHEN** пользователь успешно выполняет `POST /api/v1/auth/login`
- **THEN** ответ содержит заголовок `Set-Cookie` с refresh-токеном и атрибутами `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth`
- **AND** тело ответа содержит access-токен и не содержит поля `refresh_token`

#### Scenario: Обновление токена по cookie

- **WHEN** клиент вызывает `POST /api/v1/auth/refresh` с валидной refresh-cookie и пустым телом
- **THEN** ответ содержит новый access-токен в теле
- **AND** ответ содержит `Set-Cookie` с ротированным refresh-токеном

#### Scenario: Выход

- **WHEN** пользователь вызывает `POST /api/v1/auth/logout`
- **THEN** ответ содержит `Set-Cookie`, очищающий refresh-cookie
- **AND** соответствующий refresh-токен помечен отозванным в базе данных

### Requirement: Access-токен не сохраняется в постоянном хранилище браузера

Клиент SHALL хранить access-токен только в памяти исполняемого кода. Значения access- и refresh-токена MUST NOT записываться в `localStorage`, `sessionStorage`, IndexedDB или cookie, доступную из JavaScript.

#### Scenario: Проверка хранилищ после входа

- **WHEN** пользователь вошёл в приложение
- **THEN** `localStorage` и `sessionStorage` не содержат ключей со значением access- или refresh-токена

#### Scenario: Восстановление сессии после перезагрузки

- **WHEN** пользователь с валидной refresh-cookie перезагружает страницу
- **THEN** приложение выполняет `POST /api/v1/auth/refresh` при инициализации
- **AND** после успешного ответа пользователь остаётся аутентифицированным без повторного ввода пароля

#### Scenario: Доступ к токену только через модуль хранения

- **WHEN** выполняется поиск обращений к `localStorage` за токеном за пределами модуля хранения токенов
- **THEN** совпадений не найдено

### Requirement: Авторизация WebSocket одноразовым тикетом

Подключение к `/ws` SHALL авторизовываться одноразовым тикетом, полученным через `POST /api/v1/auth/ws-ticket`. Тикет MUST быть криптографически случайным, действовать не более 30 секунд и становиться недействительным после первого использования. Передача JWT в параметрах запроса MUST NOT использоваться.

#### Scenario: Подключение с валидным тикетом

- **WHEN** клиент получает тикет и подключается к `/ws?ticket=<значение>` в пределах срока действия
- **THEN** соединение устанавливается
- **AND** тикет помечается использованным

#### Scenario: Повторное использование тикета

- **WHEN** клиент подключается к `/ws` с тикетом, который уже был использован
- **THEN** сервер отвечает статусом `401` и не устанавливает соединение

#### Scenario: Просроченный тикет

- **WHEN** клиент подключается к `/ws` с тикетом старше 30 секунд
- **THEN** сервер отвечает статусом `401`

#### Scenario: Попытка подключения с JWT

- **WHEN** клиент подключается к `/ws?token=<jwt>`
- **THEN** сервер отвечает статусом `401`

### Requirement: Маскирование секретов в логах запросов

Логгер HTTP-запросов SHALL заменять значения параметров запроса с именами `token`, `ticket`, `refresh_token`, `code`, `state`, `password` на маску перед записью в лог.

#### Scenario: Запрос с тикетом в query

- **WHEN** обрабатывается запрос `GET /ws?ticket=abcdef0123456789`
- **THEN** в записи лога поле query не содержит подстроку `abcdef0123456789`
- **AND** содержит имя параметра `ticket` с маскированным значением

#### Scenario: Запрос с диагностическими параметрами

- **WHEN** обрабатывается запрос `GET /api/v1/dashboard/week?days=7`
- **THEN** в записи лога поле query содержит `days=7` без изменений

### Requirement: Ограничение частоты для эндпоинтов, отправляющих письма и выдающих тикеты

Эндпоинты `POST /api/v1/auth/resend-verification` и `POST /api/v1/auth/ws-ticket` SHALL иметь ограничение частоты вызовов по идентификатору пользователя и по IP-адресу.

#### Scenario: Превышение лимита повторной отправки письма

- **WHEN** пользователь вызывает `POST /api/v1/auth/resend-verification` чаще установленного лимита
- **THEN** API отвечает статусом `429`
- **AND** письмо не отправляется
