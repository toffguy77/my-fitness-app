## Context

Текущая схема: `POST /auth/login` возвращает `{token, refresh_token}`; фронт кладёт оба в `localStorage`; `api-client` подставляет `Authorization: Bearer`, а при `401` дёргает `/auth/refresh` с refresh-токеном в теле. На бэкенде refresh-токены хранятся хешами в `refresh_tokens` с ротацией и детекцией переиспользования (`auth/service.go:251-330`) — серверная часть сделана хорошо. Слабое звено — клиентское хранилище и то, что отзыв работает только по одному триггеру.

Ограничения контура: прод — nginx перед Next.js и Go API на одном домене (`burcev.team`), поэтому cookie первого уровня работают без CORS-осложнений; `AllowCredentials: false` в CORS (`main.go:230`) придётся включить только если появятся кросс-доменные клиенты — сейчас нет. PWA с service worker уже установлен, но `/api/v1/*` помечен `NetworkOnly`, так что кэширование ответов с токенами не грозит.

## Goals / Non-Goals

**Goals:**
- XSS перестаёт давать долговременный доступ: refresh-токен недоступен из JavaScript.
- Токены не попадают в логи и историю прокси.
- Смена и сброс пароля немедленно завершают все сессии пользователя на всех устройствах.
- Защита маршрутов перестаёт быть обязанностью каждой страницы.

**Non-Goals:**
- Не переходим на серверные сессии — JWT остаётся форматом access-токена.
- Не вводим device-management UI («активные сессии») — отдельная фича.
- Не трогаем 2FA.
- Не меняем срок жизни токенов и логику `remember_me`.

## Decisions

**Решение 1. Refresh — `HttpOnly` cookie, access — переменная в памяти.**
Cookie: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age` по `remember_me`. Access-токен живёт в замыкании модуля `token-storage`, не в `localStorage` и не в `sessionStorage`.
*Почему так:* это ровно та граница, где XSS теряет силу. Access-токен коротко живёт и при XSS всё равно читается из памяти — но окно ограничено его TTL, а не бесконечной ротацией.
*Стоимость:* после перезагрузки страницы access-токена нет, нужен «тихий» `/auth/refresh` при инициализации приложения — один дополнительный запрос на холодный старт.
*Альтернатива:* оба токена в cookie. Отвергнута: пришлось бы переводить весь API на cookie-аутентификацию и вводить CSRF-защиту на каждый мутирующий запрос; `Authorization: Bearer` для access проще и уже работает.
*Альтернатива:* оставить `localStorage` и ужесточить CSP. Отвергнута: CSP с nonce снижает вероятность XSS, но не устраняет последствия; для данных о здоровье этого мало.

**Решение 2. `SameSite=Strict` и `Path=/api/v1/auth`.**
Cookie нужна только эндпоинтам `refresh` и `logout`. Узкий `Path` означает, что она не прикладывается к остальным ~100 запросам — меньше поверхности и меньше трафика.
*Следствие:* CSRF-защита для refresh не нужна отдельно — `SameSite=Strict` закрывает межсайтовую отправку, а сам refresh не является чувствительной мутацией (он ротирует токен, а не меняет данные).
*Альтернатива:* `SameSite=Lax`. Отвергнута: `Strict` не мешает, потому что пользователь никогда не попадает на `/api/v1/auth/refresh` переходом по внешней ссылке.

**Решение 3. WebSocket — одноразовый ticket, а не JWT в query.**
`POST /auth/ws-ticket` возвращает 32 байта из `crypto/rand` в hex; сервер хранит хеш в таблице `ws_tickets` с `user_id`, `expires_at = now() + 30s`, `used_at`. `/ws` обменивает ticket на сессию и сразу помечает `used_at`.
*Почему так:* браузерный `WebSocket` не умеет кастомные заголовки, поэтому секрет неизбежно оказывается в URL. Пусть в URL окажется значение, которое живёт 30 секунд и сгорает после первого использования, а не JWT на весь срок жизни.
*Альтернатива:* передавать JWT в `Sec-WebSocket-Protocol`. Отвергнута: работает, но это нецелевое использование заголовка, ломается на части прокси и всё равно требует серверной поддержки — сложность та же, а семантика хуже.
*Альтернатива:* оставить JWT в query и только маскировать логи. Отвергнута: токен всё равно попадает в историю браузера, Referer и логи промежуточных узлов, которые мы не контролируем.
*Альтернатива:* хранить тикеты в памяти процесса. Отвергнута: ломается при нескольких инстансах и при рестарте; таблица в PostgreSQL стоит один индексный запрос.

**Решение 4. Маскирование query — в логгере, списком ключей.**
`logger.go` парсит `RawQuery` и заменяет значения ключей `token`, `ticket`, `code`, `state`, `refresh_token`, `password` на `***`.
*Альтернатива:* не логировать query вовсе. Отвергнута: query полезен для диагностики (`?date=`, `?days=`, пагинация).

**Решение 5. `token_version` в `users` для мгновенного отзыва access-токенов.**
JWT-claims получают поле `tv`. `RequireAuth` сравнивает его с `users.token_version`. Смена пароля, сброс пароля и «выйти со всех устройств» инкрементируют колонку.
*Стоимость:* один запрос к БД на каждый аутентифицированный запрос.
*Смягчение:* значение читается из того же запроса, который и так делают многие хендлеры? Нет — надёжнее кэш в памяти процесса на 30 секунд (`user_id → token_version`) с инвалидацией при инкременте. Итого: в худшем случае отзыв применяется с задержкой до 30 секунд, что приемлемо и явно зафиксировано в спеке.
*Альтернатива:* полагаться только на отзыв refresh-токенов. Отвергнута: access-токен продолжал бы работать до истечения TTL — окно, в которое злоумышленник сохраняет доступ уже после того, как жертва сменила пароль.
*Альтернатива:* чёрный список токенов (jti). Отвергнута: требует хранилища на каждый выданный токен; `token_version` даёт тот же эффект одной колонкой.

**Решение 6. `middleware.ts` проверяет только признак наличия сессии.**
Middleware не валидирует JWT (у него нет секрета и не должно быть) — он проверяет наличие refresh-cookie и редиректит неаутентифицированных на `/auth`, сохраняя `?next=`. Реальная авторизация остаётся на API.
*Почему так:* убирает мигание защищённого UI и делает защиту свойством конфигурации `matcher`, а не каждой страницы.
*Альтернатива:* валидация JWT в middleware. Отвергнута: потребовала бы секрет в Next.js-рантайме — расширение поверхности компрометации ради того, что API и так проверяет.

**Решение 7. CSP через nonce, генерируемый в `middleware.ts`.**
`script-src 'self' 'nonce-<random>'`, `'unsafe-eval'` удаляется. Инлайновый скрипт регистрации service worker в `layout.tsx:58` получает nonce.
*Риск:* Next.js в отдельных режимах требует `'unsafe-eval'` для dev; в проде — нет. Проверяется задачей.

## Risks / Trade-offs

- **Риск: пользователи разлогинятся при выкатке** — старые токены в `localStorage` перестанут использоваться. → Одноразовый шаг миграции на клиенте: при инициализации, если в `localStorage` есть `refresh_token`, обменять его на cookie через `/auth/refresh` и очистить хранилище. Живёт два релиза, затем удаляется (задача 6.3).
- **Риск: холодный старт замедляется на один запрос `/auth/refresh`.** → Запрос идёт параллельно с гидратацией; `middleware.ts` уже отсекает неаутентифицированных, так что лишний запрос делают только вошедшие.
- **Риск: `token_version` добавляет запрос к БД на каждый запрос.** → Кэш в памяти на 30 секунд; задержка отзыва до 30 секунд зафиксирована в спеке как допустимая.
- **Риск: ужесточение CSP ломает сторонние скрипты** (Яндекс.Метрика в `layout.tsx`). → Проверить на dev до прода; при необходимости добавить домен Метрики в `script-src` явным источником, но не возвращать `'unsafe-inline'`.
- **Риск: `ws_tickets` растёт неограниченно.** → Периодическая чистка просроченных строк фоновой задачей из изменения `background-jobs-infrastructure`; до его готовности — удаление просроченных при каждой выдаче нового тикета.
- **Trade-off: access-токен в памяти теряется между вкладками.** Каждая вкладка делает свой `/auth/refresh`. Принимаем: refresh ротируется атомарно в транзакции, а детекция переиспользования уже имеет grace-period (`auth/service.go:267-280`).

## Migration Plan

1. Миграция БД: `users.token_version` со значением по умолчанию `0`, таблица `ws_tickets`.
2. Бэкенд: выдавать cookie **и** продолжать возвращать `refresh_token` в теле (совместимость), принимать refresh из cookie и из тела.
3. Фронтенд: перейти на cookie, включить одноразовую миграцию из `localStorage`.
4. Выкатить, убедиться по метрикам, что доля запросов `/auth/refresh` с телом упала до нуля.
5. Бэкенд: убрать `refresh_token` из тела ответов и приём из тела.
6. Через два релиза удалить код одноразовой миграции.

**Откат:** шаги 2–3 обратно совместимы и откатываются возвратом образа. Шаг 5 необратим без отката фронтенда — выполнять только после подтверждения по метрикам.
