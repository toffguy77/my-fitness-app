## Context

Как метрики дня хранятся сейчас:
- одна строка `daily_metrics` на пользователя и дату: вес, шаги, тренировка (`workout_type`, `workout_duration`);
- пишется через `POST /dashboard/daily` одной метрикой за запрос;
- дата — `YYYY-MM-DD` в часовом поясе профиля (`middleware/timezone.go`, по умолчанию `Europe/Moscow`).

Тренировка увеличивает норму калорий (`nutrition-calc`). Задача-тренировка
синхронизирует метрику сама (`metric_synced`).

В Здоровье у шагов несколько источников: телефон и часы пересекаются по
времени. Правильную сумму без двойного счёта даёт только
`HKStatisticsCollectionQuery` с `.cumulativeSum` — суммирование отдельных
сэмплов на сервере даст завышенное число.

## Goals / Non-Goals

**Goals:**
- Шаги, вес и тренировки появляются у клиента и куратора без ручного ввода, в том числе пока приложение закрыто.
- Ручное значение никогда не затирается импортом.
- Повторная отправка той же пачки ничего не меняет.

**Non-Goals:**
- Сон, пульс, активная энергия, состав тела — не используются продуктом.
- Импорт еды из Здоровья: дневник — источник правды о еде, мы в Здоровье только пишем.
- Health Connect на Android.

## Decisions

### Шаги считает телефон, сервер получает дневные суммы

Приложение строит дневные суммы через `HKStatisticsCollectionQuery` в
часовом поясе **профиля** (не устройства) и отправляет
`{kind: steps, date, value}`. Сервер хранит их как есть.

Отвергнуто:
- **Отправлять сэмплы и суммировать на сервере.** Двойной счёт телефона и
  часов. Плюс трафик: тысячи сэмплов в день.

### Вес — первое взвешивание дня

Из сэмплов `bodyMass` за дату профиля берётся самый ранний. Подсказка в
приложении («Рекомендуется взвешиваться утром натощак») и недельный
отчёт исходят из одного значения в день.

Отвергнуто:
- **Последний за день** — вечерний вес после еды искажает тренд.
- **Среднее** — значение, которого не показывали весы.
- **История всех взвешиваний** — схема `daily_metrics` хранит одно
  значение, а потребителей несколько значений в день нет.

### Тренировки — по UUID, агрегат дня пересчитывается

Каждая `HKWorkout` хранится в `health_workouts` с `external_id = UUID`.
`daily_metrics.workout_*` — производная: сумма длительностей и типы за дату.

Удаления приходят из `HKAnchoredObjectQuery` как `deleted` и убирают строку,
после чего агрегат пересчитывается.

Соответствие типов:

| Здоровье | Взвешено |
|---|---|
| `traditionalStrengthTraining`, `functionalStrengthTraining` | Силовая |
| `running` | Бег |
| `cycling` | Велосипед |
| `swimming` | Плавание |
| `yoga` | Йога |
| `flexibility` | Растяжка |
| `highIntensityIntervalTraining` | HIIT |
| кардио-тренажёры (`elliptical`, `rowing`, `stairClimbing`…) | Кардио |
| прочее | Другое |

Отвергнуто:
- **Хранить только агрегат.** Без UUID повтор пачки удваивает минуты,
  а удаление в Здоровье невозможно отразить.

### Старшинство ручного ввода

У `daily_metrics` появляются колонки `steps_source`, `weight_source`,
`workout_source` со значениями `manual` | `healthkit` | NULL.

- Импорт пишет значение, только если источник NULL или `healthkit`.
- `POST /dashboard/daily` пишет всегда и ставит `manual`.
- Очистка ручного значения (ввод 0 шагов или удаление веса) не
  возвращает импорт сама; следующий импорт за эту дату его вернёт.

Отвергнуто:
- **Здоровье главнее.** Клиент, исправивший шаги руками, увидит, как
  исправление откатывается через минуту.
- **Последний записавший главнее.** Фоновая доставка срабатывает в
  непредсказуемое время, и правка руками «мигает».

### Идемпотентность и размер пачки

Ключ записи:
- шаги и вес — (пользователь, вид, дата);
- тренировка — (пользователь, `external_id`).

Пачка — до 500 записей и до 366 дней назад; не больше 120 пачек в час на пользователя. Вес из Здоровья принимается в границах 20–500 кг — строже ручного ввода (0,1–500): весы, подхватившие ребёнка или питомца, не должны сбить тренд, а человек может ввести что угодно сам. Записи с датой в будущем
отклоняются поштучно, остальные принимаются. Ответ —
`{accepted, rejected: [{index, code}]}`, по образцу
`analytics-batch-partial-acceptance`.

Отвергнуто:
- **Отклонять всю пачку при одной плохой записи.** Одна запись с
  часов с неверной датой блокировала бы синхронизацию навсегда.

### Запись в Здоровье — только с телефона, без сервера

Приложение пишет `dietaryEnergyConsumed`, `dietaryProtein`, `dietaryFatTotal`,
`dietaryCarbohydrates` как `HKCorrelation(.food)` на каждую запись дневника и
`dietaryWater` на каждый стакан.

Метаданные:
- `HKMetadataKeySyncIdentifier = "entry:<id>"`;
- `HKMetadataKeySyncVersion` = номер правки.

Правка записи заменяет образец, удаление — удаляет. Записи, сделанные в вебе
или куратором, попадают в Здоровье при следующем открытии дня в приложении.

Отвергнуто:
- **Не писать еду.** Клиенты, у которых Здоровье — общая картина
  (например, для другого приложения тренировок), просили бы это первым делом.

### Фоновая доставка

`enableBackgroundDelivery`:
- для `bodyMass` и `workoutType` — `.immediate`;
- для `stepCount` — `.hourly`: шаги часто меняются, а часового обновления
  достаточно для «Требуют внимания».

Обработчик `HKObserverQuery` ставит загрузку в очередь (`ios-app-foundation`),
отправляет её и вызывает completion handler.

## Risks / Trade-offs

- [Часовой пояс профиля отличается от часового пояса устройства в поездке] → суммы строятся по поясу профиля, приложение предлагает обновить пояс, если он расходится с устройством дольше суток.
- [Пользователь отозвал доступ в настройках iPhone] → HealthKit не сообщает об отказе на чтение; приложение показывает «нет данных из Здоровья за 3 дня — проверьте доступ» со ссылкой на настройки.
- [Нагрузка при первом подключении — год истории] → первичная загрузка — 90 дней пачками по 500, остальное не загружается.

## Migration Plan

1. Миграция колонок источника (существующие значения — `manual`, где значение задано) и `health_workouts`.
2. Бэкенд с маршрутом импорта; веб показывает подпись источника.
3. Приложение с модулем Здоровья — вместе с первой сборкой TestFlight.

Откат: маршрут импорта убирается, колонки источника остаются и не мешают.
