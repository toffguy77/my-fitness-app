## Context

Приложение работает на российском рынке, и русский останется основным языком в обозримом будущем. Значит цель — не мультиязычность ради неё самой, а два конкретных следствия: развязать API от языка и сделать тексты управляемыми.

Важный контекст момента: три параллельных изменения добавляют новых потребителей API — Telegram-бот, внешние OAuth-провайдеры с их сообщениями об ошибках, переработанный онбординг с большим количеством валидационных текстов. Каждое из них выиграет от кодов ошибок вместо русских строк.

Объём: литеральные строки на кириллице встречаются в сотнях мест. Одномоментный вынос всех — огромный PR, который невозможно отревьюировать и который конфликтует со всем остальным.

## Goals / Non-Goals

**Goals:**
- Клиент, а не сервер, решает, на каком языке говорить с пользователем.
- Изменение формулировки — правка одного файла словаря.
- Появление второго языка не требует изменений в коде, только нового словаря.
- Полнота словарей проверяется автоматически.

**Non-Goals:**
- Не добавляем второй язык в этом изменении. Инфраструктура — да, перевод — нет.
- Не вводим маршруты с языковым префиксом.
- Не переводим документацию и пользовательские руководства.
- Не занимаемся переводом контента, создаваемого кураторами.

## Decisions

**Решение 1. API отдаёт код и параметры, текст формирует клиент.**
Тело ошибки: `{ "error": { "code": "chat.forbidden", "params": { ... } } }`. Коды выводятся из типизированных ошибок `apperrors`, введённых изменением `fix-authorization-gaps`.
*Почему так:* язык — свойство клиента, а не сервера. Побочный выигрыш — исчезает необходимость разбирать смысл ошибки по её тексту.
*Альтернатива:* переводить на сервере по `Accept-Language`. Отвергнута: тянет словари на бэкенд, дублирует их с фронтендом и не решает задачу для клиентов, которым нужны коды (бот, интеграции).

**Решение 2. Переходный период с двумя полями.**
Тело ошибки временно содержит и код, и прежний текст. Клиент предпочитает код, падая на текст при неизвестном коде. Текст удаляется после перевода всех клиентов.
*Почему так:* иначе изменение становится единовременным переключением всего приложения.

**Решение 3. Вынос строк — по разделам, а не одним PR.**
Порядок: аутентификация и онбординг, затем настройки, трекер еды, дашборд, чат, кураторские экраны, административные. Каждый раздел — отдельный PR.
*Почему так:* ревьюируемые изменения и минимум конфликтов с параллельной работой.
*Следствие:* проверка в CI включается по разделам — правило применяется к уже переведённым каталогам, расширяясь по мере продвижения.

**Решение 4. Минимальный собственный словарь вместо библиотеки.**
Плоский объект «ключ → строка» с подстановкой параметров и правилами множественного числа для русского. Ключи — с пространствами имён по разделам.
*Почему не библиотека:* полноценные библиотеки локализации несут маршрутизацию по языкам, ленивую загрузку словарей и серверную интеграцию — всё это нужно при реальной мультиязычности, которой пока нет. Минимальный модуль решает задачу сегодня и не мешает перейти на библиотеку, когда появится второй язык.
*Условие пересмотра:* при добавлении второго языка вернуться к выбору.

**Решение 5. Определение языка: параметр пользователя, затем заголовок, затем русский.**
Поле `settings.language` уже существует и не используется — оно становится первым источником.

**Решение 6. Форматирование — через стандартный механизм интернационализации платформы.**
Даты, числа, единицы измерения — стандартными средствами с явной локалью, а не ручной склейкой строк. Склонения существительных при числительных — отдельной функцией с правилами русского языка.
*Почему это отдельно упомянуто:* «3 продукта / 5 продуктов / 1 продукт» сейчас решается по месту, и часть мест решает неправильно.

**Решение 7. Проверка в CI — два правила.**
Литерал на кириллице в компоненте переведённого раздела ломает сборку. Ключ, используемый в коде и отсутствующий в словаре, ломает сборку.
*Почему автоматически:* на ревью такие вещи пропускаются систематически.

## Risks / Trade-offs

- **Риск: изменение затрагивает почти все файлы и конфликтует с параллельной работой.** → Выполняется после остальных изменений; вынос строк идёт разделами; правило CI включается по каталогам.
- **Риск: клиенты сломаются на новом формате ошибки.** → Переходный период с двумя полями; удаление текста только после проверки.
- **Риск: коды ошибок расплодятся и станут такой же свалкой, как строки.** → Коды выводятся из существующих типизированных ошибок, а не заводятся произвольно; реестр в одном файле с тестом на уникальность.
- **Риск: качество формулировок ухудшится при механическом выносе.** → Вынос сопровождается сверкой одинаковых по смыслу сообщений и приведением их к единой формулировке — это отдельная ценность изменения.
- **Trade-off: собственный словарь вместо библиотеки** означает, что часть возможностей придётся дописывать. Принимаем при одном языке.

## Migration Plan

1. Реестр кодов ошибок на бэкенде, новый формат тела с сохранением текста.
2. Разбор кодов на фронтенде с запасным вариантом по тексту.
3. Модуль словаря и форматирования.
4. Вынос строк по разделам, включение правил CI по каталогам.
5. Перевод писем и шаблонов уведомлений.
6. Удаление текстового поля из тела ошибки.

**Откат:** этапы 1–2 обратно совместимы. Этап 6 — только после подтверждения, что клиентов со старым разбором не осталось.
