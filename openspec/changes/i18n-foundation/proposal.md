## Why

Русский язык зашит в код на обоих слоях. На фронтенде строки лежат прямо в компонентах. На бэкенде русские тексты возвращаются в теле ответов API: `response.Error(c, http.StatusBadRequest, "Файл фото обязателен")` (`apps/api/internal/modules/food-tracker/handler.go:367`), `"Нет доступа к этому чату"` (`chat/handler.go:304`), `"Неверный ID клиента"` (`nutrition-calc/handler.go:175`) — и так по всем модулям. Библиотеки локализации нет ни одной.

Две отдельные проблемы, из которых вторая важнее первой:

1. **API навязывает язык.** Сервер решает, на каком языке разговаривать с пользователем. Любой второй клиент — мобильное приложение, Telegram-бот из изменения `telegram-support-bot`, интеграция — получает русские строки, которые нельзя ни перевести, ни надёжно разобрать. Уже сейчас код вынужден сравнивать текст ошибок подстрокой, чтобы понять их смысл.
2. **Тексты неуправляемы.** Изменить формулировку — значит найти её среди компонентов. Одинаковые по смыслу сообщения расходятся в формулировках между экранами.

Выход за пределы русскоязычного рынка сейчас означал бы переписывание обоих слоёв. Задача этого изменения — не перевести приложение, а сделать так, чтобы перевод стал возможен и чтобы API перестал быть привязан к языку.

## What Changes

- API перестаёт возвращать готовые к показу тексты: тело ошибки получает машиночитаемый код и параметры; человекочитаемый текст формирует клиент.
- Вводится реестр кодов ошибок, единый для бэкенда и фронтенда, с соответствием «код → сообщение».
- **BREAKING (контракт API):** формат тела ошибки расширяется полем кода. Поле с текстом сохраняется на переходный период как запасной вариант и удаляется после перевода клиентов.
- На фронтенде вводится словарь сообщений и функция перевода; строки выносятся из компонентов в словарь русского языка.
- Вводится определение языка: параметр пользователя, затем заголовок `Accept-Language`, затем русский по умолчанию. Существующее поле `settings.language` начинает использоваться.
- Форматирование дат, чисел, единиц измерения и склонений выносится в общие функции с учётом языка.
- Письма и шаблоны уведомлений переводятся на ту же схему словарей.
- Вводится проверка в CI: строка на кириллице в компоненте вне словаря ломает сборку; ключ, отсутствующий в словаре, ломает сборку.

## Impact

**Бэкенд:**
- `apps/api/internal/shared/response/` — формат ошибки с кодом и параметрами.
- `apps/api/internal/shared/apperrors/` — соответствие типизированных ошибок кодам.
- Все `internal/modules/*/handler.go` — замена литеральных русских строк кодами.
- `internal/shared/email/` — шаблоны писем через словари.
- Новое middleware определения языка на основе `settings.language` и `Accept-Language`.

**Фронтенд:**
- Новый `apps/web/src/shared/i18n/` — словари, функция перевода, форматирование.
- Все компоненты с литеральными строками — вынос в словарь.
- `apps/web/src/shared/utils/api-client.ts` — разбор кода ошибки и подстановка сообщения.

**CI:**
- Правило проверки литеральных строк на кириллице вне словаря и полноты ключей.

**Зависимости:** библиотека локализации для Next.js либо собственный минимальный словарь — решается в design.

**Порядок:** после `fix-authorization-gaps` (там вводится типизация ошибок через `apperrors`, на которую опирается реестр кодов). Изменение затрагивает почти все файлы, поэтому выполнять его лучше после остальных, чтобы не создавать конфликтов слияния.
