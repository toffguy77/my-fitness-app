## Context

Соединить две половины оказалось не «позвать эндпоинт»: они написаны независимо
и не совпадают ни по форме, ни по именам, ни по составу полей.

Сервер (`GetRecommendationsResponse`, `types.go:789`):

```json
{ "daily": { "vitamins": [ { "id": …, "daily_target": …, "current_intake": …, "percentage": … } ] },
  "weekly": [ … ],
  "custom": [ { "id": …, "user_id": …, "daily_target": …, "created_at": … } ] }
```

Компонент (`RecommendationsTabProps`):

```ts
recommendations?: NutrientRecommendation[]   // плоский список, camelCase, есть isCustom
customRecommendations?: CustomRecommendation[] // требует currentIntake
currentIntakes?: Record<string, number>      // отдельная карта
```

Расхождений три: группировка против плоского списка, `snake_case` против
`camelCase`, и поля, которых нет на другой стороне — `isCustom` у клиента,
`current_intake` у своих рекомендаций на сервере.

Второе ограничение: у компонента 321 строка и три файла тестов, которые сейчас
проходят. Он не сломан — он просто не подключён.

## Goals / Non-Goals

**Goals:**
- Вкладка рекомендаций показывает данные с сервера; настройки и добавление своих
  работают.
- Ссылка в группу кураторов видна там, где обещает обработчик.
- Маршрут без вызова и без записи в реестре ломает сборку.
- Ни одна цифра не подменяется нулём молча.

**Non-Goals:**
- Не переписываем `RecommendationsTab`. Он протестирован и работает при
  переданных данных; проблема не в нём.
- Не заводим отслеживание потребления для произвольных нутриентов — этого нет на
  сервере, и делать это здесь значит подменить задачу.
- Не трогаем маршруты, законно не вызываемые из браузера: они получают запись в
  реестре, а не переделку.

## Decisions

**Решение 1. Преобразование формы — в слое API, а не в компоненте.**
`recommendationsApi.ts` принимает ответ сервера и отдаёт то, что компонент уже
умеет принимать.
*Почему так:* перекладывание расхождения в компонент означает переписать 321
строку и три файла тестов, которые сейчас проходят. Преобразование в одном месте
дешевле и оставляет проверенный код проверенным.
*Альтернатива:* привести компонент к форме сервера. Отвергнута: цена — потеря
работающих тестов ради формы, которая ничем не лучше.
*Альтернатива:* привести сервер к форме компонента. Отвергнута: `daily`,
сгруппированный по категориям, — то, как вкладка и рисует; разворачивать его на
сервере, чтобы свернуть на клиенте, бессмысленно.

**Решение 2. Потребление для своих рекомендаций отсутствует, и это видно.**
Сервер знает потребление только для нутриентов, которые сопоставляются с КБЖУ
(`service.go:1798`, карта по именам). Для произвольного нутриента взять его
неоткуда.
*Почему это ключевое решение:* очевидный ход — поставить `currentIntake: 0` —
нарисует «0 из 500 мг» и будет выглядеть как измерение. Человек решит, что не
добрал витамина, хотя никто ничего не считал.
*Как вместо этого:* тип `CustomRecommendation.currentIntake` становится
необязательным, а вкладка при отсутствии значения показывает не прогресс, а сам
ориентир. Отсутствие числа честнее нуля.
*Цена:* правка типа и одной ветки отрисовки в компоненте, которого мы решили не
переписывать. Принимается: это единственное место, где расхождение нельзя
спрятать в слой API, не соврав.

**Решение 3. Ответ отдаёт все нутриенты с признаком отслеживания, а не только
отслеживаемые.**
`is_tracked` уже читается запросом (`service.go:1758`), но в
`NutrientRecommendationWithProgress` не попадает — и это половина беды. Вторая:
нутриент с выключенным отслеживанием **выбрасывается из ответа** (`service.go`,
`if !isTracked { continue }` в дневном разборе и `AND COALESCE(unp.is_tracked,
true) = true` прямо в недельном запросе).
*Почему это меняет замысел:* `PUT /recommendations/preferences` ждёт полный
список отслеживаемых нутриентов, а экран настроек не может его собрать — то, что
человек выключил, ему больше не приходит. Переключатели пришлось бы рисовать
наугад, и первое же сохранение настроек стёрло бы выбор, которого экран не видел.
*Как вместо этого:* сервер отдаёт все нутриенты и у каждого — признак; отбор
«показывать во вкладке» делает клиент. Вкладка показывает отслеживаемые, экран
настроек — все.
*Почему это можно менять:* у ответа нет ни одного потребителя — в этом всё
изменение и состоит. Ломать нечего.

**Решение 3а. Снятие галочки должно сохраняться с первого раза.**
Найдено при разборе Решения 3, отдельный дефект.
`UpdateNutrientPreferences` (`service.go:2041`) сбрасывает в `false` только
**существующие** строки, а потом ставит `true` выбранным. Нутриент без строки
читается как отслеживаемый (`COALESCE(unp.is_tracked, true)`). Значит у человека,
который ни разу не менял настройки — то есть у любого, кто открыл экран впервые, —
снятая галочка не сохраняется: строки нет, сбрасывать нечего, вставляется только
выбранное, и при следующем чтении нутриент снова отслеживаемый.
*Как вместо этого:* одна вставка по всему справочнику, `is_tracked` = входит ли
нутриент в присланный список, с `ON CONFLICT DO UPDATE`. Тогда состояние
настроек не зависит от того, есть ли уже строки.
*Почему не поменять значение по умолчанию на `false`:* тогда человек, который
никогда не заходил в настройки, не увидел бы ни одного нутриента. По умолчанию
отслеживается всё — это правильно, ломался именно переход от умолчания к выбору.

**Решение 3б. Подробностям по нутриенту нужен экран, которого нет.**
Четвёртый маршрут — `GET /recommendations/:id` — отдаёт описание, пользу,
действие и вклад продуктов рациона. На клиенте есть тип `NutrientDetail`,
генератор для тестов и обратный вызов `onRecommendationClick`, но ни одного
компонента, который бы это показывал.
*Почему всё же делаем, а не записываем в реестр:* запись «нет экрана» — это не
причина, по которой маршрут законно не зовут, а описание того же дефекта другими
словами. Реестр, куда складывают недоделанное, перестаёт значить что-либо, и
тогда настоящая запись в нём ничего не сторожит.
*Объём:* панель подробностей поверх вкладки. Новый компонент, а не переделка
существующего, — то есть единственное место в изменении, где рисуется что-то с
нуля.
*Что при этом не выдумывается:* описание, польза, действие и границы нормы
приходят с сервера необязательными (`*string`, `*float64`) и в справочнике могут
быть пусты. Пустое поле не показывается вовсе; ноль вместо неизвестной границы не
подставляется — по той же причине, по которой его не подставляют своим
рекомендациям.

**Решение 4. Реестр исключений вместо списка догадок.**
Маршрут без вызова требует записи с причиной; маршрут без вызова и без записи
ломает сборку. Устройство — как у `protectedRoutes` в
`internal/router/authorization_matrix_test.go`.
*Почему так:* «предупреждение в CI» — тот самый способ, которым накопились 584
предупреждения линтера, среди которых потерялась мёртвая директива, сообщавшая
ровно об этом.
*Почему реестр, а не белый список путей:* запись несёт **причину**. Через полгода
вопрос будет не «есть ли здесь исключение», а «почему оно здесь»; список путей на
этот вопрос не отвечает.

**Решение 5. Сопоставление путей понимает все формы записи, а не только
базовые константы.**
Фронтенд пишет пути четырьмя способами: литералом `/api/v1/...`; через
`const BASE = '/api/v1/<домен>'` с `${BASE}/...` (таких констант одиннадцать);
через помощника `getApiUrl('/<домен>/...')`, дописывающего префикс версии
(40 вызовов в 10 файлах); и склейкой плюсом — `'/a/' + id + '/b'`. Плюс
отдельный случай: параметр, за которым идёт строка запроса,
`` `${BASE}/clients/${id}?days=${n}` ``.
*Почему это надо записать:* наивное сопоставление даёт 42 «невызываемых»
маршрута из 164, настоящих среди них 10. Реестр, забитый 32 ложными записями, —
это реестр, которому перестанут верить, и тогда настоящая запись в нём ничего не
будет значить.
*Почему это важнее, чем для прямой проверки:* там невидимый путь — пропущенная
проверка, то есть молчание. Здесь — обвинение вызываемого маршрута в том, что
его не зовут. Молчание терпят, ложь обходят.
*Что осталось известным ограничением:* сопоставление идёт по пути, а не по
методу — метод у вызова взять негде (`apiClient.get`, `post`, `fetch` с
`method` в настройках, обёртки). Путь, у которого зовут хотя бы один метод,
целиком считается вызываемым. Названо, а не обойдено молчанием.

**Решение 5а. Признанный дефект — отдельный вид записи, обязанный указать, где
работа записана.**
Проверка нашла три маршрута, которых ручной разбор не видел: добавление и снятие
избранного и загрузка статьи markdown-файлом. Это не законные исключения и не
часть этого изменения.
*Почему не обычная запись с причиной:* причина была бы «пока не дотянуто» — то
есть описание того же дефекта другими словами. Реестр, куда складывают
недоделанное, перестаёт значить что-либо.
*Как вместо этого:* поле с путём к файлу, где работа записана
(`openspec/changes/server-only-features/proposal.md`), и проверка требует, чтобы
файл существовал и был файлом, а не каталогом. Пустой каталог существует и не
говорит ничего — та же гниль, только проходящая проверку.
*Следствие:* когда работу сделают, маршрут начнут звать, и проверка сама
потребует убрать запись — она сообщает об устаревших.

**Решение 6. Реестр ставится последним шагом.**
*Почему так:* включённый в начале, он делает ветку несобираемой на весь срок
работы, и первое же срочное исправление пойдёт мимо проверок. Та же причина, по
которой `--max-warnings 0` ставили в конце уборки линтера.

**Решение 7. Ссылка в группу показывается только тем, у кого Telegram не
привязан.**
*Почему так:* обработчик существует ровно для них — «боту некуда им написать, он
не пишет первым». Показывать ссылку тому, кто уже в группе, значит предлагать
войти туда, где человек уже есть.

## Risks / Trade-offs

- **Риск: реестр превратится в свалку.** → Запись требует причины, а не галочки;
  ревью читает причину. Плюс Решение 5: без разбора констант реестр сразу
  наполнился бы ложными записями и обесценился.
- **Риск: преобразование формы разойдётся с сервером при первой правке ответа.**
  → Тест на преобразование, собранный из настоящего ответа сервера, а не из
  придуманного объекта.
- **Вкладка покажет пустоту и после соединения, и это не риск, а факт.**
  Справочник `nutrient_recommendations` пуст в обеих средах — проверено
  запросом, не предположено. Пока не выполнено `nutrient-catalogue`, показывать
  нечего, и вкладка обязана сказать это словами: пустой экран без объяснения
  неотличим от поломки. Отдельно от этого: даже с наполненным справочником у
  человека без записей о еде потребление нулевое по всем нутриентам — второе
  честное состояние, которое тоже надо объяснить.
- **Trade-off: своим рекомендациям не показывается прогресс.** Принимается:
  отсутствие числа честнее нуля, который выглядит как измерение.
