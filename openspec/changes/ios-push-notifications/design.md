## Context

Как устроена доставка (`notification-delivery`):

- **Создание.** Доменное событие создаёт строку `notifications`. Строка
  всегда показывается в приложении.
- **Задания.** По матрице каналов (`delivery.go:72`) и предпочтениям
  пользователя создаются задания на каналы `email` и `push`.
- **Push.** Задание обрабатывает `SendDuePushes` (`push.go:125`): отправляет
  на все Web Push-подписки пользователя и учитывает тихое время.
- **Повторы.** Не более трёх попыток (`maxAttempts`).
- **Telegram.** Отправляется поверх любого уведомления, если аккаунт привязан.

Чат уведомлений не создаёт. Новое сообщение приходит только по WebSocket
(`new_message`) и меняет счётчик непрочитанного (`unread_count_update`).

## Goals / Non-Goals

**Goals:**
- Клиент и куратор получают на iPhone пуш о том, что раньше видели только в открытой вкладке.
- Тап по пушу открывает конкретный экран, а не главную.
- Ответить куратору и отметить задачу можно, не открывая приложение.

**Non-Goals:**
- Push to Talk, Live Activities по пушу — не нужны продукту сейчас.
- Пуши Android — отдельное изменение, но таблица и `target` проектируются платформонезависимыми.
- Маркетинговые рассылки пушем.

## Decisions

### Задание на каждый адресат пуша

Сейчас на канал `push` создаётся одно задание (`notification_deliveries`,
`056_notification_delivery_up.sql:25`) с одним `not_before` и общим счётчиком
попыток. Для двух транспортов этого мало по двум причинам:
- Web Push в тихое время откладывается, а APNs уходит сразу, но приглушённо;
- повтор после частичного сбоя снова отправит пуш на устройства, которые уже
  его получили.

Поэтому появляется таблица `push_deliveries`, по строке на адресат:
- `id`;
- `notification_id` (NULL для сообщений чата) или `chat_message_id`;
- `user_id`;
- `transport` (`webpush` | `apns`), `subscription_id` или `device_id`;
- `status` (`pending`, `sent`, `failed`, `skipped`, `cancelled`), `attempts`,
  `not_before`, `last_error`.

Строка `notification_deliveries` канала `push` остаётся сводной: `sent`, если
хотя бы один адресат получил пуш.

Отвергнуто:
- **Одно задание на канал с перебором адресатов.** Не выражает разное
  время доставки и повторяет успешные отправки.
- **Сделать `notification_id` в `notification_deliveries` необязательным ради
  чата.** Таблица описывает доставку уведомлений. Сообщение чата
  уведомлением не является, и сводка «как человеку сообщили» перестала бы
  быть однозначной.

### Таблица `push_devices`, отдельная от Web Push-подписок

Поля таблицы:
- `id`, `user_id`, `token` (уникальный);
- `platform` (`ios`), `environment` (`sandbox` | `production`);
- `app_version`, `created_at`, `last_seen_at`, `disabled_at`.

Регистрация — upsert по `token`. Если токен уже числится за другим
пользователем (выход и вход другим аккаунтом на том же телефоне), он
**переносится**: старая привязка удаляется.

Отвергнуто:
- **Хранить токен APNs в `push_subscriptions` с фиктивным `endpoint`.**
  `validatePushEndpoint` и шифрование Web Push теряют смысл. Ошибки
  двух протоколов разные. Запросы «все устройства iOS» пришлось бы
  строить на разборе строки.
- **Привязка к устройству по `identifierForVendor`.** Лишний идентификатор
  устройства на сервере. Токен APNs и так уникален для пары
  «приложение — устройство».

### APNs: авторизация ключом, `sideshow/apns2`

Токен-авторизация `.p8`: один ключ на все приложения команды, не истекает,
не требует ежегодного продления сертификата. Клиент держит одно
HTTP/2-соединение на окружение.

`environment` устройства выбирает хост: sandbox для сборок из Xcode и
production для TestFlight и App Store.

Отвергнуто:
- **Сертификат `.p12`.** Ежегодное продление, отдельный сертификат на
  каждое окружение.
- **Сторонний сервис рассылки (Firebase и т. п.).** Ещё один обработчик
  персональных данных и данных о здоровье вне контура. Для одной платформы
  выгоды нет.

### `target` вместо разбора веб-пути

У уведомления появляется `target`:

```json
{
  "kind": "chat|task|weekly_feedback|plan|client|support_conversation|lead|article|export|notifications",
  "ids": {"...": "..."}
}
```

Поле сохраняется в `notifications.target`, отдаётся в API (`target`, в camelCase,
как прочие поля уведомлений) и кладётся в пуш. Веб и письма продолжают
пользоваться `actionUrl`.

| Тип | `kind` | `ids` |
|---|---|---|
| `trainer_feedback`, `feedback_received` | `weekly_feedback` | `report_id` |
| `task_assigned`, `task_overdue` | `task` | `task_id` |
| `plan_updated` | `plan` | `plan_id` |
| `support_escalated` | `support_conversation` | `conversation_id` |
| `curator_requested` | `lead` | `lead_id` |
| `client_left` | `client` | `client_id` |
| `new_content` | `article` | `article_id`, `slug` |
| `export_ready` | `export` | `export_id` |
| `chat_message` | `chat` | `conversation_id`, `participant_id` |
| прочее | `notifications` | — |

Отвергнуто:
- **Разбирать `actionUrl` в приложении.** Пути принадлежат вебу и
  меняются вместе с ним (так уже было с `/curator/clients/:id?tab=`). Для
  отзыва на отчёт в пути вообще нет id.
- **Отдельные поля `task_id`, `report_id`… в таблице.** Колонки растут с
  каждым типом, а `jsonb` с перечнем допустимых `kind` проверяется тестом.

### Пуш о сообщении чата без строки в списке уведомлений

После сохранения сообщения сервер смотрит, есть ли у получателя живое
WebSocket-соединение (`shared/ws` хаб, один инстанс). Если нет — создаётся
задание push типа `chat_message`. Через приложение оно не проходит: у чата
своя лента и счётчик.

Задание — строка `push_deliveries` с `chat_message_id` и без `notification_id`; в нагрузке нет `notification_id`.
Пуши группируются по `thread-id = conversation:<id>`. `apns-collapse-id` не
используется: каждое сообщение — отдельный текст.

Пуш не уходит, если с момента сообщения получатель прочитал переписку (проверка
перед отправкой).

Отвергнуто:
- **Строка `notifications` на каждое сообщение.** Список уведомлений
  превращается в копию чата, а «Прочитать все» разъезжается со счётчиком
  непрочитанного в чате.
- **Пушить всегда, даже при открытом чате.** Приложение покажет баннер
  поверх переписки, которую человек и так читает.

Многоинстансность: хаб соединений живёт в памяти одного инстанса.
Требование сформулировано как «нет соединения на инстансе, принявшем
сообщение». Когда инстансов станет больше, проверка переедет в общий реестр
присутствия. Это отмечено в Risks.

### Тихое время на iPhone — приглушить, а не отложить

Действующее требование откладывает пуш до конца тихого интервала. На iPhone
есть уровень `interruption-level: passive`: уведомление попадает в
Центр уведомлений без звука и без включения экрана. Отложенный ответ
куратора, пришедший в 8:00 пачкой, хуже, чем тихо лежащий с 23:10.

Web Push такого уровня не имеет — для него поведение прежнее.

Отвергнуто:
- **Откладывать и на iPhone.** Человек, который сам открыл телефон в
  тихое время, не видит свежий ответ куратора в Центре уведомлений.

### Счётчик на значке

`badge` = непрочитанные уведомления категории `main` + непрочитанные
сообщения чата. Категория `content` не входит: значок не должен краснеть из-за
новой статьи. Значение считается в момент отправки. Приложение уточняет его
само при каждом открытии.

## Risks / Trade-offs

- [Несколько инстансов API — проверка соединения ошибается] → пока прод
  один инстанс (контекст проекта); в коде проверка за интерфейсом
  `Presence`, реализация в памяти; задача на общий реестр — при
  масштабировании.
- [Пуш несёт текст сообщения на экран блокировки] → в настройках
  уведомлений приложения переключатель «Показывать текст сообщений»; без
  него тело — «Новое сообщение от куратора». По умолчанию текст показывается,
  как в мессенджерах.
- [Токены sandbox попадут в production] → окружение передаёт приложение по
  `aps-environment` из entitlements сборки; ошибка `BadDeviceToken`
  отключает устройство.

## Migration Plan

1. Миграция `push_devices` и `notifications.target` (номер — по
   `schema_migrations` dev и прода).
2. Бэкенд с выключенной возможностью `apns`: регистрация отвечает `503`,
   заполнение `target` уже работает.
3. Ключ `.p8` в Dokploy, `APNS_ENVIRONMENT=sandbox` на dev,
   `production` на проде.

Откат: выключить `apns` в конфигурации. Web Push не затронут.
