## Ловушка при пересчёте

Тег Метрики на один просмотр делает **два** обращения:

```
GET /watch/107159088?...&page-url=http%3A%2F%2Flocalhost%3A3070%2F
GET /watch/107159088/1?...&page-url=http%3A%2F%2Flocalhost%3A3070%2F
```

Второе, с `/1`, — внутреннее дело тега, а не второй просмотр: `page-url` у них
один и тот же. Первый подсчёт этой проверки считал оба и показал «2 просмотра
при инициализации», то есть ровно тот задвоенный просмотр, которого Решение 2
и не допускает. Считать нужно обращения, подходящие под `/watch/<id>?`, без
суффикса.

Вторая ловушка того же разбора: `page.goto()` — полная перезагрузка, а не
клиентский переход, и на ней хиты появляются сами от инициализации. Проверять
переход нужно кликом по ссылке, убедившись, что `tag.js` заново не грузился.

## Почему падают сборки на этом сервере

Разобрано попутно, к этому изменению отношения не имеет, но объясняет запись
«сборки падают из-за сети сервера».

Сообщение указывает на Docker и на DNS:

```
mirror.gcr.io/library/node:20-alpine: failed to resolve source metadata:
dial tcp: lookup mirror.gcr.io on 127.0.0.53:53: read udp ...->127.0.0.53:53: i/o timeout
```

Настоящая причина другая. У хоста **нет ни одного глобального IPv6-адреса и
нет маршрута IPv6 по умолчанию**, а DNS отдаёт AAAA-записи: `getent hosts
mirror.gcr.io` возвращает `2a00:1450:4010:c06::52`. Docker идёт по этому адресу
и получает `network is unreachable`:

```
docker: Get "https://registry-1.docker.io/v2/": dial tcp [2600:1f18:...]:443:
connect: network is unreachable
```

IPv4 при этом работает: `curl -s4 https://mirror.gcr.io/v2/` и
`https://registry-1.docker.io/v2/` отвечают `401`, то есть достижимы.

Средство из записи о падении прода — `dns` в `/etc/docker/daemon.json` — уже
применено (`77.88.8.8`, `8.8.8.8`, `1.1.1.1`, файл изменён 2026-09-17 04:57:11,
dockerd перезапущен 04:57:47, то есть настройка в силе). Оно не помогает:
резолверы всё равно отдают AAAA, а ходить по ним некуда.

Отсюда и «повтор помогает»: когда в ответе первым оказывается A-адрес, сборка
проходит. Повтор действительно прошёл — со второй попытки, 8 минут.

Лечится это на хосте, а не в коде, и не мной: на нём работает прод, а рестарт
dockerd его уронит. Варианты в порядке предпочтения — заставить резолвер не
отдавать AAAA для этого хоста, либо отключить IPv6 в ядре, либо поднять
настоящий IPv6-маршрут.

## Сверка через двое суток после выкатки (задача 5.4)

Выполнено 2026-09-26.

**Переходы внутри приложения видны.** В отчёте по путям за 25–26.09 появились
`/profile` (16 просмотров), `/curator` (10), `/settings/profile` (7),
`/curator/chat` (6), `/curator/clients/47` — пути, куда иначе как клиентской
навигацией не попасть. До изменения в отчёте были только `/`, `/auth` и
`/onboarding`, то есть прямые заходы и перезагрузки.

**Глубина просмотра перестала быть единицей:**

| дата | визитов | глубина | отказы |
|---|---|---|---|
| 23.09 (до) | 15 | 1,27 | 67% |
| 24.09 (выкатка) | 3 | 1,67 | 33% |
| 25.09 | 5 | 16,2 | 0% |
| 26.09 | 1 | 1,0 | 100% |

Числа мелкие: 25.09 это пять визитов двух человек, и 16,2 — один человек,
много ходивший по кураторским экранам. Как продуктовая метрика глубина здесь
ничего не значит. Значение имеет качественный сдвиг: глубина больше единицы
появилась вообще, а раньше её не было ни разу.

**Визиты упали с пятнадцати до единиц** — это и есть живой трафик после того,
как прогоны E2E перестали попадать в счётчик.

**Запись сессий.** Проверена в браузере 24.09: `webvisor: false` в опциях
инициализации, обращений к вебвизору нет (см. выше). Отдельного отчёта по
записям Metrika API не отдаёт, поэтому проверка сделана со стороны браузера —
там, где решение и принимается.
