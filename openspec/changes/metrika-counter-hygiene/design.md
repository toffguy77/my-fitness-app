## Context

Согласие на куки уже реализовано: `CookieConsent.tsx` держит решение в
`localStorage` под `analytics-consent`, отдаёт его через `analyticsChoice()` и
`subscribeToAnalyticsChoice()`, а `YandexMetrika.tsx` читает это через
`useSyncExternalStore`. Изменение опирается на этот механизм и не переделывает
его.

Ограничение, из которого растут решения ниже: приложение одностраничное. Опции
счётчика передаются один раз, в `ym(id, 'init', {...})`, при загрузке страницы.
Переинициализировать счётчик с другими опциями на клиентском переходе Метрика
не даёт — значит любая настройка сбора действует на весь визит целиком.

## Goals / Non-Goals

**Goals:**
- Переход между экранами виден в счётчике, и первый просмотр учтён один раз.
- Ни один ввод пользователя не уходит на серверы Яндекса.
- Потеря карты скроллинга и аналитики форм закрыта своими событиями.

**Non-Goals:**
- Не переделываем согласие: оно есть и работает.
- Не передаём `setUserID` — сшивка устройств делается своей аналитикой через
  `POST /api/v1/analytics/identify`.
- Не заводим цели и ретаргетинг — это `metrika-ads-bridge`.

## Decisions

**Решение 1. Хиты отправляет один компонент, наблюдающий за путём.**
*Почему так:* вызов из страницы забудется в первой же новой странице, и воронка
порвётся снова — ровно тем способом, которым она порвана сейчас.
*Альтернатива:* вызывать `hit` в каждом `page.tsx`. Отвергнута: двадцать мест,
которые должны остаться синхронными без всякой проверки.

**Решение 2. Первый просмотр не отправляется хитом.**
`init` сам отправляет просмотр страницы загрузки; компонент пропускает первое
значение пути.
*Почему это надо записать:* без пропуска каждая посадочная получает два
просмотра на один визит, отказы падают вдвое без причины, и следующий человек,
который посмотрит отчёт, поверит, что стало лучше.
*Проверено в браузере:* тег Метрики на один просмотр делает **два** обращения —
`/watch/<id>?` и `/watch/<id>/1?` с одинаковым `page-url`. Второе — внутреннее
дело тега. Считать надо без суффикса, иначе проверка сама себя обманет
(см. `verification.md`).

**Решение 3. Строка запроса читается из `window.location`, а не из `useSearchParams`.**
*Почему так:* метки кампании живут в строке запроса, и хит должен их нести. Но
`useSearchParams` требует границы `Suspense` вокруг компонента при статическом
рендере, а компонент монтируется в корневом макете.

**Решение 4. `webvisor` выключается, а не настраивается маскировкой.**
*Почему так:* маскировка — это список полей, который расходится с формой при
первом же её изменении. Цена расхождения — запись веса и даты рождения на
сторонний сервис, то есть именно то, что запрещено.
*Альтернатива:* включать Вебвизор только на посадочной. Отвергнута, и это
главная причина выключить его целиком: опции задаются один раз за загрузку
страницы, а дальше навигация клиентская. Посетитель, пришедший на `/` и
перешедший в `/onboarding`, продолжает записываться. Разделения по экранам в
одностраничном приложении не существует.
*Цена:* уходят карта скроллинга и аналитика форм — оба отчёта построены на его
данных. Закрывается Решением 5.

**Решение 5. То, что умел Вебвизор и нужно нам, делается своими событиями.**
- Глубина прокрутки посадочной — новое событие, четыре порога, по одному разу
  за визит на порог.
- Шаг отвала мастера уже есть: `onboarding_step_completed` и `last_step`
  заявки. Добавлять нечего.
*Почему так:* оба ответа остаются в своей базе, разрезаются по источнику и
когорте и не зависят от согласия на куки третьей стороны.

**Решение 6. `noscript`-пиксель удаляется.**
*Почему так:* он ставит куку и отправляет визит без JavaScript, в обход любого
согласия. Взамен даёт визиты посетителей с отключённым JavaScript, которые в
приложении на React всё равно не увидят ни одного экрана.

**Решение 7. Проверка согласия для прямых вызовов счётчика — в одном месте.**
`counter.ts` отвечает на два вопроса: есть ли счётчик и можно ли к нему
обращаться. Согласие берётся из `CookieConsent`.
*Почему отдельный модуль, а не повторение в каждом вызывающем:* к счётчику
обращаются из трёх мест — хиты, цели, идентификатор браузера, — и неверный
ответ в любом означает либо счётчик, который молчит, либо счётчик, работающий
без разрешения.

**Решение 8. Счётчик живёт только в проде.**
*Почему так:* dev и прод пишут в один счётчик, и 80% всех визитов — прогоны
E2E. Разделять фильтрами внутри одного счётчика значит помнить про фильтр в
каждом отчёте.
*Альтернатива:* второй счётчик для dev. Отвергнута: наблюдать за поведением
посетителей на dev некого, а второй счётчик — вторая конфигурация целей,
которая разойдётся с первой.
*Цена:* работоспособность счётчика нельзя проверить до выкатки на прод.

## Risks / Trade-offs

- **Риск: первый просмотр всё-таки задвоится.** → Тест на то, что при
  монтировании хит не отправляется, и отправляется ровно один раз на смену
  пути.
- **Риск: события прокрутки зашумят словарь.** → Четыре фиксированных порога,
  по одному разу за визит; значение проверяется сервером по объявленному
  набору.
- **Риск: выключив счётчик на dev, мы узнаем о сломанной аналитике только на
  проде.** → Проверка после выкатки состоит из одного запроса в сетевой панели.
- **Trade-off: уходит возможность посмотреть запись сессии при разборе
  жалобы.** Принимается: цена — медицинские данные на чужих серверах, и это
  решение уже было принято в `product-analytics-events`, просто не доведено до
  кода.
