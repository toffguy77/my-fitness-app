## ADDED Requirements

### Requirement: Однократное выполнение задачи при нескольких инстансах

Периодическая задача SHALL выполняться не более одного раза за свой интервал независимо от количества одновременно работающих инстансов API. Планировщик MUST захватывать межпроцессную блокировку по имени задачи перед выполнением и освобождать её после завершения.

#### Scenario: Два инстанса, один интервал

- **WHEN** два инстанса API одновременно достигают момента запуска одной и той же задачи
- **THEN** задача выполняется ровно один раз
- **AND** второй инстанс записывает результат запуска со статусом `skipped`

#### Scenario: Инстанс падает во время выполнения

- **WHEN** инстанс, удерживающий блокировку задачи, аварийно завершается
- **THEN** блокировка освобождается автоматически
- **AND** следующий запуск задачи на другом инстансе выполняется успешно

### Requirement: Объявление задачи в реестре

Периодическая задача SHALL объявляться записью в реестре с обязательными полями: имя, интервал или время суток запуска, таймаут выполнения и функция выполнения. Добавление новой задачи MUST NOT требовать изменения точки входа приложения.

#### Scenario: Задача с превышенным таймаутом

- **WHEN** выполнение задачи превышает объявленный таймаут
- **THEN** контекст выполнения отменяется
- **AND** запуск записывается со статусом `failed` и описанием причины
- **AND** блокировка задачи освобождается

#### Scenario: Задача с временем суток

- **WHEN** объявлена задача с временем запуска 03:00 по московскому времени
- **THEN** задача выполняется в первый тик планировщика после наступления 03:00
- **AND** повторно в течение тех же суток не выполняется

### Requirement: История запусков задач

Каждый запуск задачи SHALL записываться в хранилище с именем задачи, временем начала и окончания, статусом (`success`, `failed`, `skipped`), текстом ошибки при неуспехе и количеством обработанных элементов. История MUST храниться не менее 30 дней.

#### Scenario: Успешное выполнение

- **WHEN** задача завершается без ошибки
- **THEN** создаётся запись со статусом `success`, заполненными временами начала и окончания и количеством обработанных элементов

#### Scenario: Просмотр истории администратором

- **WHEN** пользователь с ролью `super_admin` вызывает `GET /api/v1/admin/jobs`
- **THEN** ответ содержит для каждой зарегистрированной задачи её имя, расписание и последний запуск с его статусом

#### Scenario: Просмотр истории неадминистратором

- **WHEN** пользователь без роли `super_admin` вызывает `GET /api/v1/admin/jobs`
- **THEN** API отвечает статусом `403`

### Requirement: Ручной запуск задачи

Пользователь с ролью `super_admin` SHALL иметь возможность запустить зарегистрированную задачу немедленно через `POST /api/v1/admin/jobs/:name/run`. Ручной запуск MUST использовать ту же блокировку, что и плановый, и MUST быть ограничен по частоте.

#### Scenario: Ручной запуск существующей задачи

- **WHEN** супер-администратор вызывает ручной запуск задачи, которая не выполняется в данный момент
- **THEN** задача выполняется
- **AND** создаётся запись о запуске

#### Scenario: Ручной запуск во время выполнения

- **WHEN** супер-администратор запускает задачу, которая уже выполняется
- **THEN** API отвечает статусом `409`
- **AND** повторного выполнения не происходит

#### Scenario: Запуск несуществующей задачи

- **WHEN** супер-администратор запускает задачу с неизвестным именем
- **THEN** API отвечает статусом `404`

### Requirement: Завершение задач при остановке сервиса

При получении сигнала остановки сервис SHALL прекратить планирование новых запусков и дождаться завершения выполняющейся задачи в пределах таймаута остановки.

#### Scenario: Остановка во время выполнения задачи

- **WHEN** сервис получает сигнал остановки во время выполнения задачи
- **THEN** новые запуски не планируются
- **AND** сервис ожидает завершения текущей задачи перед выходом

### Requirement: Регулярная уборка временных данных

Система SHALL периодически удалять устаревшие записи: попытки сброса пароля старше 24 часов, использованные и просроченные тикеты WebSocket, отозванные refresh-токены с истёкшим сроком действия, записи истории запусков старше 30 дней.

#### Scenario: Уборка попыток сброса пароля

- **WHEN** выполняется задача уборки
- **AND** в таблице попыток сброса пароля есть записи старше 24 часов
- **THEN** эти записи удаляются
- **AND** количество удалённых записей фиксируется в истории запуска
