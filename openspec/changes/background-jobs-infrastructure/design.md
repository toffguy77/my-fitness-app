## Context

Единственная фоновая задача сегодня — тикер в горутине, запущенный из `main`. Он корректен для одного инстанса и молчалив: если публикация упала, об этом узнаёт только лог. Рядом лежат две написанные, но не подключённые функции (`CollectDailySnapshot`, `CleanupOldAttempts`) — их не забыли реализовать, их забыли запустить. Это и есть аргумент за реестр: пока запуск задачи требует правки `main.go`, шаг «запустить» будет теряться.

Инфраструктурное ограничение: PostgreSQL уже есть, Redis нет и заводить его ради блокировки не хочется. Дополнительный контейнер под воркер тоже нежелателен — деплой идёт через Dokploy, каждый новый сервис это ещё одна единица эксплуатации.

## Goals / Non-Goals

**Goals:**
- Задача выполняется ровно один раз за интервал независимо от числа инстансов API.
- Добавление новой периодической задачи — одна запись в реестре, без правок `main.go`.
- Видно, когда задача выполнялась в последний раз, сколько длилась и чем закончилась.
- Кураторская аналитика начинает наполняться.

**Non-Goals:**
- Не делаем очередь задач с ретраями и приоритетами (нет сценариев, требующих её).
- Не выносим воркер в отдельный сервис.
- Не переносим отправку писем в фон — это отдельное решение.
- Не строим UI планировщика — достаточно двух админских эндпоинтов.

## Decisions

**Решение 1. Блокировка — `pg_try_advisory_lock` на время выполнения задачи.**
Перед запуском задача берёт advisory lock с ключом, вычисленным как хеш имени задачи. Не получила — пропускает тик и пишет в лог `debug`. Освобождает в `defer`.
*Почему так:* блокировка живёт в существующей БД, снимается автоматически при разрыве соединения (то есть при падении инстанса), не требует TTL и heartbeat.
*Альтернатива:* строка-семафор в таблице с `locked_until`. Отвергнута: нужен TTL и восстановление после падения — то, что advisory lock делает сам.
*Альтернатива:* Redis. Отвергнута: новая инфраструктурная зависимость ради одной функции.
*Альтернатива:* выбор лидера. Отвергнута: избыточно, задачи независимы и коротки.

**Решение 2. Реестр — декларативный список, планировщик один.**
```
jobs.Register(jobs.Job{
    Name:     "content.publish-scheduled",
    Interval: time.Minute,
    Timeout:  30 * time.Second,
    Run:      func(ctx context.Context) error { ... },
})
```
Планировщик — один тикер с минимальным шагом, который на каждом шаге отбирает задачи, чей интервал истёк по данным `job_runs`.
*Почему так:* добавление задачи не требует новой горутины и правки `main.go`; расписание становится данными.
*Альтернатива:* cron-выражения. Отвергнута: для «раз в минуту / раз в сутки / раз в неделю» интервала достаточно, а парсер cron — лишняя зависимость и лишний источник ошибок.

**Решение 3. Ежедневные и еженедельные задачи привязаны ко времени суток, а не к «прошло 24 часа».**
Снапшот за день должен собираться после того, как день закончился. Задача объявляет `RunAt` — время в таймзоне `Europe/Moscow`; планировщик запускает её в первый тик после наступления этого времени, если за текущий период запуска ещё не было.
*Почему так:* «раз в 24 часа от старта процесса» дало бы снапшоты в случайное время суток и сдвиг после каждого деплоя.

**Решение 4. Идемпотентность на стороне задачи, а не планировщика.**
Снапшоты пишутся через `INSERT ... ON CONFLICT (curator_id, date) DO UPDATE` — уникальные индексы уже есть в миграции 041. Публикация статей фильтрует по `status = 'scheduled' AND scheduled_at <= now()` и переводит статус в той же транзакции.
*Почему так:* блокировка защищает от параллельного запуска, идемпотентность — от повторного после сбоя. Нужны оба.

**Решение 5. `job_runs` — история, а не только последнее состояние.**
Колонки: `job_name`, `started_at`, `finished_at`, `status` (`success` / `failed` / `skipped`), `error`, `items_processed`. Хранение 30 дней, чистится собственной задачей уборки.
*Почему так:* «когда в последний раз собирались снапшоты и почему их нет» — первый вопрос при разборе; без истории на него не ответить.

**Решение 6. Ручной запуск доступен супер-администратору.**
`POST /admin/jobs/:name/run` выполняет задачу немедленно с той же блокировкой. Нужен для первичного наполнения снапшотов после включения и для проверки после починки.
*Ограничение:* ограничение частоты — не чаще одного запуска задачи в минуту.

**Решение 7. Бенчмарк платформы считается по завершённой неделе.**
`platform_weekly_benchmarks` — агрегат по всем кураторам за прошедшую неделю; пишется еженедельной задачей после `curator_weekly_snapshots`, в том же запуске, последовательно.
*Следствие:* сразу после выкатки разделы истории и бенчмарка пусты до первого запуска. Фронтенд обязан корректно показывать состояние «данных пока нет» — отдельная задача.

## Risks / Trade-offs

- **Риск: сбор снапшотов по всем кураторам — тяжёлая операция.** `GetAnalytics` уже распараллелен через `errgroup` (`curator/service.go:184`), но выполняется на каждого куратора. → Таймаут задачи 5 минут, последовательный обход кураторов, замер длительности в `job_runs`; при росте числа кураторов — пересмотр.
- **Риск: advisory lock удерживается «зависшей» задачей.** → У каждой задачи обязательный `Timeout`, контекст отменяется по нему, соединение возвращается в пул, блокировка снимается.
- **Риск: разделы аналитики у кураторов останутся пустыми несколько дней после выкатки** и это будет выглядеть как поломка. → Ручной запуск (Решение 6) для первичного наполнения плюс явное состояние «накапливаем данные» на фронтенде.
- **Риск: миграция публикации статей из старого планировщика меняет момент публикации.** → Интервал сохраняется минутным, логика `PublishScheduledArticles` не меняется.
- **Trade-off: планировщик внутри API-процесса,** значит фоновая нагрузка конкурирует с обслуживанием запросов. Принимаем: задачи редкие и короткие; при росте — вынос в отдельный процесс, реестр к этому уже готов.

## Migration Plan

1. Миграция `job_runs`.
2. Пакет `jobs`, перенос публикации статей, выкатка на dev — поведение статей не меняется.
3. Подключение задач уборки.
4. Реализация недельных снапшотов и бенчмарка, подключение всех трёх задач аналитики.
5. Ручной запуск на dev для первичного наполнения, проверка разделов куратора.
6. Прод: выкатка, ручной запуск, проверка.

**Откат:** возврат образа; таблица `job_runs` остаётся и не мешает предыдущей версии.
