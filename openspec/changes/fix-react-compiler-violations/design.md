## Context

Нарушения накапливались, пока ESLint не запускался вовсе. Причина падения — override `ajv: 8.18.0` в корневом `package.json`, добавленный когда-то ради устранения уязвимости: npm применяет верхнеуровневый override ко всем вхождениям, включая загрузчик конфигурации ESLint, который написан под API ajv 6. Пока `ajv-formats` не подтянул ajv 8 в корень, всё случайно работало.

Все девять случаев `set-state-in-effect` — один и тот же приём: при смене зависимости эффект синхронно сбрасывает состояние (`setItems([])`, `setLoading(true)`, `setError(null)`) и запускает загрузку. Приём даёт лишний ререндер и, при включённом компиляторе, плохо предсказуем.

## Goals / Non-Goals

**Goals:**
- Ни одного нарушения правил React Compiler.
- Правила снова блокируют слияние.
- Поведение затронутых экранов не меняется.

**Non-Goals:**
- Не переписываем слой загрузки данных на библиотеку.
- Не трогаем 587 предупреждений других правил.

## Decisions

**Решение 1. Сброс состояния при смене зависимости — через `key`, а не через `setState` в эффекте.**
Компонент со списком выносится в дочерний, которому родитель передаёт `key={category}`. React размонтирует и монтирует его заново, состояние сбрасывается само, эффект остаётся только загрузкой.
*Почему так:* это рекомендуемый способ выразить «при смене этого значения начинаем с чистого листа», и он убирает лишний ререндер.
*Альтернатива:* оставить как есть и отключить правило точечно. Отвергнута: правило указывает на настоящий лишний ререндер, а при включённом компиляторе — на непредсказуемость.

**Решение 2. Нарушения неизменяемости чинятся заменой мутации на создание нового значения.**
Компилятор исходит из того, что значения не мутируются; мутация может привести к тому, что мемоизированный результат не обновится.

**Решение 3. Ручная мемоизация, которую компилятор не может сохранить, удаляется.**
С включённым компилятором ручные `useMemo`/`useCallback` в этих местах избыточны — компилятор мемоизирует сам.

**Решение 4. Правила поднимаются до `error` одним шагом в конце.**
Промежуточное состояние «часть правил блокирует» непонятно и провоцирует отключение.

## Risks / Trade-offs

- **Риск: перенос состояния под `key` меняет момент размонтирования** и может сбросить то, что раньше сохранялось между переключениями категории. → Проверять каждый экран вручную и тестами до и после.
- **Риск: удаление ручной мемоизации ухудшит производительность,** если компилятор поведёт себя иначе, чем ожидается. → Замер до и после на списках с большим числом элементов.
- **Trade-off: пока изменение не сделано, новые нарушения этих правил не блокируются.** Принимаем осознанно и ограничиваем сроком.

## Migration Plan

1. Починить `set-state-in-effect` по одному компоненту, каждый со своей проверкой.
2. Починить нарушения неизменяемости и мемоизации.
3. Поднять правила до `error`, удалить временный блок из конфигурации.

**Откат:** изменения локальны по компонентам и откатываются по одному.
