## Context

В Next 16 `app/sitemap.ts` без динамических API считается статическим и
пререндерится при сборке. При сборке в Docker API нет.

## Goals / Non-Goals

**Goals:** карта всегда содержит опубликованные публичные статьи; сборка не
зависит от API.

**Non-Goals:** sitemap index и разбиение карты (лимит 50 000 адресов далеко);
отдельный эндпоинт API для карты.

## Decisions

1. **`export const dynamic = 'force-dynamic'`.** Карта строится на каждый
   запрос. Запрос к API кэшируется `fetch` на 5 минут (`next.revalidate: 300`):
   робот не обращается к API каждый раз, а новая статья попадает в карту
   быстро.
   *Отвергнуто:* `export const revalidate = 3600` (ISR). Первую версию всё равно
   собирает `next build` без API, и после каждой выкатки карта час остаётся
   пустой. Это та же ошибка с отсрочкой.
   *Отвергнуто:* передавать API в сборку. Сборка образа не должна ходить в
   базу прода, и dev-сборка дала бы dev-статьи в образе.

2. **Постраничный обход.** Публичная лента ограничит `limit` сотней (см.
   `seo-technical-hygiene`), поэтому карта идёт по `offset`, пока не наберёт
   `total`, и с предохранителем в 50 страниц.
   *Отвергнуто:* оставить `limit=1000`. Неограниченный `limit` у публичной ручки —
   отдельный дефект.

3. **Без `lastmod` у статических страниц.** `new Date()` на каждый запрос
   сообщает роботу, что всё меняется постоянно, и он перестаёт доверять полю.

4. **Ошибка API — карта без статей, но ответ 200.** Пустая карта статей лучше
   ошибки всей карты. Ошибка пишется в лог сервера, а не проглатывается молча.

## Risks / Trade-offs

- Каждый запрос карты рендерится заново → запрос к API кэширован, а сама сборка
  XML из десятков адресов дешёвая.
