## Context

API отвечает в обёртке `{status, data, message?, code?, params?}` (`internal/shared/response/response.go:11-24`); машинный `code` уже введён, чтобы клиенты не разбирали русский текст. Маршрутов на `dev` 201, публичных (`/api/v1/public/*`) — 15. Таблица маршрутов закреплена `routes.golden`, схема базы — `schema.golden`, защищённость маршрутов — `protectedRoutes`: в репозитории принят приём «эталон в файле плюс тест, который валит сборку». Схемы ответов нет ни в каком виде, OpenAPI-инструментов в `go.mod` нет.

Интеграционные тесты идут под тегом `integration` на настоящей базе через `testsupport.SchemaWithMigrations` (`internal/testsupport/schema.go:29`), который без `TEST_DATABASE_URL` пропускает тест. В CI их гоняет `Integration Tests` (`make test-integration-ci`, PostgreSQL 18 как в Yandex Cloud).

Обработчики и сервисы собираются в `main()` (`cmd/server/main.go:68-675`) и передаются в `router.New(Deps)`. Внешние зависимости — S3 (`storage.S3API`), SMTP, модели распознавания, Web Push — создаются там же; отсутствие учётных данных отключает способность (`config.Features`), и она отвечает `503`.

Решения, принятые до этого изменения: веб не замораживается и `/api/v2` целиком не заводится; клиенты — нативные Swift (сейчас) и Kotlin (следом); первая версия iOS — ядро клиента, кабинет куратора и удаление аккаунта (правило App Store 5.1.1(v)).

## Goals / Non-Goals

**Goals:**
- Контракт операций, которые вызывает iOS, записан в машиночитаемом виде и не может разойтись с тем, что API отвечает на самом деле.
- Правка, ломающая выпущенную сборку, останавливается в PR, а не обнаруживается на телефоне.
- Из контракта получается файл, по которому генерируются клиенты на Swift и Kotlin.

**Non-Goals:**
- Не описываем маршруты, которые вызывает только веб; веб меняется так же свободно, как сейчас.
- Не переводим веб на типы из схемы и не трогаем `check-api-contract.mjs`.
- Не меняем поведение ни одного обработчика — ни форму ответа, ни коды. Расхождение схемы и кода, найденное тестом, правится в схеме, если ответ корректен, или отдельной задачей, если это дефект.
- Мобильная авторизация, APNs, `app-config`, `X-Client`, universal links — подпроект 2. Xcode-проект и Swift-код — подпроект 3.
- Не генерируем серверный код из схемы.

## Decisions

**Решение 1. Схема пишется руками и сверяется с живыми ответами.**
OpenAPI 3.1 в `apps/api/openapi/`: `openapi.yaml` (версия, серверы, `bearerAuth`, общие компоненты), `paths/<модуль>.yaml` по модулям роутера, `components/<сущность>.yaml`.
*Почему так:* схема описывает ровно то, что обещано клиенту, а тест (решение 4) не даёт ей разойтись с кодом — тот же приём, что `routes.golden`.
*Альтернатива:* генерация из аннотаций (`swaggo/swag`). Отвергнута: комментарии расходятся с кодом так же молча, как отдельный файл, а гарантии соответствия ответа не дают — понадобилась бы та же сверка, плюс комментарии на сотне обработчиков.
*Альтернатива:* фреймворк со схемой из типов (Huma, ogen). Отвергнута: переписывание сотен обработчиков ради клиента, которого ещё нет.

**Решение 2. В схеме только операции мобильных клиентов, помеченные `x-clients`.**
Каждая операция несёт `x-clients: [ios]` (позже — `android`). Операции без пометки в схему не попадают вовсе.
*Почему так:* проверка совместимости касается только того, что может сломать выпущенную сборку. Если описать веб-маршруты, каждая правка веба начнёт проходить через правила, которые ему не нужны.
*Почему пометка, а не «всё в схеме — для iOS»:* Android может появиться с другим набором операций; сборка файла для клиента (решение 7) фильтрует по пометке.

**Решение 3. Обёртка и ошибки описаны один раз.**
`components/envelope.yaml`: успех — `{status: "success", data: <T>}`, ошибка — `Error {status: "error", code: ErrorCode, message?, params?}`. Каждая операция ссылается на них, а не повторяет форму. `ErrorCode` — открытое перечисление (решение 6), известные значения сверяются тестом с константами `apperrors/codes.go`.
*Почему так:* клиент различает ошибки по `code`, а это поле — самое вероятное место расхождения: обработчик, который ещё зовёт `response.Error` без кода, получает код по статусу (`response.go:65`).

**Решение 4. Сверка — на настоящем роутере, настоящей базе и с закрытыми объектами.**
Тест `internal/contract/` (тег `integration`) собирает роутер через `internal/app` (решение 5) на тестовой базе, засевает минимальный мир (клиент, куратор, связь между ними, записи дневника, переписка, уведомление) и прогоняет сценарии через `httptest`. Запрос и ответ проверяются `kin-openapi` (`openapi3filter.ValidateRequest`/`ValidateResponse`).
Сценарии — Go-таблицы по модулям: `cases_<модуль>_test.go`, запись `{операция, от чьего имени, параметры, тело, ожидаемый статус}`.
- **Покрытие:** для каждой операции с `x-clients` и каждого объявленного в ней статуса должен быть сценарий. Нет — тест падает и называет операцию и статус.
- **Закрытые объекты:** перед проверкой тест обходит загруженную схему и ставит `additionalProperties: false` всем объектам ответа, где оно не задано явно. Поле в ответе, которого нет в схеме, — ошибка; так схема не отстаёт от кода. Опубликованная схема остаётся открытой.
- **`null`:** nullable только то, что объявлено `type: [..., "null"]`. Пустой срез Go, сериализованный как `null`, при объявленном массиве — ошибка. Это самая частая поломка Go ↔ Swift.
- **Не пропускается молча:** при `CI=true` и пустом `TEST_DATABASE_URL` тест падает (`t.Fatal`), а не пропускается. Для этого в `testsupport` появляется `RequireSchemaWithMigrations`.
- **Внешние сервисы:** база настоящая, а S3, SMTP, модель распознавания и Web Push подменяются на границе сети заглушками в памяти, реализующими те же интерфейсы. Иначе операции загрузки фото и распознавания имели бы только сценарий `503`.
*Альтернатива:* sqlmock и подменённые сервисы. Отвергнута: подмена описывает мир так, как мы его себе представляем, и в схему уехало бы это представление — так уже пропускались живые дефекты.
*Альтернатива:* снимки ответов (golden JSON) вместо схемы. Отвергнута: снимок ловит любое изменение, включая совместимое добавление поля, и не даёт клиенту типов.

**Решение 5. Сборка зависимостей выносится из `main()` в `internal/app`.**
`app.Build(cfg, db, log, ext) (router.Deps, *app.Background, error)`, где `ext` — внешние клиенты (S3, почта, модели, push), созданные в `main()` по конфигурации. `main()` оставляет за собой загрузку конфигурации, подключение к базе, миграции, создание внешних клиентов, запуск HTTP-сервера и фоновых заданий из `Background`.
*Почему так:* тест должен проверять тот роутер, что работает на проде. Собранная в тесте копия зависимостей разошлась бы с `main()` при первой же правке, и тест проверял бы её.
*Стоимость:* правка 600 строк `main()` без изменения поведения. Сторож — `TestRoutesMatchGolden` и существующие тесты `cmd/server`; переезд отдельной задачей до появления схемы.
*Альтернатива:* собирать зависимости в тесте вручную. Отвергнута по причине выше.

**Решение 6. Перечисления в ответах: открытые и закрытые.**
Перечисление, которое будет расти (`ErrorCode`, тип уведомления, тип сообщения, тип задачи), описывается как `type: string` со списком `x-known-values`; генерированный клиент получает строку и обязан обрабатывать неизвестное значение. Закрытое `enum` — только то, что не растёт (роль, `status` обёртки).
*Почему так:* `swift-openapi-generator` строит из `enum` закрытый Swift-`enum` и падает при декодировании незнакомого значения. Новый тип уведомления на сервере уронил бы весь список уведомлений в выпущенной сборке.
*Альтернатива:* закрытые `enum` и запрет их расширять. Отвергнута: тогда каждый новый тип уведомления — поломка контракта и новая версия эндпоинта.

**Решение 7. Один собранный файл на клиента, коммитится.**
`make openapi` (`apps/api/Makefile`) вызывает `redocly bundle` и фильтр по `x-clients`, результат — `apps/api/openapi/dist/ios.yaml`. `scripts/check-mobile-contract.mjs` в `Static Checks` пересобирает файл и падает, если закоммиченный отличается, — так же, как `TestKnowledgeMatchesUserGuide` сверяет базу знаний бота. Проверка в Node, а не в Go: сборка идёт через `redocly`.
*Почему так:* генераторы плохо понимают многофайловую схему; закоммиченный файл даёт iOS-проекту (подпроект 3) вход без Node и показывает в диффе PR, что именно поменялось для клиента.
*Альтернатива:* один большой файл без сборки. Отвергнута: 90–100 операций в одном YAML — несколько тысяч строк, которые неудобно ревьюить.

**Решение 8. Совместимость проверяет `oasdiff` против схемы целевой ветки.**
Скрипт `scripts/check-mobile-contract.mjs` (по образцу остальных `check-*.mjs`, тесты в `scripts/__tests__/`) берёт `dist/ios.yaml` из merge-base с целевой веткой (на push — из предыдущего коммита), запускает `oasdiff breaking --format json` и вычитает разрешённые поломки из `apps/api/openapi/accepted-breaks.yaml`. Шаг «Check mobile API contract compatibility» — в джобе `Static Checks`; имена джоб не меняются.
Поломкой считается всё, что `oasdiff` относит к уровню `ERR`, плюс добавление значения в закрытое перечисление ответа. Типичные случаи: удалена операция, поле ответа или значение перечисления; поле ответа стало необязательным или nullable; поменялся тип или формат; в запросе появился обязательный параметр или поле или сузились допустимые значения; поменялся путь, метод или авторизация.
*Почему скрипт, а не голый `oasdiff` с `--err-ignore`:* разрешённой поломке нужны причина и номер сборки, после которой операция не используется; формат игнор-файла `oasdiff` их не хранит, а режим до первого релиза (решение 9) ему неизвестен.

**Решение 9. До первого релиза проверка только сообщает.**
Строгость определяется схемой **целевой** ветки: если в её `openapi.yaml` нет `info.x-first-release`, скрипт печатает отчёт и завершается успешно; если есть — поломка валит сборку. Отметку ставит PR релиза первой сборки в App Store.
*Почему по целевой ветке:* PR не может выключить проверку, удалив отметку у себя.
*Почему так:* пока выпущенных сборок нет, защищать нечего, а схема в первые недели будет меняться постоянно.

**Решение 10. Несовместимая правка — новая версия отдельной операции.**
Если операции, которую вызывает выпущенная сборка, нужна поломка, рядом появляется та же операция под `/api/v2/<тот же путь>` с новым контрактом; старая получает `deprecated: true` и живёт, пока её вызывают поддерживаемые сборки. Префикс `/api/v2` содержит только переведённые операции, остальное остаётся в `/api/v1`.
Удаление устаревшей операции разрешается записью в `accepted-breaks.yaml` (операция, причина, последняя сборка, которая её вызывает) после того, как `min_supported_version` поднята выше этой сборки и трафика с поддерживаемых сборок нет (`X-Client`, подпроект 2).
*Альтернатива:* версия в заголовке (`Accept: …;v=2`). Отвергнута: невидима в `routes.golden`, в логах доступа и в `protectedRoutes`, а генераторы описывают её неудобно.
*Альтернатива:* суффикс в пути (`/entries-v2`). Отвергнута: версия смешивается с именем ресурса, и правила вроде «всё под `/api/v2` — переведённые операции» становится не на что опереть.

**Решение 11. Каждая операция схемы существует в таблице маршрутов.**
Тест в `internal/router/` переводит пути схемы в форму Gin (`{id}` → `:id`) и проверяет каждую операцию по `routes.golden`. Обратное не требуется: маршрут без схемы — нормальное состояние для веба.

## Risks / Trade-offs

- **Ручное описание ~100 операций — объём.** → Пишется по модулям вместе со сценариями; тест покрытия не даёт пропустить статус. Расхождения, найденные при описании, — это дефекты, которые сейчас незаметны вебу; дефектами занимаемся отдельными задачами, не меняя поведение в этом изменении.
- **Заглушки внешних сервисов могут отличаться от настоящих.** → Подменяется только сетевая граница, форма ответа API определяется нашим кодом; поведение самих S3 и моделей тест контракта не проверяет и не обязан.
- **Закрытые объекты в тесте раздражают при добавлении поля.** → Это и есть цель: поле, добавленное в код без схемы, клиент не увидит. Цена — одна строка в YAML.
- **`oasdiff` может не распознать поломку, которой нет в его каталоге.** → Тест контракта ловит расхождение схемы и кода, `oasdiff` — расхождение двух схем; смысловые поломки (единицы измерения) не ловит никто, они остаются на ревью.
- **Вынос `main()` может незаметно поменять порядок инициализации.** → Отдельная задача, отдельный PR, проверка на dev-стенде (`/health` перечисляет включённые способности) до начала работы над схемой.
- **Схема станет устаревшей, если поломку «разрешать» слишком легко.** → Каждая запись `accepted-breaks.yaml` проходит ревью в PR и требует номер сборки.

## Migration Plan

1. Вынос сборки зависимостей в `internal/app`; выкатка на dev, сверка `/health` и smoke-проверка входа.
2. Каркас схемы: корень, обёртка, ошибки, тесты сверки с `routes.golden` и `apperrors`, `make openapi`, шаг CI в режиме отчёта.
3. Тест контракта с одним модулем (`auth`) — проверка механизма.
4. Остальные модули по одному PR: `users` (включая удаление аккаунта), `dashboard`, `food-tracker`, `nutrition-calc`, `chat`, `notifications`, `curator`.
5. `x-first-release` ставится PR релиза первой сборки (подпроект 3) — не в этом изменении.

Откат любого шага — revert PR: схема и тесты не влияют на поведение API.
