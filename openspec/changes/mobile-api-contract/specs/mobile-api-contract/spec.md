## ADDED Requirements

### Requirement: Схема описывает операции мобильных клиентов

Репозиторий SHALL содержать OpenAPI 3.1-схему в `apps/api/openapi/`. Каждая операция схемы MUST нести пометку `x-clients` с непустым списком клиентов. Операция, которую не вызывает ни один мобильный клиент, MUST NOT присутствовать в схеме.

#### Scenario: Операция без пометки клиента

- **WHEN** в схему добавлена операция без `x-clients`
- **THEN** тест схемы падает и называет метод и путь операции

#### Scenario: Схема загружается и проходит валидацию

- **WHEN** запускаются тесты бэкенда
- **THEN** схема загружается `kin-openapi` и проходит валидацию документа без ошибок

### Requirement: Каждая операция схемы существует в таблице маршрутов

Каждая операция схемы MUST соответствовать маршруту из `internal/router/testdata/routes.golden` с тем же методом и путём (параметры `{id}` схемы соответствуют `:id` Gin). Маршрут, отсутствующий в схеме, MUST NOT считаться ошибкой.

#### Scenario: Схема описывает несуществующий маршрут

- **WHEN** схема содержит операцию `GET /api/v1/dashboard/nonexistent`
- **THEN** тест сверки с таблицей маршрутов падает и называет эту операцию

#### Scenario: Маршрут только для веба

- **WHEN** маршрут есть в `routes.golden`, но отсутствует в схеме
- **THEN** тест сверки проходит

### Requirement: Обёртка ответа и ошибка описаны один раз

Схема SHALL описывать успешный ответ как `{status: "success", data}` и ошибку как `Error` с полями `status`, `code`, необязательными `message` и `params`. Каждый ответ каждой операции MUST ссылаться на эти компоненты. Известные значения `ErrorCode` MUST совпадать с множеством констант кодов в `internal/shared/apperrors/codes.go`.

#### Scenario: Новый код ошибки в бэкенде

- **WHEN** в `apperrors/codes.go` добавлена константа кода, а в `ErrorCode` схемы её нет
- **THEN** тест сверки кодов падает и называет недостающий код

#### Scenario: Ответ операции не использует обёртку

- **WHEN** ответ операции в схеме описан без ссылки на компонент обёртки или `Error`
- **THEN** тест схемы падает и называет операцию и статус

### Requirement: Живые ответы соответствуют схеме

Тест контракта SHALL выполнять каждую операцию схемы через настоящий роутер, собранный тем же кодом, что и в `main()`, на настоящей базе с применёнными миграциями. Запрос и ответ MUST проверяться по схеме. При проверке объекты ответа MUST считаться закрытыми: поле, не объявленное в схеме, — ошибка. Значение `null` MUST допускаться только там, где схема объявляет `null` среди типов.

#### Scenario: Поле в ответе, которого нет в схеме

- **WHEN** обработчик возвращает поле, не объявленное в схеме операции
- **THEN** тест контракта падает и называет операцию и путь к полю

#### Scenario: Пустой список сериализован как null

- **WHEN** схема объявляет поле ответа массивом без `null`, а обработчик возвращает `null`
- **THEN** тест контракта падает и называет операцию и поле

#### Scenario: Обязательное поле отсутствует

- **WHEN** обработчик не возвращает поле, объявленное в схеме обязательным
- **THEN** тест контракта падает и называет операцию и поле

#### Scenario: Роутер теста совпадает с продовым

- **WHEN** тест контракта собирает роутер через `app.Build`
- **THEN** таблица маршрутов этого роутера совпадает с `routes.golden`

### Requirement: Каждый объявленный ответ проверен сценарием

Для каждой операции схемы и каждого объявленного в ней кода статуса MUST существовать хотя бы один сценарий теста контракта, который этот статус получает.

#### Scenario: Объявленный статус без сценария

- **WHEN** операция объявляет ответ `404`, а ни один сценарий его не получает
- **THEN** тест покрытия падает и называет операцию и статус

#### Scenario: Сценарий получает необъявленный статус

- **WHEN** сценарий получает код статуса, которого операция не объявляет
- **THEN** тест контракта падает и называет операцию и полученный статус

### Requirement: Тест контракта не пропускается в CI

При `CI=true` и отсутствии `TEST_DATABASE_URL` тест контракта MUST завершаться ошибкой, а не пропуском. Вне CI отсутствие базы MAY приводить к пропуску.

#### Scenario: База не настроена в CI

- **WHEN** тест контракта запускается с `CI=true` и пустым `TEST_DATABASE_URL`
- **THEN** тест завершается ошибкой с сообщением о незаданной базе

#### Scenario: База не настроена локально

- **WHEN** тест контракта запускается без `CI` и без `TEST_DATABASE_URL`
- **THEN** тест пропускается с сообщением о незаданной базе

### Requirement: Растущие перечисления в ответах открыты

Перечисление в ответе, набор значений которого может расти, SHALL описываться как строка со списком известных значений в `x-known-values`, без `enum`. Закрытое `enum` в ответе допускается только для наборов, которые не растут; перечень таких наборов MUST храниться в тесте схемы.

#### Scenario: Закрытое перечисление вне перечня

- **WHEN** в схеме ответа появляется `enum`, не входящий в перечень закрытых наборов
- **THEN** тест схемы падает и называет компонент и поле

### Requirement: Собранный файл для клиента совпадает с исходниками

`make openapi` SHALL собирать для каждого клиента из `x-clients` один файл `apps/api/openapi/dist/<клиент>.yaml`, содержащий только операции с этим клиентом. Закоммиченный файл MUST совпадать с результатом сборки из текущих исходников.

#### Scenario: Исходник изменён, файл не пересобран

- **WHEN** в `apps/api/openapi/paths/` изменено описание операции, а `dist/ios.yaml` не пересобран
- **THEN** проверка в CI падает и предлагает выполнить `make openapi`

#### Scenario: Фильтр по клиенту

- **WHEN** операция помечена `x-clients: [android]`
- **THEN** она присутствует в `dist/android.yaml` и отсутствует в `dist/ios.yaml`

### Requirement: Несовместимая правка контракта останавливается в CI

Проверка совместимости SHALL сравнивать `dist/ios.yaml` из PR с тем же файлом в merge-base целевой ветки (на push — в предыдущем коммите). Поломкой MUST считаться изменение уровня `ERR` по классификации `oasdiff` и добавление значения в закрытое перечисление ответа. Если `openapi.yaml` целевой ветки содержит `info.x-first-release`, поломка, не перечисленная в `accepted-breaks.yaml`, MUST валить сборку; иначе проверка MUST выводить отчёт и завершаться успешно.

#### Scenario: Удалено поле ответа после первого релиза

- **WHEN** целевая ветка содержит `x-first-release`, а PR удаляет поле ответа операции с `x-clients: [ios]`
- **THEN** шаг «Check mobile API contract compatibility» падает и называет операцию и поле

#### Scenario: Удалено поле ответа до первого релиза

- **WHEN** целевая ветка не содержит `x-first-release`, а PR удаляет поле ответа
- **THEN** шаг выводит отчёт о поломке и завершается успешно

#### Scenario: Добавлено необязательное поле ответа

- **WHEN** PR добавляет в ответ операции необязательное поле
- **THEN** шаг завершается успешно без сообщений о поломке

#### Scenario: Добавлен обязательный параметр запроса

- **WHEN** целевая ветка содержит `x-first-release`, а PR делает обязательным новое поле тела запроса
- **THEN** шаг падает и называет операцию и поле

#### Scenario: PR удаляет отметку первого релиза

- **WHEN** целевая ветка содержит `x-first-release`, а PR удаляет её и одновременно удаляет поле ответа
- **THEN** шаг падает: строгость определяется схемой целевой ветки

#### Scenario: Добавлено значение в открытое перечисление

- **WHEN** PR добавляет значение в `x-known-values` открытого перечисления ответа
- **THEN** шаг завершается успешно

### Requirement: Разрешённая поломка записывается с обоснованием

Запись в `apps/api/openapi/accepted-breaks.yaml` SHALL содержать операцию, идентификатор поломки `oasdiff`, причину и номер последней сборки iOS, которая вызывает операцию. Запись без любого из полей MUST отвергаться проверкой. Запись MUST пропускать только совпадающую поломку.

#### Scenario: Запись без номера сборки

- **WHEN** в `accepted-breaks.yaml` есть запись без номера сборки
- **THEN** шаг проверки совместимости падает и называет запись

#### Scenario: Запись разрешает одну поломку

- **WHEN** запись разрешает удаление операции A, а PR удаляет операции A и B
- **THEN** шаг падает и называет только операцию B

### Requirement: Несовместимая версия операции живёт под /api/v2

Новая несовместимая версия операции SHALL регистрироваться под `/api/v2` с тем же остатком пути, а прежняя версия MUST оставаться под `/api/v1` с `deprecated: true` в схеме. Под `/api/v2` MUST NOT регистрироваться маршруты, у которых нет предшественника под `/api/v1`.

#### Scenario: Маршрут под /api/v2 без предшественника

- **WHEN** в роутере зарегистрирован маршрут `/api/v2/<путь>`, а `/api/v1/<путь>` с тем же методом отсутствует
- **THEN** тест роутера падает и называет маршрут
