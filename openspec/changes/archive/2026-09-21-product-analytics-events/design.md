## Context

Продукт готовится к трём изменениям, которые перестраивают вход: новый онбординг с ранним сбором контактов, вход через внешних провайдеров и Telegram-бот поддержки до регистрации. Каждое из них имеет смысл ровно настолько, насколько его эффект измерим. Сейчас измерить нечем.

Ограничение: данные приложения — о здоровье. Отправлять их во внешний аналитический сервис нельзя без отдельных юридических оснований. Значит хранилище событий должно быть своим, а состав событий — сознательно ограниченным.

## Goals / Non-Goals

**Goals:**
- Видна воронка от первого визита до активированного пользователя.
- Видно удержание по когортам регистрации.
- Эффект изменений входа в продукт измеряется до и после.
- Ни одно событие не содержит данных о здоровье и содержимого переписки.

**Non-Goals:**
- Не строим систему A/B-экспериментов (может появиться позже поверх этих событий).
- Не заменяем Яндекс.Метрику — она остаётся для веб-трафика.
- Не строим интерфейс исследования данных: на первом этапе достаточно набора готовых запросов.
- Не отслеживаем поведение внутри экрана (тепловые карты, записи сессий).

## Decisions

**Решение 1. Собственное хранилище событий в PostgreSQL, а не внешний сервис.**
Таблица событий с полями: имя, время, идентификатор посетителя, идентификатор пользователя, платформа, версия приложения, свойства в JSON.
*Почему так:* данные о здоровье и продуктовые события живут рядом; отправка последних наружу потребовала бы отдельного анализа рисков и согласия пользователя. Своя таблица снимает вопрос.
*Стоимость:* нет готовых отчётов, их надо писать запросами.
*Альтернатива:* внешний продуктовый аналитический сервис. Отвергнута по причине выше.
*Альтернатива:* выводить события в логи и агрегировать оттуда. Отвергнута: логи не предназначены для запросов по когортам.

**Решение 2. Фиксированный словарь событий, валидация на приёме.**
Имя события и набор обязательных свойств объявляются в общем месте; сервер отклоняет событие, которого нет в словаре.
*Почему так:* свободные имена превращаются в свалку из опечаток и синонимов через месяц. Отклонение неизвестного события заставляет расширять словарь осознанно.

**Решение 3. Идентификатор посетителя генерируется на клиенте и связывается с пользователем при входе.**
До регистрации события несут только идентификатор посетителя; после успешного входа отправляется событие связывания, добавляющее идентификатор пользователя.
*Почему это ключевое решение:* без него воронка обрывается ровно там, где интереснее всего — на переходе «аноним → зарегистрирован».
*Хранение:* идентификатор посетителя — не персональные данные и живёт в браузере; в терминах изменения `secure-token-lifecycle` это допустимое использование локального хранилища, поскольку он не является секретом.

**Решение 4. Разделение источников: клиент отправляет намерения, сервер — факты.**
Клиент: просмотры экранов, нажатия, шаги форм. Сервер: успешная регистрация, подтверждение почты, назначение куратора, отправка отчёта.
*Почему так:* клиентское событие «зарегистрировался» врёт при обрыве соединения после успешного запроса и теряется при блокировщиках. Факты должны приходить оттуда, где они произошли.

**Решение 5. Пакетная отправка с клиента.**
События копятся и уходят пачкой по таймеру, при уходе со страницы и при достижении размера пачки.
*Почему так:* один запрос на десяток событий вместо десяти запросов; при уходе со страницы используется механизм фоновой отправки, чтобы события не терялись.

**Решение 6. Ограниченный состав свойств, проверяемый автоматически.**
Свойства события — только категориальные и числовые значения из объявленного набора. Запрещены: адрес почты, имя, содержимое сообщений, вес, замеры, калории, названия блюд.
*Почему явный запрет:* «отправим на всякий случай, потом разберёмся» — типичный способ, которым медицинские данные оказываются в аналитике. Проверка автоматическая, а не на ревью.

**Решение 7. Набор отчётов — четыре запроса, а не интерфейс.**
Воронка регистрации, воронка онбординга, активация за 24 часа, удержание по когортам. Хранятся в репозитории как SQL с описанием.
*Почему так:* четыре ответа на настоящие вопросы полезнее интерфейса, в котором никто не строит запросы.

## Risks / Trade-offs

- **Риск: таблица событий быстро вырастет.** → Индексы по времени и имени; политика хранения сырых событий (предварительно 12 месяцев) с задачей чистки; при росте — агрегация в суточные срезы.
- **Риск: блокировщики рекламы отрежут отправку событий.** → Приёмка на собственном домене под общим путём API, а не на стороннем; серверные события не зависят от клиента вовсе.
- **Риск: события всё-таки утекут персональными данными.** → Автоматическая проверка состава свойств по словарю на приёме плюс тест, отклоняющий свойства из запрещённого списка.
- **Риск: приёмка станет вектором нагрузки.** → Ограничение частоты по идентификатору посетителя и по IP, предел размера пачки.
- **Trade-off: отсутствие готового интерфейса аналитики** замедляет исследование данных. Принимаем на первом этапе.

## Migration Plan

1. Словарь событий и схема таблицы.
2. Приёмка с валидацией и ограничением частоты.
3. Клиентский модуль и инструментирование ключевых мест.
4. Серверные события.
5. Отчёты и фиксация базовых значений до изменений входа в продукт.

**Откат:** отправка отключается переменной окружения; таблица остаётся.
