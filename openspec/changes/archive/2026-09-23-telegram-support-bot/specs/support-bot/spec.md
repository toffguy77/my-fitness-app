## ADDED Requirements

### Requirement: Приём сообщений через webhook

Бот SHALL принимать обновления Telegram через HTTP-обработчик с проверкой секретного заголовка. Обновление без корректного секрета MUST отклоняться без обработки.

#### Scenario: Обновление с корректным секретом

- **WHEN** приходит обновление с корректным секретным заголовком
- **THEN** сообщение сохраняется и обрабатывается
- **AND** возвращается успешный ответ

#### Scenario: Обновление без секрета

- **WHEN** приходит обновление без секретного заголовка или с неверным значением
- **THEN** обновление отклоняется
- **AND** сообщение не сохраняется и не обрабатывается

#### Scenario: Бот не настроен

- **WHEN** токен бота не задан в конфигурации
- **THEN** сервис стартует с предупреждением о выключенной возможности
- **AND** обработчик webhook возвращает статус `503`

### Requirement: Ответы формируются только по базе знаний

Ответы бота SHALL основываться исключительно на встроенном корпусе документации. Бот MUST NOT отвечать на вопросы, ответа на которые в корпусе нет, используя общие знания модели.

#### Scenario: Вопрос, покрытый документацией

- **WHEN** пользователь спрашивает о том, что описано в базе знаний
- **THEN** бот отвечает по содержанию базы знаний
- **AND** ответ содержит указание на раздел документации

#### Scenario: Вопрос вне базы знаний

- **WHEN** пользователь задаёт вопрос, ответа на который в базе знаний нет
- **THEN** бот сообщает, что не может ответить
- **AND** предлагает передать вопрос человеку

#### Scenario: Контрольный набор вопросов

- **WHEN** выполняется проверка на контрольном наборе вопросов, часть которых заведомо не покрыта базой знаний
- **THEN** на покрытые вопросы даны ответы с указанием разделов
- **AND** на непокрытые вопросы дан отказ с предложением эскалации

### Requirement: Стабильный кэшируемый префикс запроса

Запрос к модели SHALL формироваться так, что база знаний и системная инструкция составляют неизменяемый префикс, помеченный для кэширования, а переменная часть запроса следует после него. Префикс MUST NOT содержать меток времени, идентификаторов запроса и иных изменяющихся значений.

#### Scenario: Побайтовая стабильность префикса

- **WHEN** префикс запроса формируется дважды подряд для разных пользователей
- **THEN** оба префикса побайтово совпадают

#### Scenario: Повторные обращения читают кэш

- **WHEN** выполняется серия обращений к модели в пределах срока жизни кэша
- **THEN** доля токенов, прочитанных из кэша, превышает установленный порог

### Requirement: Границы компетенции бота

Бот MUST NOT запрашивать и обсуждать конкретные показатели здоровья пользователя, включая вес, замеры тела и состояние здоровья. Бот MUST NOT давать индивидуальных рекомендаций по питанию и тренировкам.

#### Scenario: Запрос индивидуальной рекомендации

- **WHEN** пользователь просит рассчитать ему рацион или оценить его показатели
- **THEN** бот не даёт индивидуальной рекомендации
- **AND** направляет в приложение, где эту работу выполняет куратор

#### Scenario: Пользователь сообщает данные о здоровье

- **WHEN** пользователь по своей инициативе сообщает боту показатели здоровья
- **THEN** бот не запрашивает уточнений по ним и не строит на них ответ

### Requirement: Связывание чата с заявкой

Переход к боту по ссылке с подписанным токеном заявки SHALL связывать чат Telegram с этой заявкой. Доступ к заявке по её идентификатору без действительной подписи MUST быть невозможен.

#### Scenario: Переход по действительной ссылке

- **WHEN** посетитель открывает бота по ссылке с действительным подписанным токеном заявки
- **THEN** чат связывается с этой заявкой
- **AND** оператор видит шаг онбординга и введённые параметры при эскалации

#### Scenario: Переход по недействительной ссылке

- **WHEN** переход выполняется с некорректной или просроченной подписью
- **THEN** связывание не выполняется
- **AND** бот продолжает работать в общем режиме

### Requirement: Направление зарегистрированного пользователя к куратору

Если чат связан с существующим аккаунтом, бот SHALL отвечать на общие вопросы о продукте и MUST направлять в чат с куратором вопросы, касающиеся индивидуального плана, питания и прогресса.

#### Scenario: Зарегистрированный пользователь спрашивает про свой план

- **WHEN** пользователь со связанным аккаунтом спрашивает о своём плане питания
- **THEN** бот не отвечает по существу
- **AND** направляет в чат с куратором в приложении

### Requirement: Ограничение частоты и предел обращений к модели

Бот SHALL ограничивать частоту сообщений от одного чата и соблюдать общий дневной предел обращений к модели. При исчерпании предела бот MUST отвечать понятным сообщением и предлагать эскалацию.

#### Scenario: Превышение частоты одним чатом

- **WHEN** из одного чата поступает больше сообщений, чем разрешено за интервал
- **THEN** бот отвечает сообщением об ограничении
- **AND** обращение к модели не выполняется

#### Scenario: Исчерпан дневной предел

- **WHEN** общий дневной предел обращений к модели исчерпан
- **THEN** бот сообщает о временной недоступности автоматических ответов
- **AND** предлагает передать вопрос человеку

### Requirement: Хранение переписки с ботом

Переписка с ботом SHALL храниться ограниченный срок и удаляться по его истечении. Переписка чата, связанного с аккаунтом, MUST входить в состав выгрузки и удаления персональных данных пользователя.

#### Scenario: Истечение срока хранения

- **WHEN** срок хранения диалога истёк
- **THEN** сообщения диалога удаляются задачей уборки

#### Scenario: Удаление аккаунта

- **WHEN** пользователь, чей аккаунт связан с чатом бота, удаляет аккаунт
- **THEN** переписка этого чата обрабатывается согласно объявленной стратегии удаления данных
