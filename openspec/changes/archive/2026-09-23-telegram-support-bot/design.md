## Context

Бот нужен для узкой задачи: снять вопросы, мешающие человеку дойти до регистрации. Это не замена куратору — внутри приложения общение с куратором уже есть и остаётся основным каналом. Значит бот должен быть намеренно ограниченным: отвечать по документации, а во всём остальном звать человека.

Инфраструктурное ограничение: развёртывание через Dokploy, каждый новый сервис — ещё одна единица эксплуатации. В `apps/api` уже есть HTTP-сервер, конфигурация, логирование, база и реестр фоновых задач.

Ограничение по данным: бот работает с людьми **до** регистрации. Он не должен ни спрашивать, ни обсуждать вес, замеры и состояние здоровья — на такие вопросы он отвечает общей информацией из документации и предлагает продолжить в приложении, где для медицинских данных есть законное основание и защищённый канал.

По модели: проект уже обращается к LLM через OpenRouter (`internal/shared/openrouter/`) для распознавания еды, с дневным лимитом на пользователя. Модель по умолчанию `anthropic/claude-sonnet-4` устарела — актуальные варианты Claude Opus 5 (`claude-opus-5`, $5 за 1M входных и $25 за 1M выходных токенов), Claude Sonnet 5 (`claude-sonnet-5`, $2 и $10) и Claude Haiku 4.5 (`claude-haiku-4-5`, $1 и $5).

## Goals / Non-Goals

**Goals:**
- Человек получает ответ на вопрос о продукте за секунды, круглосуточно, не покидая привычный мессенджер.
- Ответы соответствуют документации и не выдумываются.
- Вопрос, на который бот не может ответить, доходит до человека, а не теряется.
- Оператор видит контекст: шаг онбординга, параметры, историю диалога.
- Не появляется нового сервиса в эксплуатации.

**Non-Goals:**
- Бот не консультирует по питанию, тренировкам и здоровью — это работа куратора.
- Бот не является каналом уведомлений (это изменение `notifications-delivery-channels`).
- Не делаем ботов в других мессенджерах.
- Не строим полноценную систему обращений с очередями, приоритетами и соглашениями об уровне сервиса.
- Не переносим чат с куратором в Telegram.

## Decisions

**Решение 1. Бот — модуль внутри `apps/api`, обновления через webhook.**
Telegram шлёт обновления на публичный путь с секретом в заголовке; обработчик кладёт сообщение в базу и отвечает.
*Почему не отдельный сервис:* переиспользуются конфигурация, логирование, база, реестр задач и наблюдаемость; не появляется второй контейнер, второй деплой и второй набор секретов.
*Почему webhook, а не опрос:* опрос требует постоянно работающего цикла и ломается при нескольких инстансах; webhook — обычный HTTP-обработчик.
*Риск связанности:* при росте бота его можно вынести — модуль изолирован за интерфейсом.

**Решение 2. База знаний — существующая документация, встроенная в бинарь.**
`docs/user-guide/*.md` встраивается через механизм встраивания файлов, как это уже сделано для миграций (`apps/api/migrations/embed.go`).
*Почему это лучшее из доступного:* документация уже написана, уже на русском, уже поддерживается и покрывает ровно те вопросы, которые задают. Ответы бота начинают зависеть от неё, что даёт правильный стимул её обновлять.
*Почему встраивание:* корпус версионируется вместе с кодом, откат образа откатывает и знания; нет расхождения между тем, что задеплоено, и тем, что читает бот.

**Решение 3. Никакого векторного поиска — весь корпус в закэшированном префиксе.**
1327 строк русской документации — порядка 20–30 тысяч токенов, что помещается в контекст любой текущей модели целиком. Корпус идёт первым, неизменным блоком с пометкой кэширования; вопрос пользователя — после последней точки кэширования.
*Почему так:* кэшированное чтение стоит примерно десятую часть обычного ввода, а запись в кэш — около 1,25 обычной стоимости. При потоке вопросов подавляющее большинство запросов читает префикс из кэша. Векторная база дала бы худшие ответы (фрагменты вместо целостной картины) и добавила бы инфраструктуру.
*Условие пересмотра:* если корпус вырастет в разы, вернуться к вопросу отбора фрагментов.
*Обязательное следствие для реализации:* префикс должен быть побайтово стабильным — никаких меток времени, идентификаторов запроса и переменных приветствий до точки кэширования. Проверяется наблюдением за долей чтений из кэша.

**Решение 4. Строгая привязка к источнику: не нашёл в корпусе — не отвечает.**
Системная инструкция запрещает отвечать по общим знаниям модели; при отсутствии ответа в корпусе бот говорит, что не знает, и предлагает передать вопрос человеку. Ответ сопровождается указанием раздела документации.
*Почему это центральное решение:* выдуманный ответ про то, платный ли сервис или что происходит с данными о здоровье, стоит дороже, чем отсутствие ответа. Указание раздела делает ошибку проверяемой.
*Как проверяется:* набор контрольных вопросов, где часть заведомо вне корпуса; тест требует отказа и предложения эскалации.

**Решение 5. Модель — актуальная, задаётся конфигурацией.**
По умолчанию `claude-opus-5`. Значение выносится в переменную окружения, чтобы выбор модели и связанный с ним расход были решением эксплуатации, а не константой в коде. Устаревший `anthropic/claude-sonnet-4` в `openrouter/client.go:20` заменяется в любом случае.
*Соображение стоимости:* при закэшированном префиксе основная часть ввода читается из кэша, поэтому запрос стоит существенно меньше номинала; более дешёвые `claude-sonnet-5` или `claude-haiku-4-5` остаются доступной альтернативой через ту же переменную, если по наблюдениям качество ответов это позволит.
*Проверить при реализации:* сохраняется ли кэширование префикса при обращении через OpenRouter; если нет — обращаться к первичному API напрямую для этого сценария.

**Решение 6. Связывание с заявкой — по ссылке с подписанным токеном, а не по контакту.**
Кнопка «Спросить в Telegram» ведёт на бота с параметром глубокой ссылки, содержащим подписанный токен заявки. Бот связывает чат с заявкой.
*Почему не по имени пользователя или телефону:* имя в Telegram не подтверждает личность, а совпадение по контакту дало бы возможность подтянуть чужую заявку.
*Что это даёт оператору:* шаг, на котором человек застрял, и введённые параметры — то есть ответ на вопрос «что у него не получилось» без переспрашивания.

**Решение 7. Зарегистрированный пользователь направляется в приложение.**
Если чат связан с существующим аккаунтом, бот отвечает на общие вопросы, но по всему, что касается плана, питания и прогресса, направляет в чат с куратором.
*Почему так:* куратор — оплаченная и содержательная часть продукта; дублирование канала размывает ответственность и уводит переписку из места, где она видна куратору.

**Решение 8. Эскалация — простая: пометка, очередь, ответ, закрытие.**
Обращение создаётся по явной просьбе человека, при отказе бота ответить и при повторном непонимании. Оператор работает в административном разделе; ответ доставляется в тот же чат.
*Почему минимально:* объём обращений неизвестен; строить очереди и уровни поддержки до появления потока преждевременно.

**Решение 9. Ограничения против злоупотребления.**
Ограничение частоты по чату и общий дневной предел обращений к модели. При исчерпании — вежливый отказ и предложение эскалации.
*Почему обязательно:* публичный вход, за которым стоит платная модель. Дневной лимит на распознавание еды в проекте уже есть — здесь применяется тот же подход.

**Решение 10. Данные о здоровье в боте не обрабатываются.**
Системная инструкция запрещает запрашивать и обсуждать конкретные показатели. Сообщения пользователей хранятся ограниченный срок и входят в состав выгрузки и удаления, если чат связан с аккаунтом.

## Risks / Trade-offs

- **Риск: бот всё равно выдумает ответ.** → Строгая инструкция, обязательное указание раздела, набор контрольных вопросов в тестах, ручная проверка первых сотен диалогов, лёгкий путь эскалации.
- **Риск: расход на модель выйдет из-под контроля.** → Ограничение частоты по чату, дневной предел, наблюдение за долей чтений из кэша, модель в переменной окружения.
- **Риск: префикс перестанет кэшироваться из-за случайного изменения.** → Метрика доли чтений из кэша и оповещение при её падении; тест на побайтовую стабильность собираемого префикса.
- **Риск: webhook станет вектором нагрузки или подделки.** → Секретный заголовок Telegram, ограничение частоты, ограничение размера тела из `harden-api-limits`.
- **Риск: обращения останутся без ответа.** → Оповещение оператору о новом обращении, отображение времени ожидания, честное сообщение человеку о режиме работы поддержки.
- **Риск: документация устареет и бот начнёт вводить в заблуждение.** → Зависимость ответов от `docs/user-guide/` фиксируется в `CLAUDE.md`; изменение поведения продукта обязано сопровождаться правкой документации.
- **Trade-off: бот в общем процессе API** делит с ним ресурсы и деплой. Принимаем ради простоты эксплуатации; модуль изолирован и выносится при необходимости.

## Migration Plan

1. Клиент Telegram, приём webhook, эхо-ответ — проверка контура на dev.
2. Встраивание корпуса, сборка префикса, обращение к модели с кэшированием; замер доли чтений из кэша.
3. Набор контрольных вопросов и проверка отказов на вопросах вне корпуса.
4. Эскалация и административный раздел оператора.
5. Связывание с заявкой и с аккаунтом.
6. Ограничения частоты и дневной предел.
7. Публикация ссылки на бота на посадочной странице и в онбординге; наблюдение за первыми диалогами вручную.

**Откат:** бот выключается снятием переменных окружения; на webhook перестают приходить обновления после его отзыва в Telegram. Основной продукт не затрагивается.
