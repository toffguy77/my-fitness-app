## Context

Текущий CI занимает шесть джоб и создаёт впечатление плотного контроля: тесты, покрытие, сборка, сканирование безопасности, сканирование контейнеров, анализ производительности. При этом ревизия обнаружила в проде незарегистрированный обработчик, фронтенд, обращающийся к несуществующему пути, полностью мёртвую фичу с зелёными тестами и модуль-заглушку, отдающий выдуманные данные. Ни одна из шести джоб не могла их поймать — потому что все они проверяют артефакты по отдельности, а не работающую систему.

Ключевое наблюдение: тесты на `sqlmock` проверяют, что функция составляет ожидаемый SQL, а не что фича работает. Такой тест остаётся зелёным, если функцию никто не вызывает. Отсюда приоритет: E2E и интеграционные тесты против реальной БД важнее, чем ещё один процент покрытия.

## Goals / Non-Goals

**Goals:**
- Ни один шаг CI не изображает проверку.
- Класс ошибок «код написан, но не подключён» ловится автоматически.
- Гонки в горутинах обнаруживаются до прода.
- Проверки безопасности блокируют, а не информируют.
- Между зелёным CI и выкаткой есть автоматическая связь.

**Non-Goals:**
- Не повышаем целевые пороги покрытия — цель не число, а осмысленность проверок.
- Не переписываем существующие тесты на моках на интеграционные.
- Не вводим нагрузочное тестирование.
- Не переезжаем с Dokploy.

## Decisions

**Решение 1. E2E — обязательная блокирующая джоба на каждом PR.**
Поднимаются PostgreSQL как сервис-контейнер, собранные образы API и веба, применяются миграции, засеваются тестовые пользователи, прогоняется Playwright.
*Почему обязательная, а не ночная:* ночной прогон сообщает о поломке после слияния. Ровно те дефекты, которые мы чиним, дожили до прода именно так.
*Стоимость:* несколько минут на PR. Приемлемо.
*Альтернатива:* прогон только на `dev`. Отвергнута: `main` получает изменения из `dev`, ошибка попадёт в прод.

**Решение 2. Интеграционные тесты против реальной PostgreSQL — отдельный тег сборки.**
Файлы помечаются `//go:build integration`; локально не мешают, в CI запускаются отдельной джобой с сервис-контейнером.
*Почему тегом:* `go test ./...` остаётся быстрым для разработчика.
*Что покрывают в первую очередь:* применение всех миграций вперёд и назад; выполнение реальных запросов каждого модуля; проверка, что зарегистрированные маршруты действительно отвечают.

**Решение 3. Порог покрытия бэкенда вводится по фактическому уровню, а не по желаемому.**
Измеряем текущее покрытие и ставим порог на нём же, запрещая снижение. Повышение — отдельным решением.
*Почему так:* порог выше фактического заблокирует все PR и будет немедленно отключён.
*Альтернатива:* сразу целевые 80%. Отвергнута по причине выше.

**Решение 4. Фиктивный шаг удаляется, а не переписывается.**
Реальную проверку фронтенда уже делает `jest` через `coverageThreshold`. Дублирующий шаг с `echo` удаляется целиком.
*Почему это важно:* шаг с зелёной галочкой и текстом «coverage meets threshold» хуже отсутствия шага — он вводит в заблуждение при чтении лога.

**Решение 5. `golangci-lint` включается ограниченным набором анализаторов.**
Стартовый набор: `govet`, `errcheck`, `staticcheck`, `ineffassign`, `bodyclose`, `rowserrcheck`, `sqlclosecheck`, `noctx`. Последние четыре напрямую релевантны коду с `database/sql` и HTTP-клиентами.
*Почему не весь набор:* полный набор даст сотни срабатываний на существующем коде, и линтер отключат. Расширение — отдельными шагами.

**Решение 6. `-race` включается для всего прогона тестов.**
*Стоимость:* прогон замедляется в несколько раз.
*Почему всё равно да:* хаб WebSocket разделяется между горутинами, кураторская аналитика использует `errgroup` с записью в общие структуры. Это ровно тот код, где гонка проявится под нагрузкой прода и не проявится локально.

**Решение 7. Образы собираются один раз, передаются артефактом.**
Джоба `build-images` сохраняет образы, `container-security-scan` и `e2e` их загружают.
*Выигрыш:* три сборки превращаются в одну.

**Решение 8. Развёртывание — отдельный workflow, запускающий Dokploy через его API.**
Успешный CI на `dev` запускает деплой dev; тег вида `v*` на `main` — деплой прода. После выкатки workflow опрашивает `/ready` до успеха с таймаутом и помечает деплой неуспешным при его недостижении.
*Почему через API, а не автодеплой Dokploy по push:* автодеплой по push выкатывает и то, что не прошло CI.
*Альтернатива:* оставить ручной деплой. Отвергнута: не связывает зелёный CI с выкаткой, а память команды уже фиксировала «работа считается сделанной только после проверки на dev и prod».

**Решение 9. Обязательный набор проверок для слияния.**
Блокируют: тесты фронтенда, тесты бэкенда с `-race`, линтеры, интеграционные тесты, E2E, сборка, целостность кодовой базы, сканирование безопасности. Не блокируют: анализ размеров артефактов.

## Risks / Trade-offs

- **Риск: включение `-race` и E2E удлиняет обратную связь на PR.** → Джобы идут параллельно; общее время определяется самой длинной, а не суммой. Целевое время полного прогона — до 15 минут.
- **Риск: существующие e2e-тесты нестабильны, поскольку не запускались в CI.** → Первый шаг — прогнать как есть, отсортировать на рабочие и нестабильные; нестабильные временно помечаются пропускаемыми с заведённой задачей, а не отключают всю джобу.
- **Риск: `golangci-lint` и `-race` дадут срабатывания на существующем коде.** → Разбор — отдельные задачи внутри этого изменения; включение блокировки после исправления.
- **Риск: снятие `continue-on-error` с `npm audit` заблокирует PR из-за уязвимости в транзитивной зависимости без исправления.** → Механизм осознанного исключения с указанием причины и срока пересмотра, по образцу существующего `.trivyignore`.
- **Trade-off: автоматический деплой прода по тегу** требует дисциплины с тегами. Принимаем: тег — явное намеренное действие.

## Migration Plan

1. Удалить фиктивный шаг, включить `-race`, `go vet`. Быстро и без нового окружения.
2. Добавить `golangci-lint` в информационном режиме, разобрать срабатывания, включить блокировку.
3. Добавить интеграционную джобу с PostgreSQL и прогоном миграций.
4. Добавить E2E: прогнать, стабилизировать, включить блокировку.
5. Единая сборка образов, снятие `continue-on-error`.
6. Workflow развёртывания, сначала только dev.
7. Включить обязательные проверки в настройках защиты веток.

**Откат:** каждый шаг — отдельный PR в workflow; откат снятием требования в защите ветки.
