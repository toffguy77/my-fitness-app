## Context

Авторизация в API сейчас двухслойная: `RequireAuth` кладёт `user_id` в контекст, `RequireRole` проверяет роль. Третий слой — «принадлежит ли запрошенный ресурс этому пользователю» — реализован вручную внутри сервисов. В модуле `curator` он сделан аккуратно: `verifyRelationship` вызывается в 14 местах из 15. Пятнадцатый роут ведёт в другой модуль (`nutrition-calc`), где такой функции нет, — и проверка потерялась.

Это структурная, а не единичная проблема: пока проверка живёт в сервисе, ничто не связывает «роут принимает `:id` чужого ресурса» с «проверка выполнена». Один файл на 542 строки с плоским списком роутов делает пропуск незаметным при ревью.

RLS мог бы быть защитной сеткой, но он выключен миграцией 015 и middleware не подключён. Возвращать его сейчас — отдельный крупный проект (нужен отдельный пользователь БД без `BYPASSRLS`, `FORCE ROW LEVEL SECURITY` на каждой таблице, ревизия всех запросов, включая админские и кураторские, которые обязаны видеть чужие строки). Здесь мы этого не делаем, но и не оставляем полумёртвый код, который создаёт ложное впечатление защиты.

## Goals / Non-Goals

**Goals:**
- Закрыть найденную IDOR-уязвимость.
- Сделать так, чтобы пропустить проверку владения на новом роуте было структурно трудно, а не «нужно не забыть».
- Сделать список защищаемых роутов явным и проверяемым тестом.
- Убрать мёртвый RLS-код, чтобы он не читался как работающая защита.

**Non-Goals:**
- Не возвращаем RLS (отдельный проект; см. Open Questions).
- Не меняем модель ролей (`user` / `coordinator` / `super_admin`).
- Не трогаем публичные контентные роуты, у которых нет владельца.

## Decisions

**Решение 1. Проверка связи — middleware на группе роутов, а не вызов в сервисе.**
`RequireClientRelationship(db)` читает `:id` из пути, берёт `user_id` из контекста, проверяет активную запись в `curator_client_relationships` и кладёт `client_id` в контекст. Вешается один раз на подгруппу `/curator/clients/:id`.
*Почему так:* защита становится свойством маршрута. Новый роут, добавленный в эту группу, защищён по умолчанию — включая роуты из чужих модулей, что и было корнем уязвимости.
*Альтернатива:* добавить `verifyRelationship` в `nutrition-calc`. Отвергнута: чинит один случай, не чинит класс. Следующий роут из третьего модуля повторит историю.
*Альтернатива:* вынести проверку в общий сервис-хелпер. Отвергнута: всё ещё требует помнить о вызове.

**Решение 2. `verifyRelationship` в `curator/service.go` остаётся.**
Двойная проверка стоит один быстрый индексный запрос и защищает сервисный слой, если его когда-нибудь вызовут не из HTTP-хендлера (фоновая задача, gRPC).
*Trade-off:* лишний запрос на роут. Принимаем: запрос по уникальному индексу, единицы микросекунд.

**Решение 3. Пакет `internal/router` с файлом на домен.**
`router.New(deps) *gin.Engine` — единственная точка регистрации. Каждый доменный файл экспортирует `registerXxxRoutes(rg *gin.RouterGroup, deps Deps)`.
*Почему так:* даёт ревьюеру диф на 20 строк в файле своего домена вместо строки, потерянной среди сотни. Это же изменение — предпосылка для теста-матрицы, которому нужен собранный роутер.
*Альтернатива:* оставить `main.go`. Отвергнута: файл уже скрыл одну уязвимость и один незарегистрированный роут (см. изменение `enforce-password-policy`).

**Решение 4. Тест-матрица строится обходом реального роутера.**
Тест получает `gin.Engine` из `router.New`, перебирает `engine.Routes()` и для каждого роута с параметром пути `:id`/`:clientId` проверяет наличие записи в явном реестре `protectedRoutes` (роут → тип защиты). Роут с `:id`, отсутствующий в реестре, роняет тест.
*Почему так:* невозможно добавить роут с чужим идентификатором и не заметить этого — компилятор не поможет, а тест поможет.
*Альтернатива:* только точечные негативные тесты. Отвергнута: покрывает то, что вспомнили, и молчит о новом.

**Решение 5. Ответ при отказе — `403` без раскрытия существования ресурса.**
Тело — общее сообщение на русском, без указания, существует ли клиент. `404` не используем, чтобы не плодить два кода для одного класса отказа и не заставлять фронт различать их.
*Альтернатива:* `404` для сокрытия существования. Отвергнута: куратор и так знает список своих клиентов; `403` честнее описывает ситуацию и проще для фронта.

**Решение 6. Удаление RLS-кода, а не его починка.**
Удаляются `middleware/rls.go`, `WithRLSConn`, `rlsConnFromContext` и ветвление в трёх методах `postgres.go`. Миграции 004 и 015 остаются в истории нетронутыми.
*Альтернатива:* включить RLS. Отвергнута как отдельный проект: требует нового пользователя БД, `FORCE ROW LEVEL SECURITY`, политик для кураторских и админских чтений и ревизии всех запросов. Делать это «заодно» — рисковать боевыми данными.

## Risks / Trade-offs

- **Риск: перенос ~100 роутов в новый пакет ломает пути или теряет middleware.** → Тест-матрица сравнивает полный список `method + path + количество handlers` до и после переноса; снимок списка роутов фиксируется в тесте как golden-файл.
- **Риск: middleware ломает роуты, где `:id` — не идентификатор клиента** (например, `/curator/clients/:id/weekly-plan/:planId`). → Middleware вешается на подгруппу `/clients/:id`, `planId` и `taskId` проверяются в сервисе по `curator_id`, как сейчас.
- **Риск: удаление веток RLS в `postgres.go` затронет все запросы.** → Ветки сейчас никогда не срабатывают (middleware не зарегистрирован), поведение эквивалентно; покрывается существующими тестами модулей.
- **Trade-off: `403` вместо `404`** раскрывает, что запрошенный идентификатор в принципе валиден. Для кураторов, работающих внутри одной платформы, это приемлемо.

## Migration Plan

1. Исправить IDOR точечно (`nutrition-calc/handler.go`) и выкатить отдельным коммитом — уязвимость закрывается, не дожидаясь рефакторинга.
2. Добавить middleware и тест-матрицу.
3. Перенести регистрацию роутов в `internal/router`, сверяя golden-снимок.
4. Удалить мёртвый RLS-код.
5. Перевести обработку ошибок на `apperrors`.

**Откат:** каждый шаг — отдельный коммит, откатывается независимо. Схема БД не затрагивается.

## Open Questions
