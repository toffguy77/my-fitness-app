## Context

Сейчас `CreateNotification` вызывается из мест порождения событий: `curator/service.go:2325,2346,2367` (план обновлён, задача назначена, получен фидбек), из чата и из публикации контента. Каждое такое место знает про запись в таблицу и ничего не знает про доставку. Это удачно: достаточно расширить одну функцию, а не двадцать точек вызова.

Ограничения контура: SMTP — ящик Яндекса с бытовыми лимитами отправки, поэтому поток писем «на каждое событие» нежелателен и технически, и по восприятию. Push через сервисы браузеров бесплатен и мгновенен, но требует разрешения пользователя, которое даёт меньшинство, и не работает на iOS вне установленного на домашний экран PWA. Значит ни один канал не самодостаточен: нужны оба плюс приложение.

## Goals / Non-Goals

**Goals:**
- Клиент узнаёт о сообщении куратора, не открывая приложение.
- Куратор видит, что клиент оповещён.
- Пользователь управляет каналами по типам событий и не получает лишнего.
- Поток писем ограничен и не выглядит спамом.

**Non-Goals:**
- Не вводим SMS и мессенджеры как каналы уведомлений (Telegram-бот в отдельном изменении решает задачу поддержки, а не уведомлений).
- Не строим маркетинговые рассылки.
- Не делаем мобильные приложения с нативным push.
- Не меняем состав доменных событий.

## Decisions

**Решение 1. Точка расширения — `CreateNotification`, а не места порождения событий.**
Функция после записи в таблицу ставит задания на доставку по каналам согласно предпочтениям.
*Почему так:* один шов вместо двадцати; новые типы событий получают доставку автоматически.
*Альтернатива:* шина событий с подписчиками. Отвергнута: избыточна для десятка типов событий и добавляет асинхронность там, где её пока не требуется.

**Решение 2. Три канала с разной ролью, а не три копии одного сообщения.**
- Приложение — источник истины, получает всё.
- Push — мгновенное оповещение о срочном: сообщение в чате, назначенная задача, фидбек куратора.
- Почта — догоняющий канал: письмо уходит, только если пользователь не прочитал уведомление в приложении в течение заданного времени.
*Почему так:* иначе пользователь получает одно и то же трижды, и первым делом отключает всё.
*Альтернатива:* отправлять во все каналы сразу. Отвергнута по причине выше.

**Решение 3. Письма уходят дайджестом, а не по событию.**
Непрочитанные события копятся; задача формирует одно письмо не чаще заданной частоты (по умолчанию раз в сутки; для сообщений чата — ускоренный порог в несколько часов). Мгновенные письма остаются только у транзакционных операций (подтверждение почты, сброс пароля) — они не проходят через этот слой.
*Почему так:* держит нагрузку на почтовый ящик предсказуемой и снижает шанс попасть в спам.

**Решение 4. Web Push с ключами VAPID, подписки — в базе.**
Одна запись на устройство: endpoint, ключи, момент создания, момент последнего успеха. Ответы `404` и `410` от сервиса доставки означают, что подписка мертва — она удаляется.
*Почему в базе, а не в памяти:* подписки переживают перезапуск и работают при нескольких инстансах.
*Ограничение iOS:* push работает только для PWA, добавленного на домашний экран. Интерфейс должен объяснять это, а не молча не работать. Фиксируется требованием спека.

**Решение 5. Тихое время — по часовому поясу пользователя, с задержкой, а не отменой.**
Push, выпавший в тихое время, не отменяется, а доставляется в начале следующего разрешённого интервала. Приложение и почта тихим временем не ограничены.
*Почему задержка, а не отмена:* пропавшее уведомление хуже пришедшего позже.

**Решение 6. Матрица предпочтений «тип события × канал» с явными умолчаниями.**
Умолчания: сообщение в чате — приложение и push; задача назначена, план обновлён, получен фидбек — приложение и push; напоминание об отчёте — приложение и почта; публикация контента — приложение, по категориям (существующее поведение сохраняется).
*Почему явные умолчания:* пользователь, ничего не настроивший, должен получать полезное и не получать назойливое.
*Миграция:* существующие записи `content_notification_preferences` переносятся в новую модель без изменения смысла для пользователя.

**Решение 7. Отписка от писем — по подписанной ссылке без входа.**
Ссылка содержит идентификатор пользователя и подпись; переход отключает почтовый канал для соответствующего типа. Требование почтовых провайдеров и обычная вежливость.
*Безопасность:* ссылка позволяет только отключить доставку, ничего не раскрывает и не включает.

**Решение 8. Учёт доставки отдельной таблицей.**
`notification_deliveries`: уведомление, канал, статус, время попытки, ошибка. Позволяет ответить на вопрос «дошло ли до клиента» и показать это куратору.
*Почему это важно продукту:* куратор, видящий «оповещён», перестаёт дублировать сообщения и звонить.

**Решение 9. Доставка выполняется фоновой задачей, а не в обработчике запроса.**
`CreateNotification` пишет уведомление и задание на доставку в одной транзакции; отправкой занимается задача.
*Почему так:* отправка push и письма не должна ни замедлять запрос куратора, ни падать вместе с внешним сервисом.

## Risks / Trade-offs

- **Риск: письма попадут в спам при росте объёма.** → Дайджест вместо потока, корректные заголовки отписки, проверка SPF/DKIM/DMARC для домена отправителя (отдельная задача), контроль доли неуспешных доставок.
- **Риск: push не работает на iOS без установки PWA** и это воспримут как поломку. → Определение платформы и явная подсказка про добавление на домашний экран.
- **Риск: пользователи откажут в разрешении на push и вернуть его будет некуда.** → Запрашивать разрешение не при первом входе, а в момент, когда польза очевидна (после первого сообщения от куратора), с предварительным объяснением.
- **Риск: накопление мёртвых подписок.** → Удаление при ответах `404`/`410`, периодическая чистка.
- **Риск: ключи VAPID не заданы в окружении.** → Push объявляется опциональной возможностью; при отсутствии ключей канал выключается с предупреждением при старте, интерфейс его не предлагает.
- **Trade-off: догоняющие письма приходят с задержкой.** Принимаем: срочное закрывает push, а письмо — страховка для тех, у кого push нет.

## Migration Plan

1. Схема: подписки, доставки, расширение предпочтений, тихое время. Перенос существующих предпочтений контента.
2. Слой доставки и задача отправки, пока с одним включённым каналом «приложение» — поведение не меняется.
3. Push: ключи, подписка, отправка. Включение на dev, проверка на браузерах и на iOS-PWA.
4. Почта: дайджест, отписка, шаблоны. Включение на dev.
5. Новая страница предпочтений.
6. Постепенное включение на проде: сначала push для сообщений чата, затем остальные типы, затем письма.

**Откат:** каналы выключаются переменными окружения без пересборки; уведомления в приложении продолжают работать.

## Open Questions

- Настроены ли SPF, DKIM и DMARC для домена отправителя? Проверяется задачей 1.2; без них дайджесты пойдут в спам.
- Какой порог «не прочитано» для догоняющего письма о сообщении чата — два часа или четыре? Уточнить после наблюдения за поведением на проде.
