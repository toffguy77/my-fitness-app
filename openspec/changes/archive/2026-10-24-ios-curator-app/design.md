## Context

Кураторская часть веба — пять вкладок (`CuratorFooterNavigation.tsx`):
«Клиенты», «Чаты», «Контент», «Заявки», «Обращения». Права на бэкенде:
- всё под `/curator/*` открыто `coordinator`;
- заявки и обращения — ещё и `super_admin`;
- маршруты клиента закрыты `RequireClientRelationship`.

«Требуют внимания» считает сервер (`collectAttention` в
`modules/curator/service.go`), это единственное определение. Приложение его
только показывает.

## Goals / Non-Goals

**Goals:**
- Ответить клиенту, проставить КБЖУ по фото, взять заявку и ответить в обращение — за секунды с телефона, в том числе из пуша.
- Видеть, кому нужно внимание, в том же порядке и по тем же причинам, что в вебе.

**Non-Goals:**
- Создание и правка статей, загрузка обложек и медиа, импорт `.md`.
- График бенчмарка 4/8/12 недель с выбором периода — показывается упрощённо (последние 4 недели).
- Офлайн-запись для куратора: действия куратора — только онлайн, кэш — для первого кадра.

## Decisions

### Четыре вкладки, «Контент» — в веб

В таббаре «Клиенты», «Чаты», «Заявки», «Обращения». Бейджи:
- у «Чатов» — непрочитанные сообщения;
- у «Обращений» — эскалированные без ответа.

Отвергнуто:
- **Перенести редактор статей.** Markdown с тулбаром, превью, импорт
  файлов и drag-and-drop — работа за клавиатурой. Урезанный редактор на
  телефоне породит статьи, которые потом всё равно правят в вебе.
- **Список статей только для чтения.** Куратор не делает с ним ничего
  полезного на ходу. Лишняя вкладка в таббаре.

### Переписка по id клиента — отдельная ручка

Карточка клиента, пуш и ссылка `/curator/chat/:clientId` открывают переписку
по клиенту. Веб сейчас загружает весь список переписок и ищет нужную, а при
неудаче висит на «Загрузка…».

`GET /conversations/by-participant/:userId` отдаёт переписку, где вызывающий и
`userId` — участники. Если такой нет — `404`. Защита — `participant`:
посторонняя пара даёт `404`, а не `403`, чтобы не раскрывать существование
переписки.

Отвергнуто:
- **Искать в списке на телефоне.** Лишняя загрузка на каждом пуше. Тот же
  баг с вечной загрузкой.

### Ввод КБЖУ по фото — лист поверх переписки

Кнопка «Ввести КБЖУ» есть под каждым фото клиента. Она открывает лист:
- блюдо, приём, вес, ккал, Б/Ж/У;
- приём по умолчанию — по времени фото, по тем же часам, что у клиента.

Отправка — `POST /conversations/:id/messages/:msgId/food-entry`. Лист не
закрывается при ошибке сети и сохраняет введённое.

### Отзыв, план и задачи — листы с формой

Формы короткие (до 8 полей), поэтому это листы `.presentationDetents([.large])`
с «Готово» в навигационной панели. Подтверждение нужно только у удаления плана:
«Удалить активный план? Клиент останется без целей…».

### Обращения: ответ в канал обращения, повтор без дубля

- **Подпись поля ответа** зависит от `channel`: «Ответ уйдёт в Telegram» для
  Telegram и «Ответ увидит посетитель сайта» для веб-виджета.
- **Недоставка.** У исходящего сообщения с `delivered: false` есть подпись
  «Не доставлено в Telegram · Повторить».
- **Повтор.** `POST …/messages/:messageId/retry` отправляет тот же текст
  тому же получателю и ставит `delivered_at`. Новой записи в треде нет.

Отвергнуто:
- **Повтор как новый ответ.** В треде две одинаковые реплики, а клиент при
  удачной второй попытке видит дубль, если первая на деле дошла с опозданием.

### Пуши куратору

Через `ios-push-notifications`:
- `chat_message` — с ответом из уведомления;
- `support_escalated` — открывает тред;
- `curator_requested` — открывает заявку;
- `client_left` — открывает клиента.

## Risks / Trade-offs

- [Куратор отвечает из пуша, не видя контекста] → ответ из пуша приходит в ту же переписку; в пуше видно имя клиента и последнее сообщение; заметно меньше риска, чем ответ с задержкой в часы.
- [Суперадмин ожидает админку в приложении] → экран профиля суперадмина показывает «Админка — в веб-версии» со ссылкой.
