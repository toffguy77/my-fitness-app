# Контракт API `plan-diary-logging`

## Отклонения

Записаны бэкендом при реализации; всё ниже имеет приоритет над таблицами.

1. **Идентификатор продукта версии — SQL-функция `recipe_product_id(uuid)`**
   (миграция 094), а не `uuid_generate_v5`: `uuid-ossp` — расширение, которое
   миграция поставить надёжно не может (одна схема на всю базу, управляемый
   кластер). Функция — md5 над `'recipe-product:' || version_id` с битами
   версии и варианта UUID v3. Это единственное место вычисления: одобрение,
   «Съел» и поиск зовут её же; в Go идентификатор не вычисляется.
2. **Заполнение — в самой миграции**, без шага на старте сервиса. Продукт
   получают версии в состоянии `approved` **и `superseded`**: блюдо
   сохранённого плана может ссылаться на устаревшую версию.
3. **`serving_unit = 'g'`**, не `'г'`: единицы — коды с миграции 061.
   `serving_size` и `default_weight` — вес порции рецепта.
4. **Итоги и само блюдо по весу записи.** У съеденного блюда `nutrition`,
   `percent_of_target` и вклад в `totals`/`remaining`/`deviations`/
   `calorie_split` считаются по `eaten_grams`; `grams` остаётся весом плана
   (вернётся, если запись удалят). `eaten_grams` — `portion_amount` записи
   как есть: дневник и сам считает КБЖУ по нему как по граммам при любом
   `portion_type`.
5. **Съедено — только при совпадении** `user_id`, даты и приёма записи с
   блюдом. Иначе `eaten = false`, `eaten_grams = null`, `food_entry_id = null`
   (хотя ссылка в базе хранится до следующего «Съел»).
6. **`POST .../eat`:** `404` — плана на дату нет (план **не** собирается) или в
   приёме нет блюда (приём не в плане или пуст); `422` — неизвестный
   `:mealType`, дата, `grams` ≤ 0 или > 2000 (не округляется), `time` не
   `HH:MM` (00:00–23:59). Повтор — `200` с той же записью, и `grams`/`time`
   повтора игнорируются. `time` по умолчанию — время клиента
   (`user_settings.timezone`), если дата плана — его сегодня. Блокируется строка
   **плана** (`meal_plans … FOR UPDATE`), как во всех правках плана, а не только
   блюда: иначе пересборка, идущая параллельно, могла бы переписать блюдо без
   связи. Запись создаётся внутри той же транзакции тем же путём, что
   `POST /food-tracker/entries`.
7. **`POST .../refit`:** `404`, если плана нет (не собирает). Подгоняются веса
   несъеденных блюд без ручного веса; закреплённые несъеденные блюда тоже
   подгоняются по весу (как в `PUT`), ручные и съеденные — нет. Та же
   подгонка (съеденное — с весом записи) идёт после любого `PUT` блюда.
8. **`PUT .../items/:mealType` у съеденного:** `409 {code: "conflict"}` на
   `recipe_id`, `grams` **и** `reset_grams`; `locked` разрешён.
9. **`regenerate`** оставляет съеденное в его версии и связи, даже если рецепт
   стал недоступен или приём убран из настроек (тогда приём возвращается в
   `meal_types` плана).
10. **`GET ?generate=false`** — `422` на неверную дату, как и без флага; любое
    другое значение `generate` ведёт себя как прежний `GET`.
11. **Поиск:** у элемента-рецепта `source: "recipe"`, `recipeId`,
    `verified: true`, `brand: null`, `category: "Блюда"`, `servingSize` — вес
    порции. У прочих элементов `recipeId` отсутствует. Продукты рецептов
    исключены и из каталога ингредиентов (`/admin/recipes/catalogue-search`,
    исключения клиента): блюдо — не ингредиент.
12. **Аналитика:** `plan_item_eaten` — `source` **обязательное**, значения
    `plan`/`diary`; `plan_refit`, `recipe_logged_from_search` — без свойств.


Миграция — `094_plan_diary_logging`. Обёртка ответов и коды ошибок — как в
`recipe-catalogue/api.md`. Маршруты плана — `RequireRole("client")`, владелец
из сессии, `owner` в `protectedRoutes`.

## Изменения существующих ответов

`PlanItem` (из `meal-day-plan/api.md`) получает поля:

```ts
interface PlanItem {
  // ...прежние поля
  eaten: boolean                 // есть запись дневника на дату и приём пищи этого блюда
  eaten_grams: number | null     // вес из записи дневника (а не из плана)
  food_entry_id: string | null   // только когда eaten = true
}
```

Итоги плана (`totals`, `percent_of_target`, `remaining`, `deviations`) для съеденных
блюд считаются по `eaten_grams`.

Поиск дневника `GET /api/v1/food-tracker/search` (ответ `{items: FoodItem[], total}`):
`FoodItem.source` может быть `"recipe"`; у таких элементов есть
`recipeId: string` (camelCase, как остальные поля `FoodItem`) и `id` — UUID
продукта текущей одобренной версии. Запись такого продукта — обычный
`POST /api/v1/food-tracker/entries`.

## Новые маршруты

| Метод | Путь | Тело / параметры | Ответ |
|---|---|---|---|
| GET | `/api/v1/meal-plans/:date?generate=false` | — | `MealPlan` или `204` без тела, если плана нет; план не создаётся |
| POST | `/api/v1/meal-plans/:date/items/:mealType/eat` | `{grams?: number, time?: "HH:MM"}` | `201 {entry_id: string, plan: MealPlan}`; повтор — `200` с той же записью; `404` нет плана или приём пуст; `422` grams ≤ 0 или > 2000 |
| POST | `/api/v1/meal-plans/:date/refit` | — | `MealPlan` |

- `grams` по умолчанию — вес блюда в плане; `time` по умолчанию — текущее время
  клиента для сегодняшней даты, `12:00` для прочих.
- Запись создаётся как `portionType: "grams"` в приёме пищи блюда, с КБЖУ продукта
  версии рецепта блюда.
- `PUT .../items/:mealType` и `regenerate` для съеденного блюда: замена — `409`;
  пересборка оставляет съеденные блюда на месте с весом записи.
