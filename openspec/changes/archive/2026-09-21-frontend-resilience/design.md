## Context

App Router даёт готовый механизм границ ошибок на уровне сегментов (`error.tsx`), но он не работает, пока файлы не созданы. Сейчас их нет ни одного, поэтому любая ошибка всплывает до дефолтного экрана Next.js. Параллельно в проекте лежит классовый `ErrorBoundary`, не смонтированный никуда, и труба отправки клиентских логов (`shared/utils/logger.ts` → `POST /api/v1/logs`), которая принимает только то, что отправили осознанно.

Ограничение: логи уходят на собственный бэкенд, а не в сторонний сервис. Значит объём отправляемого нужно контролировать самим — цикл рендера, падающий на каждом кадре, способен устроить самому себе отказ в обслуживании.

## Goals / Non-Goals

**Goals:**
- Пользователь никогда не видит английский дефолтный экран фреймворка.
- Сбой одного виджета не уносит страницу целиком.
- У каждой показанной пользователю ошибки есть идентификатор, по которому поддержка находит запись в логах.
- Ошибки клиента становятся видимыми без обращения пользователя.

**Non-Goals:**
- Не подключаем сторонний сервис отслеживания ошибок — это делает изменение `observability-baseline`.
- Не вводим офлайн-режим с очередью запросов.
- Не переписываем существующие состояния загрузки внутри компонентов.

## Decisions

**Решение 1. Два уровня границ: сегменты App Router и точечный `ErrorBoundary`.**
`error.tsx` ловит ошибки рендера сегмента и даёт `reset()`. `ErrorBoundary` применяется точечно вокруг виджетов, падение которых не должно уносить экран.
*Почему оба:* `error.tsx` работает на границе маршрута — падение виджета дашборда унесло бы весь дашборд. Точечная граница оставляет остальные виджеты живыми.
*Альтернатива:* только `error.tsx`. Отвергнута: слишком грубая гранулярность для дашборда с независимыми виджетами.
*Альтернатива:* только `ErrorBoundary`. Отвергнута: не покрывает ошибки серверных компонентов, для которых существует именно `error.tsx`.

**Решение 2. Идентификатор ошибки генерируется на клиенте и показывается пользователю.**
Короткая читаемая строка (например, 8 символов из безопасного алфавита без похожих знаков), одна и та же на экране и в отправленной записи.
*Почему так:* пользователь диктует её в поддержку голосом или пишет в чат — она должна быть короткой и не содержать `0`/`O`, `1`/`l`.
*Альтернатива:* UUID. Отвергнута: не диктуется.
*Альтернатива:* идентификатор с сервера. Отвергнута: ошибка может произойти до или вместо запроса.

**Решение 3. Ограничение потока — по отпечатку ошибки, а не общим счётчиком.**
Отпечаток — хеш от сообщения и первой строки стека. На отпечаток отправляется ограниченное число записей за интервал, дальше только счётчик.
*Почему так:* общий лимит заглушил бы редкую важную ошибку из-за шумной частой.

**Решение 4. Сетевую ошибку отличаем по типу исключения `fetch`, а не по коду.**
`fetch` выбрасывает `TypeError` при недоступности сети; ответ с `5xx` — это успешный `fetch` с плохим статусом. Разделяем на уровне `api-client`, наверх отдаём разные типы ошибок.
*Следствие:* сообщение «проверьте соединение» перестаёт показываться при работающем интернете и упавшем сервере — сейчас они неразличимы.

**Решение 5. Список сегментов с собственным `error.tsx` — по признаку самостоятельного экрана.**
`dashboard`, `food-tracker`, `chat`, `curator`, `admin`, `settings`. Мелкие маршруты (`legal`, `auth`) наследуют корневой.
*Почему так:* собственный экран ошибки имеет смысл там, где у пользователя есть куда вернуться внутри раздела.

## Risks / Trade-offs

- **Риск: глобальный перехват ошибок создаёт нагрузку на `/api/v1/logs`.** → Ограничение по отпечатку на клиенте плюс ограничение частоты по IP на бэкенде (задача 4.4).
- **Риск: `error.tsx` в сегменте скрывает ошибку от разработчика в dev.** → В `development` экран дополнительно показывает сообщение и стек.
- **Риск: идентификатор ошибки бесполезен, если запись не дошла до сервера** (упал и сам логгер). → Отправка идёт до отрисовки экрана, ошибки самого логгера подавляются.
- **Trade-off: точечные границы вокруг виджетов** добавляют обёртки в разметку. Принимаем: применяем только к виджетам с внешними данными.

## Migration Plan

1. Базовые компоненты и утилита идентификатора.
2. Страницы ошибок App Router — выкатываются самостоятельно, дают немедленный эффект.
3. Границы вокруг виджетов.
4. Глобальный перехват и ограничение частоты на бэкенде — выкатывать вместе, чтобы не открыть поток без защиты.

**Откат:** изменения аддитивные, откат возвратом сборки.
