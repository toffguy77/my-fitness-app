## Context

- Цель на дату даёт `nutrition-calc` `RecalculateForDate` (`apps/api/internal/modules/nutrition-calc/service.go:28`): учитывает недельный план куратора, берёт последний вес не позже даты, сохраняет строку в `daily_calculated_targets` и возвращает `nil`, когда считать не из чего; `MissingInputsFor` (`:124`) говорит, чего не хватает. Сейчас его зовут пять мест — шестое ничего не ломает.
- Кандидаты — одобренные версии рецептов, отфильтрованные `recipeaccess` (`recipe-catalogue`, решение 5). У версии есть КБЖУ на 100 г, вес порции и приёмы пищи.
- Записи дневника, связь с планом и список покупок — следующие изменения; здесь план только хранится и показывается.

Цели план читает, ничего не записывая: `nutrition-calc` `TargetForDate` отдаёт сохранённую строку `daily_calculated_targets` за дату — ту же, что показывает дневник, — а если её нет, считает цель без сохранения. *Отвергнуто:* звать `RecalculateForDate` — он перезаписывает строку текущим профилем (для прошлой даты это подмена истории) и создаёт строки на будущие даты, которые дневник потом отдаёт как есть, не замечая недельного плана куратора, назначенного позже. Найдено ревью; сторож — `TestOpeningPlanLeavesStoredTargetsAlone`.

## Goals / Non-Goals

**Goals:** детерминированный подбор под КБЖУ без модели; правка поверх; честный показ недобора; хранение плана по датам.

**Non-Goals:** несколько блюд в приёме пищи, повтор ингредиентов между днями (готовка партиями), учёт съеденного (`plan-diary-logging`), планы для куратора.

## Decisions

### 1. Схема

```
meal_plan_settings  user_id PK → users ON DELETE CASCADE, meal_types TEXT[] NOT NULL
meal_plans          id UUID, user_id → users ON DELETE CASCADE, date DATE, seed BIGINT,
                    target_kcal, target_protein, target_fat, target_carbs, created_at, updated_at,
                    UNIQUE (user_id, date)
meal_plan_items     plan_id → meal_plans ON DELETE CASCADE, meal_type, recipe_id, recipe_version_id,
                    grams INT, locked BOOL, manual_grams BOOL, PRIMARY KEY (plan_id, meal_type)
```

Строка блюда хранит версию рецепта, а не только рецепт: план на прошлую дату не меняется от одобрения новой версии. При пересборке и замене берётся текущая одобренная версия.

*Отвергнуто:* хранить план как JSONB в одной строке — `plan-diary-logging` и `shopping-list` ссылаются на отдельные блюда и группируют по ним.

### 2. Подбор — чистый пакет `mealplan/generator`

Вход: цель дня, выбранные приёмы и их доли, кандидаты по приёмам (КБЖУ на 100 г, вес порции), закреплённые и ручные блюда, рецепты из планов за 7 дней, зерно. Выход: блюдо и вес на каждый приём, КБЖУ, отклонения.

1. **Отбор кандидатов.** Для каждого приёма — до 12 рецептов, ближайших по соотношению Б/Ж/У к доле цели этого приёма (косинусная близость вектора КБЖУ на 100 г).
2. **Сочетания.** Полный перебор, если произведение размеров ≤ 600; иначе 600 сочетаний, выбранных генератором случайных чисел с данным зерном. Закреплённые и ручные приёмы фиксированы.
3. **Подгонка весов.** Переменные — множители порций `x_i ∈ [0,5; 2]` незафиксированных блюд. Целевая функция — взвешенная сумма квадратов относительных отклонений: калории ×4, белок ×3 (недобор), белок ×1 (перебор), жиры ×1, углеводы ×1. Решается проекционным градиентным спуском (≤ 4 переменных, 200 итераций), затем вес округляется до 10 г, и проверяются соседние значения ±10 г у каждого блюда.
4. **Оценка.** Значение целевой функции плюс 0,05 за каждый рецепт из планов последних 7 дней. Побеждает минимум; при равенстве — меньший id рецепта (детерминизм).

Допуски спеки (калории ±5%, белок ≥ 90%, жиры и углеводы ±15%) проверяются после подбора; что вне допуска — уходит в ответ как недобор или перебор.

*Отвергнуто:* линейное программирование с целочисленными переменными — внешняя зависимость ради задачи, которая перебором решается за миллисекунды. *Отвергнуто:* подбор моделью — недетерминирован и не гарантирует цифры (претензия к mise).

### 3. Зерно

Начальное зерно — хеш `(user_id, date)`; «пересобрать» записывает новое случайное. Повторное открытие читает сохранённый план и не подбирает заново.

### 4. Альтернативы

Для приёма пищи перебираются доступные кандидаты этого приёма (без текущего), для каждого подгоняются веса всех незафиксированных блюд дня, возвращаются 5 лучших по оценке.

### 5. API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/meal-plans/:date` | план на дату; собирает, если его нет |
| POST | `/api/v1/meal-plans/:date/regenerate` | пересобрать с новым зерном |
| GET | `/api/v1/meal-plans/:date/items/:mealType/alternatives` | альтернативы |
| PUT | `/api/v1/meal-plans/:date/items/:mealType` | `{recipe_id?, grams?, locked?, reset_grams?}` |
| GET/PUT | `/api/v1/meal-plan-settings` | выбранные приёмы пищи |

Все под `RequireRole("client")`, владелец — из сессии; в `protectedRoutes` — `owner`. Ответ плана содержит цель, блюда (рецепт, версия, фото, вес, КБЖУ, проценты, флаги `locked`, `manual_grams`, `unavailable`), итоги, остатки, раскладку калорий, отклонения, `target_changed`, пустые приёмы с причиной.

GET, который пишет (сборка при первом открытии), — сознательно: план на дату — производная, и отдельный «создать» добавил бы клиенту лишний шаг. Повторный GET идемпотентен.

### 6. Фронтенд

`features/meal-plan/`: `DayPlanView` (переключатель даты, итоги дня с процентами и раскладкой калорий, карточки приёмов пищи), `MealSlotCard` (блюдо, вес, КБЖУ, «заменить», «закрепить», правка веса), `AlternativesSheet`, `PlanWarnings` (недобор, `target_changed`, пустой приём, недоступное блюдо, нет цели со ссылкой на профиль). `/menu` открывается на плане сегодняшнего дня, вкладка «Рецепты» — каталог из `recipe-catalogue`.

### 7. События аналитики

`plan_generated` (первая сборка), `plan_regenerated`, `plan_item_replaced`, `plan_item_locked`, `plan_grams_set`, а также `plan_off_target` с показателем вне допуска — чтобы видеть, хватает ли каталога.

## Risks / Trade-offs

- **Маленький каталог → плохое попадание.** Пока рецептов мало, допуск часто не выполняется. Предупреждение показывает недобор честно, а не выдаёт плохой план за хороший.
- **Доли приёмов фиксированы.** Настройка долей отложена; если клиенты попросят, это отдельное изменение.
- **GET с записью** — повторный запрос безопасен, гонку двух первых запросов закрывает `UNIQUE (user_id, date)` с повторным чтением.
