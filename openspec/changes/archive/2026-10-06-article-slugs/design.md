## Context

Статей на проде 10, все от одного автора, все с аудиторией `all`. Статьи с
аудиторией `my_clients` и `selected` читает только вошедший клиент через
`GET /api/v1/content/feed/:id`; публичная ручка их не отдаёт.

## Goals / Non-Goals

**Goals:** читаемый адрес; старые ссылки не ломаются; адрес не уплывает при
правке заголовка.

**Non-Goals:** история slug и редиректы после переименования опубликованной
статьи; slug у внутренних (кураторских, админских) маршрутов, где UUID остаётся.

## Decisions

1. **Транслитерация по упрощённой схеме, как в адресах Яндекса.** ж→zh, х→kh,
   ц→ts, ч→ch, ш→sh, щ→shch, ю→yu, я→ya, ё→e, й→y, ъ/ь опускаются, всё
   прочее, кроме латиницы и цифр, превращается в дефис. Длина до 80 символов,
   обрезка по границе слова. «Что такое КБЖУ и зачем его считать?» →
   `chto-takoe-kbzhu-i-zachem-ego-schitat`.
   *Отвергнуто:* кириллические адреса. В ссылках и логах они превращаются в
   `%D0%...`, и их не прочесть там, где аудит и жаловался.

2. **Заполнение существующих статей в самой миграции.** SQL-функция в схеме
   `pg_temp` повторяет транслитерацию Go. Повторы разводятся суффиксом `-2`,
   `-3` в порядке `published_at`. Совпадение двух реализаций сторожит тест,
   прогоняющий одни и те же заголовки через миграцию и через `Slugify`.
   *Отвергнуто:* заполнять при старте сервиса из Go. Скрытая работа на старте,
   которую никто не увидит в списке миграций и которая повторяется на каждом
   инстансе.

3. **Slug неизменен после публикации.** Правка заголовка опубликованной статьи
   slug не трогает, а явная смена slug у опубликованной статьи отклоняется
   (`409`).
   *Отвергнуто:* таблица прежних slug с редиректами. Для десятка статей одного
   автора это лишний механизм; если понадобится, его можно добавить, не трогая
   этот контракт.

4. **Одна публичная ручка для UUID и slug.** Если `:id` разбирается как UUID —
   поиск по `id`, иначе по `slug` с проверкой формата. Новый маршрут не
   появляется, `routes.golden` и `protectedRoutes` не меняются.
   *Отвергнуто:* `GET /public/content/by-slug/:slug`. Второй публичный маршрут
   на ту же сущность, и записи в обоих реестрах ради одного условия.

5. **301 в `middleware.ts`.** Для пути `/content/<uuid>` middleware спрашивает
   публичный API. Если статья публичная, отвечает `301` на `/content/<slug>`,
   иначе пропускает запрос дальше: это может быть статья для клиентов куратора.
   *Отвергнуто:* `permanentRedirect` в странице. Он отвечает 308, а аудит прямо
   требует 301. Яндекс 308 понимает хуже, а цена 301 — один запрос к API
   только на старых адресах.

6. **Карточка несёт `slug` только при публичном адресе.** Персональная лента
   отдаёт `slug` лишь для статей с аудиторией `all`. Для остальных ссылка
   строится по UUID, потому что по slug их публичная страница не найдёт.

7. **`slug NOT NULL` и уникальное ограничение после заполнения.** Миграция
   добавляет столбец, заполняет все строки и только потом ставит `NOT NULL` и
   `UNIQUE`. Каждый путь создания статьи обязан присвоить slug, иначе вставка
   упадёт сразу, а не породит статью без адреса.
   *Отвергнуто:* частичный уникальный индекс `WHERE slug IS NOT NULL`. Он
   допускает статьи без адреса, а требование говорит, что адрес есть у каждой.

## Risks / Trade-offs

- Две реализации транслитерации (SQL и Go) → SQL выполняется один раз на
  существующих данных и сверен тестом; дальше работает только Go.
- Middleware ходит в API для UUID-адресов → только для старых ссылок; при
  ошибке API запрос пропускается к странице, и она отрисует статью сама.
