## Context

Собственная аутентификация в проекте сделана добротно: refresh-токены хешируются, ротируются, есть детекция переиспользования (`auth/service.go:251-330`). Добавление внешних провайдеров не должно её ломать — внешняя идентичность лишь заменяет способ доказать, кто ты, а дальше выпускается та же пара токенов.

Ключевой риск любой реализации входа через провайдера — совпадение адресов почты. Если внешняя учётная запись с адресом, уже зарегистрированным в системе, автоматически входит в существующий аккаунт, то компрометация или подделка ответа провайдера даёт захват чужого аккаунта. Если же не входит — пользователь получает второй аккаунт и теряет данные. Решение этого вопроса — центральное в дизайне.

Отдельно: три провайдера отличаются деталями (состав возвращаемых полей, наличие подтверждённой почты, способ получения профиля), но не сутью потока. Значит различия должны быть локализованы в адаптере.

## Goals / Non-Goals

**Goals:**
- Регистрация в один шаг без пароля и без письма подтверждения.
- Добавление нового провайдера — реализация интерфейса и запись в реестре, без изменений в потоке аутентификации.
- Совпадение адресов почты не приводит ни к захвату аккаунта, ни к его дублированию.
- Пользователь не может потерять доступ, отвязав последний способ входа.

**Non-Goals:**
- Не реализуем вход по номеру телефона с кодом.
- Не становимся провайдером идентичности для других сервисов.
- Не переносим существующих пользователей на внешних провайдеров принудительно.
- Не реализуем единый выход из всех сервисов провайдера.

## Decisions

**Решение 1. Authorization Code с PKCE, состояние в подписанной cookie.**
Параметр состояния и верификатор PKCE кладутся в кратко живущую `HttpOnly` cookie, а не в серверное хранилище.
*Почему PKCE, хотя клиент конфиденциальный:* защищает от подмены кода авторизации и не стоит ничего.
*Почему cookie, а не таблица:* состояние живёт минуты, привязано к браузеру и не требует уборки.
*Альтернатива:* Implicit flow. Отвергнута: устарел и отдаёт токен через фрагмент URL.

**Решение 2. Совпадение почты не даёт автоматического входа — требуется подтверждение владения аккаунтом.**
Если внешняя учётная запись приносит адрес, уже зарегистрированный, система не входит в аккаунт, а предлагает привязку: пользователь подтверждает владение вводом текущего пароля либо переходом по ссылке, отправленной на этот адрес. Только после этого привязка создаётся, и вход выполняется.
*Почему так:* автоматический вход по совпадению адреса — известный способ захвата аккаунта, если провайдер не гарантирует подтверждённость адреса или если она подделана. Цена — один дополнительный шаг у части пользователей.
*Альтернатива:* автоматически входить, если провайдер сообщает адрес подтверждённым. Отвергнута: мы полагались бы на чужое утверждение в вопросе, где ошибка стоит чужого аккаунта с данными о здоровье.
*Альтернатива:* создавать второй аккаунт. Отвергнута: пользователь теряет дневник и куратора, а поддержка получает поток обращений на слияние.

**Решение 3. Идентичность определяется парой «провайдер + идентификатор пользователя у провайдера», а не почтой.**
Почта — атрибут, который может измениться и не уникален между провайдерами.
*Следствие:* смена адреса на стороне провайдера не ломает вход.

**Решение 4. Единый интерфейс адаптера.**
Адаптер отвечает за построение адреса авторизации, обмен кода на токен и получение нормализованного профиля: идентификатор у провайдера, почта при наличии, имя, ссылка на аватар.
*Почему так:* поток аутентификации не должен знать о различиях провайдеров. Добавление MAX сводится к одному файлу.
*Отсутствие почты у провайдера:* допустимая ситуация — тогда после первого входа система просит указать адрес и подтверждает его письмом; до подтверждения аккаунт ограничен так же, как неподтверждённый при обычной регистрации.

**Решение 5. MAX — третий адаптер, подключаемый после проверки возможностей платформы.**
Отдельная задача: подтвердить наличие у платформы MAX потока OAuth 2.0 для веб-приложений, состав возвращаемого профиля и порядок регистрации приложения. Если поток отличается от OAuth 2.0, MAX выносится в отдельное изменение, а Yandex ID и VK ID выпускаются без него.
*Почему явной задачей:* закладывать в спецификацию непроверенное утверждение о чужом API — способ получить сюрприз на этапе реализации.

**Решение 6. Пользователь без пароля получает пароль через существующий поток восстановления.**
Отдельного эндпоинта установки пароля не вводится: восстановление доступа уже умеет задавать новый пароль по ссылке на подтверждённый адрес.
*Почему так:* меньше кода и меньше поверхности; поток уже покрыт ограничением частоты и тестами.

**Решение 7. Нельзя отвязать последний способ входа.**
Отвязка запрещена, если у пользователя не установлен пароль и это единственная привязка.
*Почему так:* иначе пользователь одним нажатием теряет доступ к аккаунту с данными за год.

**Решение 8. Провайдеры — опциональные возможности.**
Не заданы идентификатор и секрет — провайдер выключен, кнопка не отображается, эндпоинты отвечают `503` в соответствии с изменением `harden-config-and-secrets`.
*Почему так:* локальная разработка и dev не должны требовать регистрации приложений у всех провайдеров.

**Решение 9. Аватар из профиля провайдера не копируется автоматически.**
Ссылка сохраняется, но аватар предлагается установить явно.
*Почему так:* автоматическое скачивание чужого изображения в наш бакет — лишний внешний запрос и лишние данные без запроса пользователя.

## Risks / Trade-offs

- **Риск: подтверждение владения при совпадении почты усложняет путь и снизит конверсию у части пользователей.** → Касается только тех, у кого уже есть аккаунт с этим адресом, то есть возвращающихся; экран объясняет, что происходит и почему.
- **Риск: провайдер вернёт адрес, которым пользователь не владеет.** → Автоматический вход по совпадению не выполняется никогда (Решение 2); при отсутствии совпадения создаётся новый аккаунт, что безопасно.
- **Риск: изменение схемы `users.password` на необязательное сломает существующие запросы.** → Проверить все места чтения поля; вход по паролю для пользователя без пароля должен давать штатный отказ, а не ошибку.
- **Риск: политика безопасности содержимого заблокирует переход к провайдеру.** → Проверить на dev после ужесточения политики в `secure-token-lifecycle`.
- **Риск: секреты приложений провайдеров попадут в репозиторий.** → Только переменные окружения; имена без префикса публичных переменных согласно правилу из `remove-dead-code`.
- **Trade-off: отсутствие автоматического слияния аккаунтов** оставляет возможность завести два аккаунта на разные адреса. Принимаем: слияние аккаунтов — отдельная операция, которую делает поддержка.

## Migration Plan

1. Схема: таблица привязок, снятие обязательности пароля. Проверить чтения поля пароля.
2. Интерфейс адаптера и поток авторизации с одним провайдером (Yandex ID) на dev.
3. Второй провайдер (VK ID) — проверка того, что различия локализованы в адаптере.
4. Связывание с существующим аккаунтом и управление привязками в настройках.
5. Проверка возможностей MAX и, при подтверждении, третий адаптер.
6. Включение на проде по одному провайдеру с наблюдением за долей успешных входов.

**Откат:** провайдеры выключаются переменными окружения без пересборки; вход по паролю продолжает работать.

## Open Questions

- Возвращает ли VK ID адрес почты без дополнительных разрешений? Проверяется задачей 1.3; от ответа зависит, потребуется ли шаг ввода адреса после входа.
