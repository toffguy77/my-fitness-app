## Context

Все исправления найдены при разборе экранов для iOS. Каждое — расхождение
между тем, что обещает интерфейс, руководство пользователя или спека, и
тем, что делает код.

Порядок: это изменение выполняется до iOS-изменений. Два его серверных
куска нужны приложению:
- переписка по клиенту;
- повтор недоставленного ответа.

Третий кусок — согласия до создания аккаунта — общий с нативным
`native/consents`.

## Goals / Non-Goals

**Goals:**
- Данные, которые человек ввёл, попадают туда, куда он думает.
- Нет элементов интерфейса, которые ничего не делают.
- Спека и `CLAUDE.md` описывают код таким, какой он есть.

**Non-Goals:**
- Переключатель Apple Health — его заменяет `healthkit-sync`.
- Редизайн затронутых экранов.

## Decisions

### Согласия до создания аккаунта через провайдера

Колбэк, который создал бы новый аккаунт, сохраняет ожидающий вход тем же
механизмом, что `needs_link_confirmation` (pending-cookie на `/api/v1/auth`).
Затем он уводит на `/auth/consents`. Страница — блок `ConsentSection` с
формы регистрации и кнопка «Продолжить».

`POST /auth/oauth/consents` создаёт аккаунт и записывает согласия тем же
кодом, что регистрация по паролю (`service.go:295`). Нативный
`POST /auth/native/consents` (`ios-native-session`) — тот же сервис, но с
`pending_token` в теле вместо cookie.

Отвергнуто:
- **Чекбоксы согласий над кнопками провайдеров.** Существующий
  пользователь, который просто входит, увидел бы согласия, которые уже давал.
  Новый — мог бы нажать провайдера, не отметив их, и вернуться к той же ошибке.
- **Создать аккаунт и спросить согласия после.** Аккаунт без согласия на
  обработку данных о здоровье — то, чего форма регистрации не допускает.
- **Исправить только в приложении.** Веб продолжил бы создавать такие аккаунты.

Существующие аккаунты, созданные через провайдера без согласий, при
следующем входе проходят тот же экран. Признак — отсутствие обязательных
согласий в `user_consents`.

### Мост для приложения 0.3.x до нативного экрана согласий

Приложение 0.3.x входит через провайдера веб-потоком с `app_challenge` и
экрана согласий не знает; `POST /auth/native/consents` появится в
`ios-native-session`. До тех пор:
- **аккаунт, уже привязанный к провайдеру**, но без обязательных согласий, при
  входе *из приложения* получает сессию, как раньше. Иначе все, кто заводил
  аккаунт через Яндекс или VK, остались бы без приложения. В вебе тот же
  аккаунт проходит экран согласий;
- **новый аккаунт из приложения не создаётся**: колбэк отвечает
  `error=consents_required`, и регистрация через провайдера идёт через сайт.

Мост снимается в `ios-native-session` вместе с появлением нативного экрана.
Тест — `TestAppSignIn_ConsentsBridgeUntilNativeScreen`.

### Отзыв на отчёт — параметр дашборда, а не отдельная страница

Уведомление ведёт на `/dashboard?report=<id>`. Блок отзыва показывается под
карточками дня, страница прокручивается к нему.

Отвергнуто:
- **Страница `/dashboard/weekly-reports/[id]/feedback`, как в старом
  `actionURL`.** Ради одного блока — отдельный маршрут, оболочка и
  навигация назад. Дашборд и так показывает неделю, к которой относится отзыв.
- **Последний отзыв на дашборде всегда.** Нужен эндпоинт списка отчётов
  клиента, которого нет, а без даты прочтения непонятно, когда блок скрывать.

### Поиск со второго символа

API принимает `min=2`, руководство обещает 2, `SearchTab` разрешает 2. Только
хук ставит 3. Нагрузку держит задержка 300 мс и кэш запросов хука.

### Выход — сервер, затем локально

`POST /auth/logout` с cookie отзывает refresh-токен. Сеть может упасть —
тогда локальный выход всё равно выполняется: человек нажал «Выйти» и должен
оказаться на `/auth`.

### Переписка по клиенту и повтор ответа — общие с iOS

Требования к API — `curator-conversation-lookup` и `support-reply-retry`
(перенесены сюда из `ios-curator-app`). Веб начинает ими пользоваться в этом
же изменении, iOS — в своём.

## Risks / Trade-offs

- [Новый экран согласий снижает конверсию регистрации через провайдера] →
  обязательные согласия нельзя отмечать заранее, поэтому экран — короткие
  тексты и одна кнопка. Эффект меряется шагом воронки «согласия» (навык
  `product-analytics`).
- [Старые уведомления об отзыве содержат битую ссылку] → миграция данных
  переписывает `action_url` вида `/dashboard/weekly-reports/<id>/feedback` в
  `/dashboard?report=<id>`.

## Migration Plan

1. Бэкенд:
   - согласия для провайдеров;
   - `by-participant`;
   - `retry`;
   - `actionURL` отзыва и миграция старых ссылок (номер — по `schema_migrations` dev и прода).
2. Веб: остальные исправления.
3. Спека `config-validation` и `CLAUDE.md`.
