## Context

Данные пользователя разбросаны по ~20 таблицам и четырём бакетам S3 (`weekly-progress-photos`, `profiles-photos`, `chats`, `food-photos`). Часть из них принадлежит не только пользователю: сообщения в чате видит куратор, недельные отчёты с фидбеком куратора — часть его рабочего процесса, снапшоты аналитики агрегируют клиентов.

Слепое каскадное удаление (`ON DELETE CASCADE` уже стоит на многих внешних ключах) уничтожило бы часть рабочих данных куратора и оставило бы дыры в агрегатах. Значит для каждой таблицы нужна явная стратегия.

## Goals / Non-Goals

**Goals:**
- Пользователь может потребовать удаления и получить его без обращения в поддержку.
- Ошибочное удаление обратимо в течение 30 дней.
- Пользователь может забрать свои данные в машиночитаемом виде.
- Для каждой таблицы с данными пользователя зафиксирована стратегия, а не «как получится».

**Non-Goals:**
- Не строим админский интерфейс управления удалениями (достаточно истории задач).
- Не реализуем удаление по требованию куратора или администратора — только по инициативе самого пользователя.
- Не удаляем данные из резервных копий БД — они живут по своему сроку хранения, что фиксируется в политике.

## Decisions

**Решение 1. Мягкое удаление с периодом отмены 30 дней.**
`deletion_requested_at` ставится сразу, `deleted_at` — фоновой задачей через 30 дней. В промежутке аккаунт деактивирован: вход возможен, но приводит к экрану «восстановить аккаунт?».
*Почему так:* удаление аккаунта с фотографиями и дневником за год — операция, которую делают сгоряча. Немедленное необратимое удаление породит поток обращений «верните».
*Альтернатива:* немедленное удаление. Отвергнута по причине выше.
*Альтернатива:* период 14 дней. Отвергнута: 30 — распространённая практика и покрывает отпуск.

**Решение 2. Вход в период ожидания отменяет удаление явным действием, а не автоматически.**
Успешный вход показывает экран с выбором: восстановить или продолжить удаление. Автоматическая отмена при входе опасна: пользователь мог войти, чтобы забрать выгрузку.
*Альтернатива:* автоотмена при входе. Отвергнута по причине выше.

**Решение 3. Для каждой таблицы — явная стратегия, зафиксированная в коде таблицей соответствий.**
Три стратегии:
- `delete` — записи, принадлежащие только пользователю: дневник питания, вода, метрики, задачи, планы, уведомления, refresh-токены, пользовательские продукты.
- `anonymize` — записи, участвующие в чужом рабочем процессе: сообщения чата (текст сохраняется, `sender_id` переводится на технического «удалённого пользователя»), недельные отчёты с фидбеком куратора.
- `keep` — обезличенные агрегаты, не содержащие персональных данных: `curator_daily_snapshots`, `platform_weekly_benchmarks`.
Стратегия объявляется списком в `erasure.go`; тест сверяет, что список покрывает все таблицы схемы, содержащие ссылку на `users`.
*Почему так:* без сверки со схемой новая таблица тихо выпадет из удаления. Именно так и появляются «забытые» персональные данные.
*Альтернатива:* полагаться на `ON DELETE CASCADE`. Отвергнута: каскад удалил бы переписку у куратора и не тронул бы файлы в S3.

**Решение 4. Файлы в S3 удаляются по префиксу пользователя.**
Ключи объектов включают идентификатор пользователя. Удаление обходит четыре бакета и удаляет объекты с префиксом.
*Риск:* если хотя бы в одном бакете ключи не содержат идентификатор пользователя, объекты осиротеют. → Задача проверяет формат ключей во всех четырёх бакетах перед реализацией.

**Решение 5. Экспорт — асинхронный, архив в S3, ссылка одноразовая.**
Запрос ставит запись в `data_exports`; фоновая задача собирает JSON по таблицам и файлы, пакует в ZIP, кладёт в приватный бакет; пользователь получает уведомление и скачивает по ссылке со сроком жизни 24 часа и однократным использованием.
*Почему так:* синхронная сборка архива с фотографиями за год не уложится в таймаут HTTP.
*Альтернатива:* синхронный JSON без файлов. Отвергнута: фотографии прогресса — существенная часть данных пользователя.

**Решение 6. Технический пользователь «удалённый» создаётся миграцией.**
Строка в `users` с фиксированным идентификатором, служебным email и ролью `user`, помеченная как системная. На неё переводятся анонимизированные ссылки.
*Альтернатива:* `sender_id NULL`. Отвергнута: потребовала бы снять `NOT NULL` и обрабатывать `NULL` во всех запросах чата.

**Решение 7. Удаление выполняется в одной транзакции, файлы — после её фиксации.**
Если удаление файлов упало, транзакция уже зафиксирована; недоудалённые объекты подбирает повторный проход задачи по списку из `job_runs`.
*Почему так:* обратный порядок оставил бы пользователя без файлов, но с данными в БД при откате транзакции.

## Risks / Trade-offs

- **Риск: неполное удаление из-за забытой таблицы.** → Тест сверяет список стратегий со схемой БД: любая таблица со ссылкой на `users` без объявленной стратегии роняет тест.
- **Риск: удаление ломает целостность данных куратора.** → Анонимизация вместо удаления для сообщений и отчётов; интеграционный тест проверяет, что после удаления клиента чат у куратора открывается.
- **Риск: экспорт нагружает S3 и БД.** → Не более одного активного экспорта на пользователя, не чаще одного раза в сутки.
- **Риск: ссылка на архив утечёт.** → Одноразовая, 24 часа, привязана к пользователю, требует аутентификации.
- **Trade-off: данные остаются в резервных копиях БД** после удаления. Фиксируется в политике конфиденциальности с указанием срока хранения копий.

## Migration Plan

1. Миграция: колонки, таблица `data_exports`, технический пользователь.
2. Реализация экспорта — выкатывается первым, не несёт риска потери данных.
3. Реализация запроса на удаление и деактивации, без исполнения.
4. Реализация необратимого удаления, проверка на dev на тестовом аккаунте с полным набором данных.
5. Включение фоновой задачи исполнения.
6. Актуализация `/legal/privacy`.

**Откат:** до шага 5 включительно необратимых операций не выполняется. После — откат невозможен по природе операции, поэтому шаг 4 обязателен и выполняется на dev.

## Open Questions

- Содержат ли ключи объектов во всех четырёх бакетах идентификатор пользователя? Проверяется задачей 1.2.
- Нужно ли уведомлять куратора об удалении клиента? Предварительно да — уведомление в приложении без указания причины.
