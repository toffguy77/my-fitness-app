## Context

- `food_entries.food_id` — UUID `food_items` с `ON DELETE RESTRICT` (`apps/api/migrations/006_create_food_entries_table_up.sql`); запись хранит копию названия и КБЖУ порции. `CreateEntry` (`apps/api/internal/modules/food-tracker/service.go:154`) принимает `foodId`, `mealType`, `portionType`, `portionAmount`, `date`, `time`.
- `food_items.source` ограничен `database|usda|openfoodfacts|user` (`005_create_food_items_table_up.sql:73`); `category` — обязательный текст.
- `SearchFoods` (`service.go:962`) ищет по `user_foods`, `products` и `food_items` одним запросом — продукты рецептов попали бы в выдачу сами, без фильтра доступности.
- План (`meal-day-plan`) хранит блюдо как `(plan_id, meal_type)` с версией рецепта и весом.

## Goals / Non-Goals

**Goals:** запись блюда плана одним действием без новой схемы дневника; одно состояние «съедено» в плане и дневнике; рецепты в поиске с тем же правилом доступности.

**Non-Goals:** запись нескольких блюд одним нажатием за весь день; частичная запись ингредиентов; изменение распознавания по фото.

## Decisions

### 1. Продукт версии — детерминированный UUID

`food_items.id = uuid_v5(namespace_recipes, recipe_version_id)`, `source='recipe'`, `category='Блюда'`, `verified=true`, `default_weight` = вес порции. Создаётся в той же транзакции, что одобрение (`ON CONFLICT DO NOTHING`), и заполняется для уже одобренных версий в миграции (SQL-функция `uuid_generate_v5` из `uuid-ossp`, если расширение есть; иначе — одноразовым шагом на старте сервиса, идемпотентно).

*Отвергнуто:* одна запись `food_items` на рецепт, переписываемая при новой версии — запись дневника хранит КБЖУ, но «повторить запись» и избранное взяли бы новое КБЖУ под старым названием. *Отвергнуто:* новая колонка `recipe_version_id` в `food_entries` — меняет схему дневника ради того, что выражается ссылкой на продукт.

### 2. Связь плана и записи — внешний ключ с `SET NULL`

`meal_plan_items.food_entry_id UUID REFERENCES food_entries(id) ON DELETE SET NULL`. Удаление записи в дневнике само возвращает блюдо в несъеденные — без кода в `food-tracker`. Съеденный вес читается из записи соединением, поэтому правка веса в дневнике видна плану без синхронизации.

*Отвергнуто:* флаг `eaten` в плане — расходится с дневником при любой правке в дневнике.

### 3. «Съел» — транзакция в `mealplan`

`POST /api/v1/meal-plans/:date/items/:mealType/eat {grams?}`: блокирует строку блюда (`FOR UPDATE`); если `food_entry_id` уже задан и запись существует — возвращает её (`200`); иначе создаёт запись через сервис `food-tracker` (тот же путь, что `CreateEntry`, `portionType='grams'`, время — текущее время клиента из запроса или 12:00 для прошлых дат) и сохраняет связь (`201`).

### 4. Чтение плана без сборки

`GET /api/v1/meal-plans/:date?generate=false` — отдаёт план, если он есть, иначе `204`. Дневник зовёт только этот вариант.

### 5. Подгонка остатка

`POST /api/v1/meal-plans/:date/refit`: съеденные блюда передаются генератору как ручные с весом записи; закреплённые и ручные остаются; подгоняются остальные. Замена и пересборка съеденного — `409`.

### 6. Поиск

В `SearchFoods` ветка `food_items` получает `AND source <> 'recipe'`, и добавляется ветка рецептов: текущая одобренная версия доступных рецептов (`AvailableFilter`) с полнотекстовым поиском по названию. Результат помечается `source: 'recipe'` и `recipeId`.

### 7. Фронтенд

- `MealSlotCard`: кнопка «Съел» с выпадающей правкой веса; съеденное блюдо показывает вес из дневника, кнопки замены скрыты; «Подогнать остаток» в итогах дня, когда есть съеденные.
- `MealSlot` дневника: блок «По плану» с несъеденными блюдами и «+»; данные — `GET ...?generate=false`.
- Поиск дневника: значок «рецепт», переход к карточке рецепта.

## Risks / Trade-offs

- **Продукты рецептов в `food_items` видны другим путям** (недавние, избранное, распознавание). Недавние и избранное — допустимо: клиент уже ел это блюдо. Распознавание по фото сопоставляет по названию с выдачей поиска — её фильтр закрывает.
- **`ON DELETE RESTRICT` у записей** — продукт рецепта нельзя удалить, пока на него есть записи; удалять его и не нужно.
- **Время записи для прошлых дат** — 12:00 условно; дневник группирует по приёму пищи, не по времени.
