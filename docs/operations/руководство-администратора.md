# Руководство администратора и куратора

Что здесь: почта на домене, бот поддержки, очередь обращений и чат с клиентом —
с той стороны, с которой их видит человек, а не сервер.

> Этот файл намеренно лежит **не** в `docs/user-guide/`. Оттуда бот поддержки
> отвечает пользователям и отвечает строго по написанному: положи сюда
> админские шаги — и он начнёт пересказывать их клиентам.

---

## 1. Почта на домене `burcev.team`

### Что уже стоит

Домен подключён к Яндекс 360, записи DNS отвечают в мире:

| Запись | Значение | Зачем |
|---|---|---|
| `MX @` | `mx.yandex.net.` (10) | входящая почта |
| `TXT @` | `v=spf1 redirect=_spf.yandex.net` | SPF: кому можно слать от домена |
| `TXT mail._domainkey` | `v=DKIM1; …` | DKIM: подпись писем |
| `TXT _dmarc` | `v=DMARC1; p=none; rua=mailto:support@burcev.team` | DMARC: отчёты о подделках |
| `CNAME mail` | `domain.mail.yandex.net.` | веб-интерфейс почты |

Общие ящики: `info@burcev.team` и `support@burcev.team`.

`p=none` в DMARC — это «наблюдать, не трогать». Так и надо начинать: сначала
неделю-другую смотрим отчёты, приходящие на `support@`, убеждаемся, что свои
письма проходят с подписью, и только потом ужесточаем до `p=quarantine`.
Ужесточить раньше — значит отправить собственные письма в спам и узнать об этом
от пользователей.

### Что осталось сделать

**Приложение не может войти под общим ящиком.** У общего ящика нет своего
пароля: он не аккаунт, а папка, к которой выдают доступ. Отправляет всегда
сотрудник — либо от своего адреса, либо «как» общий ящик, если ему выдали такую
роль. Значит, нужен аккаунт сотрудника.

1. **Завести сотрудника `noreply@burcev.team`** — Пользователи → Сотрудники.

   Отдельный аккаунт, а не чей-то личный, именно потому, что личный уже подвёл:
   почта в обеих средах шла с `thatguy@yandex.ru`, пароль приложения на нём
   отозвали, и всё восстановление паролей молча умерло в обеих средах разом.
   Аккаунт, которым не пользуется человек, не теряет пароль от того, что человек
   сменил пароль.

2. **Создать для него пароль приложения** — войти в Яндекс ID под `noreply@`,
   раздел «Пароли приложений» → «Почта». Если пункт недоступен, включить
   двухфакторную проверку; если недоступен и после — Безопасность → Ограничения
   в кабинете организации.

   Этот пароль показывается **один раз**. Он и есть `SMTP_PASSWORD`.

3. **Прописать переменные** в обеих средах Dokploy:

   ```
   SMTP_HOST=smtp.yandex.ru
   SMTP_PORT=465
   SMTP_USERNAME=noreply@burcev.team
   SMTP_PASSWORD=<пароль приложения>
   SMTP_FROM_ADDRESS=noreply@burcev.team
   SMTP_FROM_NAME=BURCEV
   SMTP_REPLY_TO=support@burcev.team
   ```

   `SMTP_REPLY_TO` — чтобы человек, нажавший «ответить» на письмо о сбросе
   пароля, попал в общий ящик поддержки, а не в `noreply@`, который никто не
   открывает.

4. **Убедиться, что письмо доходит и подписано.** После выкатки — запросить
   сброс пароля на свой внешний адрес (например, Gmail) и в полученном письме
   открыть «Показать оригинал»: там должны стоять `dkim=pass`, `spf=pass`,
   `dmarc=pass` для `burcev.team`. Ежечасная проверка возможностей отвечает на
   другой вопрос — «принимает ли сервер наш пароль», — и о подписи не знает
   ничего.

### Если всё же хочется слать от `support@burcev.team`

Так можно, и ответы тогда сразу ложатся в общий ящик. Цена — роль «полная
отправка по SMTP» на общий ящик для `noreply@` и нестандартный логин:

```
SMTP_USERNAME=burcev.team/noreply/support     # домен/логин/имя ящика
SMTP_FROM_ADDRESS=support@burcev.team
```

Пароль остаётся паролем приложения сотрудника `noreply@`. Вариант рабочий, но
подвижных частей больше, а `Reply-To` даёт тот же результат одной строкой —
поэтому по умолчанию делаем проще.

## 2. Эта почта на личном Mac

Общий ящик в почтовой программе — это **не** отдельная учётная запись. Логин
собирается из трёх частей через косую черту.

**Почта (macOS), Настройки → Учётные записи → Другая учётная запись:**

| Поле | Свой ящик | Общий ящик |
|---|---|---|
| Логин | `имя@burcev.team` | `burcev.team/имя/support` |
| Пароль | пароль приложения | пароль приложения **своего** аккаунта |
| IMAP | `imap.yandex.ru`, порт 993, SSL | то же |
| SMTP | `smtp.yandex.ru`, порт 465, SSL | то же |
| Аутентификация | «Обычный пароль» | то же |

Здесь `имя` — логин сотрудника, `support` — имя общего ящика (не адрес
целиком). Пароль приложения создаётся в Яндекс ID под своим аккаунтом, тип
«Почта», и показывается один раз.

Если Почта macOS упорно не входит — почти всегда это обычный пароль вместо
пароля приложения: при включённой двухфакторной проверке обычный пароль по IMAP
не принимается, а сообщение об ошибке об этом не говорит.

## 3. Бот поддержки в Telegram

### Что он делает

Отвечает на вопросы **строго по `docs/user-guide/`** и ничего не придумывает.
Не нашёл ответа — так и говорит, и зовёт человека.

Это не осторожность ради осторожности: бот разговаривает с людьми до
регистрации, и выдуманный ответ про чужие деньги или чужое здоровье дороже
молчания.

### Откуда он берёт знания

Файлы `docs/user-guide/` вшиты в двоичный файл API (`go:embed` не умеет
смотреть за пределы модуля, поэтому лежит копия в
`apps/api/internal/modules/support/knowledge/`).

**Меняется поведение продукта — правится `docs/user-guide/`, затем в `apps/api`:**

```bash
make sync-knowledge
```

`TestKnowledgeMatchesUserGuide` роняет сборку, если копия разошлась с
оригиналом. Без него бот отвечал бы по документации, которую никто уже не
читает, — и это выглядело бы как исправная работа.

### Когда бот зовёт человека

Разговор уходит в очередь оператора с указанием причины:

| Причина в очереди | Что произошло |
|---|---|
| `по просьбе пользователя` | человек сам попросил живого |
| `ответа нет в документации` | вопрос не покрыт `docs/user-guide/` |
| `база знаний недоступна` | не прочиталась база — это неисправность |
| `ошибка обращения к модели` | модель не ответила |
| `исчерпан дневной лимит обращений к модели` | упёрлись в дневной предел |

Первые две — нормальная жизнь. Три последних означают, что **сломано что-то у
нас**, и если они идут потоком, чинить надо не очередь.

## 4. Очередь обращений — `/admin/support`

Открыта только роли `super_admin`. Куратор её не видит: у куратора свой чат с
клиентами, это другое место (раздел 5).

- Обращения, ждущие человека, стоят наверху; под каждым — причина.
- «Ответить» отправляет сообщение обратно в Telegram тому, кто спросил.
- «Закрыть» убирает обращение из очереди; человек может написать снова, и
  разговор откроется заново.

Об эскалации операторы узнают обычным уведомлением — тем же путём, что и всё
остальное в продукте, то есть по почте или push в зависимости от собственных
настроек. Отдельный канал настраивать не нужно. Если уведомление не дошло, а
обращение в очереди есть — смотреть надо настройки уведомлений, а не поддержку.

## 5. Чат куратора с клиентом — это не поддержка

Сам чат описан в [Руководстве куратора, «Чат с клиентами»](../curator-guide/07-чат-с-клиентами.md).
Здесь — только то, чего там нет: как он соотносится с поддержкой.

Поддержка — про продукт, для кого угодно, в том числе до регистрации. Чат
куратора — про конкретного человека и его питание, внутри приложения. Разговоры
не смешиваются: написать в поддержку из чата нельзя и наоборот.

Одна вещь, о которой стоит знать куратору: он видит только своих клиентов, и
держится это на проверке связи «куратор — клиент» на каждом запросе, а не на
изоляции в базе данных — её нет. **Если куратор увидел чужого клиента, это
неисправность, а не настройка**, и сообщать о ней надо сразу.

## 6. Когда что-то сломалось

Раз в час каждая включённая возможность отвечает на вопрос «ты ещё работаешь».
Не «заполнены ли настройки» — это другой вопрос, и за один день он дважды
разошёлся с правдой: почта перестала принимать пароль, у поставщика модели
кончились деньги, а `/ready` всё это время докладывал, что всё хорошо.

- `GET /health` — перечисляет возможности и то, какие из них отвечают.
- Сломанная возможность отвечает `503` **одинаково**, а не молча делает вид.
- В Telegram приходит тревога; в Grafana — панель `capability health`.

Чего проверка не умеет: она не отправляет писем, не тратит денег и ничего не
пишет. Значит, «почта отвечает» означает «сервер принял пароль», но не
«письмо дошло и не попало в спам». Это проверяется руками — раздел 1, шаг 4.

### Сборки падают на скачивании образа

Симптом в журнале выкатки:

```
failed to do request: Head "https://mirror.gcr.io/v2/library/alpine/manifests/3.19":
dial tcp [2a00:1450:4010:c0e::52]:443: connect: network is unreachable
```

Это та же неисправность, что обездвижила бота и грозила почте: **на хосте нет
маршрута в IPv6, а резолвер отдаёт адреса IPv6**. Код приложения её обходит
(`internal/shared/httpx` набирает номер только по IPv4), но сборка идёт мимо
кода — адрес выбирает buildkit.

Повтор выкатки обычно помогает: система пробует адреса по очереди и иногда
успевает откатиться на IPv4. Это не решение, а везение.

**Решение — одна строка на хосте**, системное предпочтение IPv4:

```bash
echo 'precedence ::ffff:0:0/96  100' >> /etc/gai.conf
systemctl restart docker
```

Так резолвер продолжает отдавать оба адреса, но выбирается всегда IPv4. Ничего
не ломается, когда IPv6 однажды появится: тогда эту строку надо будет убрать —
и вспомнить о ней поможет `internal/shared/httpx`, где живёт та же заплатка для
кода.

### Учётные записи для проверок на dev

Набор Playwright входит готовыми учётными записями. На dev их нет, а завести
оттуда, где есть Go, нельзя: управляемый PostgreSQL закрыт снаружи. Поэтому
сеятель умеет печатать SQL — выполнить его можно там, где база достижима.

На своей машине:

```bash
cd apps/api
set -a; . путь/к/переменным/E2E; set +a   # значения — в .github/workflows/e2e.yml
go run ./cmd/seed-e2e -sql > seed.sql
```

На сервере:

```bash
psql "$DATABASE_URL" -f seed.sql
```

Скрипт безопасен к повтору и не трогает чужие данные: идентификаторы в нём не
зашиты, всё ищется по адресу почты. Учётные записи заводятся сразу
подтверждёнными и с пройденным онбордингом — это фикстуры, а не люди.

После этого набор гоняется против dev:

```bash
npm run test:e2e:staging
```

### Контейнеры теряют базу на секунду

В журнале API периодически:

```
hostname resolving error: lookup rc1d-….mdb.yandexcloud.net on 127.0.0.11:53: server misbehaving
```

`127.0.0.11` — встроенный резолвер Docker. Он изредка не отвечает, и запрос к
базе падает, хотя база исправна. За сутки таких отказов около десяти — это
четверть всех ошибок на dev, и каждый виден человеку как пустой экран куратора.

Приложение это не чинит и чинить не должно: имя разрешается до подключения.
Лечится на хосте — дать Docker явные серверы имён:

```json
// /etc/docker/daemon.json
{ "dns": ["77.88.8.8", "8.8.8.8"] }
```

```bash
systemctl restart docker
```

Перезапуск Docker перезапускает и контейнеры, включая прод, — делать в окно.

Тот же хост не разрешает имена базы и снаружи контейнеров: `getent hosts`
возвращает пустоту. Поэтому `psql` с хоста ходит по адресу, а не по имени —
см. помощник `~/devdb`.

### Схема: как проверить, что миграции описывают то, что есть

Миграции однажды разошлись с живой схемой и молчали об этом полтора года.
Каталог еды залили в базу до появления миграций, а миграция 005 создаёт
`products` через `CREATE TABLE IF NOT EXISTS` — на dev и проде она не сделала
ничего, записавшись применённой. В репозитории не было ни `categories`, ни
`nutrients`, ни полнотекстового индекса поиска еды; собранный по миграциям
сервис работал, но искал перебором по сорока трём тысячам продуктов.

Свела миграция 066. Чтобы это не вернулось, есть две разные проверки:

**Внутри репозитория** — снимок `internal/shared/database/testdata/schema.golden`
сверяется в CI. Изменил миграцию, не обновив снимок — сборка падает:

```bash
UPDATE_GOLDEN=1 go test -tags=integration ./internal/shared/database/
```

**Против живой среды** — снимком не поймать, до базы из CI не дотянуться.
Сверять руками, когда есть повод (после ручной правки базы, после импорта):

```bash
# на сервере, в контейнере той же мажорной версии
sudo docker run --rm -e PGPASSWORD="$PW" -e PGSSLMODE=require \
  mirror.gcr.io/library/postgres:18-alpine \
  pg_dump -h <адрес> -p 6432 -U burcev-dev -d web-app-db-dev --schema-only
```

**Версии должны совпадать.** Прод — PostgreSQL 18, и CI с локальной разработкой
теперь тоже. На 16 сравнение показывало десятки расхождений, которых нет:
PG17+ записывает `NOT NULL` отдельными ограничениями.

### Ссылка на бота не видна никому

Кнопка «Задать вопрос в Telegram» рендерится только когда задана
`NEXT_PUBLIC_TELEGRAM_BOT` — имя бота без `@`. Не задана — компонент возвращает
`null`, и ссылки нет ни на одной странице. Ошибки при этом нет нигде: так
задумано, «лучше никакой ссылки, чем мёртвая».

Оборотная сторона задумки: бот может быть собран, исправен и проверен — и
недостижим, а выглядеть это будет как «никто не спрашивает». Именно так и было
до 14 сентября: переменная не была задана ни на dev, ни на проде.

```
NEXT_PUBLIC_TELEGRAM_BOT=burcevteam_dev_bot   # dev
NEXT_PUBLIC_TELEGRAM_BOT=burcevteam_bot       # prod
```

**Переменная нужна на сборке, а не на запуске:** Next вшивает `NEXT_PUBLIC_*` в
код при сборке. Изменение подхватится следующей выкаткой, перезапуск контейнера
не поможет.

Проверить, что ссылка видна: `curl -s https://<домен>/ | grep -c 't.me/'` —
должно быть больше нуля.

### Порядок выкатки на прод

1. **Снять резервную копию базы**, если в релизе есть миграции:
   `yc managed-postgresql cluster backup c9q1384cb8tqrg09o8n4`
2. **Обновить `APP_VERSION`** в переменных прода — `vГГГГ.ММ.ДД+<короткий SHA>`
   коммита, который собираетесь слить. **До слияния, не после.**
3. Слить `dev` в `main` — Dokploy выкатит сам, и сборка подхватит переменную.
4. Проверить: `curl -s https://burcev.team/ready` — версия должна совпасть с
   выкаченной, `ready: true`, возможности на месте.

**Правка переменной применяется выкаткой, но не мгновенно.** И `compose.deploy`,
и `compose.redeploy` пересоздают контейнер с новым окружением — только проходит
это две-три минуты, и ответ API приходит задолго до конца.

Отсюда правило: **проверяйте по контейнеру, а не по ответу API.**

```bash
sudo docker inspect <контейнер> --format '{{.Created}}'   # должно быть после правки
sudo docker exec <контейнер> printenv APP_VERSION          # и значение новое
```

2026-09-15 я на этом ошибся дважды: посмотрел через полторы минуты, увидел
прежний контейнер и записал в эту инструкцию, что выкатка переменную не
подхватывает. Через три минуты контейнер пересоздался. Вывод из слишком ранней
проверки выглядит точно так же, как вывод из настоящего отказа.

Сама `APP_VERSION` забывается легче всего, и забывалась: с 11 по 15 сентября
`/ready` сообщал `v2026.09.11`, пока код уехал на 26 коммитов вперёд. Во время
разбора инцидента такая строка отправляет к не тому коммиту — тот самый случай,
когда сообщению верят не глядя.

**Сборки падают на скачивании образа?** Если `mirror.gcr.io` не резолвится по
IPv4, забрать базовые образы заранее, тогда сборщик возьмёт их из кэша:

```bash
for i in golang:1.26-alpine alpine:3.19 node:20-alpine; do
  sudo docker pull "mirror.gcr.io/library/$i"
done
```

Демон скачивает исправно; спотыкается именно сборщик — он на Go и системное
предпочтение IPv4 из `/etc/gai.conf` не читает.

### Первое, что стоит посмотреть

| Симптом | Куда смотреть |
|---|---|
| письма не приходят никому | `/health`, затем пароль приложения `noreply@` |
| письма приходят в спам | заголовки письма: `dkim`/`spf`/`dmarc`, отчёты DMARC на `support@` |
| бот принимает, но не отвечает | сеть до `api.telegram.org` — на этом хосте нет маршрута в IPv6 |
| бот молчит совсем | вебхук Telegram: у бота один адрес на все среды, последняя выкатка забирает его себе |
| бота никто не спрашивает | ссылки нет на страницах — раздел выше, `NEXT_PUBLIC_TELEGRAM_BOT` |
