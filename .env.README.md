# Environment Files Strategy

## Branch-Specific Approach

### Dev Branch (current)
✅ **Commit .env files** - для упрощения совместной разработки

```bash
# Add .env files to git (use force flag)
bash scripts/add-env-files.sh

# Or manually
git add -f .env.local
git add -f apps/api/.env
git add -f apps/web/.env.local
```

### Staging/Production Branches
❌ **Never commit .env files** - используйте GitHub Secrets и CI/CD

#### Номера миграций

Перед тем как завести новую миграцию, посмотрите, какие номера **уже заняты в
базе**, а не только какие файлы лежат в ветке. Базы dev и прода уходят вперёд
вместе с другими ветками, и `internal/shared/database/migrator.go` сверяет
только номер: версия, записанная в `schema_migrations`, считается применённой
независимо от имени файла.

Совпадение номера означает, что миграция **молча не выполнится**, приложение
поднимется как ни в чём не бывало, а первый же запрос к новым колонкам ответит
`500`. Так едва не уехали `073`–`075` изменения `metrika-ads-bridge`: номера
оказались заняты `magic_links`, `email_verification_code_purpose` и
`lead_conversation_index`.

## Security

### Development Credentials (committed in dev)
- Yandex.Cloud PostgreSQL development database
- Development JWT secret
- Local API endpoints
- **Safe to commit** - isolated development environment

### Production Credentials (never committed)
- Stored in GitHub Secrets
- Injected via CI/CD
- Rotated regularly
- **Never commit to git**

## Quick Commands

```bash
# Check current environment
cat apps/api/.env | grep DATABASE_URL

# Test database connection
make -f Makefile.db db-status

# Start development
make dev

# View all environment variables
env | grep -E "(DATABASE|API|JWT)"
```

## Migration Between Branches

### From dev to staging/production
1. Remove .env files from git
2. Store credentials in GitHub Secrets
3. Update CI/CD to use secrets
4. Never commit .env files again

### From staging/production to dev
1. Copy .env.example files
2. Fill with development credentials
3. Add to git with `-f` flag
4. Commit and push

## Troubleshooting

### "Files are ignored by .gitignore"
```bash
# Use force flag
git add -f .env.local

# Or use the script
bash scripts/add-env-files.sh
```

### "Wrong credentials"
```bash
# Check ENV_SETUP.md for correct values
cat ENV_SETUP.md

# Or check .env.example
cat apps/api/.env.example
```

### "Database connection failed"
```bash
# Verify credentials
make -f Makefile.db db-status

# Check if database is accessible
ping $DB_HOST
```

## Best Practices

1. ✅ Commit .env in **dev branch only**
2. ✅ Use .env.example for templates
3. ✅ Document all variables in ENV_SETUP.md
4. ✅ Use different credentials per environment
5. ❌ Never commit production credentials
6. ❌ Never reuse dev credentials in production
7. ❌ Never commit .env in main/staging branches

## Источник истины по переменным API

`apps/api/.env.example` — полный и авторитетный список переменных, которые читает
`apps/api/internal/config/config.go`. Полнота проверяется автотестом
`TestEnvExampleCoversEveryReadVariable`: переменная, добавленная в код, но не
внесённая в пример, роняет сборку.

Каждая переменная помечена одной из трёх меток:

| Метка | Что означает |
|---|---|
| `[обязательна]` | При `NODE_ENV=production` сервис **не стартует** без неё |
| `[опциональна]` | Включает отдельную возможность; без неё возможность выключена, её эндпоинты отвечают `503`, при старте пишется `WARN` |
| `[есть дефолт]` | Можно не задавать |

### Обязательные в production

`APP_DOMAIN`, `JWT_SECRET`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_ADDRESS`,
плюс `DATABASE_URL` **или** `DB_PASSWORD`.

`JWT_SECRET` дополнительно проверяется: минимум 32 байта, значения-заглушки
(`dev-secret-key`, `change-me`, `secret`, `test`) отвергаются. Сгенерировать:

```bash
openssl rand -base64 48
```

При неполной конфигурации сервис печатает **все** проблемы разом и завершается —
чинить окружение по одной переменной за деплой не нужно.

### Какие возможности выключаются без ключей

`email`, `food_recognition`, `weekly_photos`, `profile_avatars`,
`chat_attachments`, `content_media`. Текущее состояние видно в
`GET /health` в поле `features`.

### Устаревшее

`CORS_ORIGIN` в старых примерах не читается кодом — CORS настраивается в
`cmd/server/main.go`. `SUPABASE_*` читаются, но не используются.
