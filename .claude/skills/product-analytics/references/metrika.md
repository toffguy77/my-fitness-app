# Яндекс.Метрика

Счётчик **107159088**, сайт `burcev.team`, часовой пояс Europe/Moscow.
Работает только на проде: на dev идентификатор снят намеренно, иначе прогоны
E2E снова дадут 80% визитов.

Доступ — через MCP `mcp__yandex-metrika__*`. Номер счётчика подставляется сам,
передавать его не нужно.

## Инструменты

| Инструмент | Для чего |
|---|---|
| `get_stat_report` | основной: метрики в разрезе измерений за период |
| `compare_periods` | два периода сразу, с разницей и процентом |
| `list_goals` | идентификаторы целей — нужны для метрик достижений |
| `get_counter_info` | имя, сайт, часовой пояс |
| `list_metrics_and_dimensions` | поиск по названиям, когда не помнишь код |
| `compare_segments` | два сегмента на одном периоде |
| `request_logs` / `get_logs_status` / `download_logs` / `run_sql` | сырые визиты и просмотры через Logs API, когда агрегатов не хватает |

## Что чем меряется

Даты: `YYYY-MM-DD` или `today`, `yesterday`, `NdaysAgo`.

**Визиты** (`ym:s:*`) — посещения:
`ym:s:visits`, `ym:s:users`, `ym:s:bounceRate`,
`ym:s:avgVisitDurationSeconds`, `ym:s:pageDepth`.

**Просмотры** (`ym:pv:*`) — страницы:
`ym:pv:pageviews`, `ym:pv:users`.

Смешивать семейства в одном запросе нельзя.

Полезные измерения: `ym:s:trafficSource`, `ym:s:deviceCategory`,
`ym:s:browser`, `ym:s:regionCity`, `ym:pv:URLPath`,
`ym:s:UTMSource`, `ym:s:UTMCampaign`.

Достижения целей: `ym:s:goal<id>reaches`. Идентификатор бери из `list_goals` —
он числовой и в коде нигде не записан.

## Цели

Пять своих целей заведены 2026-09-24 скриптом `scripts/metrika-goals.mjs`,
который читает список из `MIRRORED_EVENTS` в коде:

`landing_viewed`, `onboarding_started`, `onboarding_result_shown`,
`lead_saved`, `registration_opened`.

Плюс пять автоцелей Метрики (отправка формы, контактные данные и прочее) —
они заведены не нами и набраны в основном прогонами E2E до 2026-09-24.

**Признак ретаргетинга у всех нулевой, и это не недоделка.** Цель становится
условием подбора аудитории в тот момент, когда её выбирают в кампании Директа;
признак — следствие, а не причина. Из кода его выставить нельзя: проверено,
API принимает `is_retargeting: 1` и игнорирует.

## Почему Метрика всегда меньше своей базы

Счётчик считает только тех, кто согласился на аналитические куки и не включил
блокировщик. Своя база считает всех: события уходят на собственный домен и от
согласия не зависят.

Расхождение в полтора-два раза — норма. **Сравнивать эти числа между собой
нельзя**; каждое отвечает на свой вопрос.

## Ловушки

**До 2026-09-24 данные засорены.** dev и прод писали в один счётчик: 295
визитов из 368 за месяц давали прогоны E2E. Любой период, задевающий эту дату,
непригоден для сравнения — скажи об этом прежде, чем называть числа.

**Хиты при клиентской навигации появились тогда же.** Раньше счётчик видел
только прямые заходы и перезагрузки, поэтому просмотры внутренних страниц
занижены, а показатель отказов завышен. Через эту дату глубину просмотра и
отказы не сравнивать.

**Один просмотр — два запроса.** Тег делает `/watch/<id>?` и
`/watch/<id>/1?` с одинаковым `page-url`. На отчёты это не влияет, но при
проверке счётчика в браузере считать надо без суффикса, иначе получится
ровно то задвоение, которого в данных нет.

**Записей сессий и карты скроллинга нет.** Вебвизор выключен: он сохранял
ввод в поля, а в мастере вводятся параметры тела. Не предлагай их как способ
разобраться.

## Когда агрегатов мало

Logs API отдаёт отдельные визиты и просмотры. Порядок: `request_logs` →
`get_logs_status` (готовится не мгновенно) → `download_logs` → `run_sql` по
локальной копии.

Нужно редко. Уместно, когда вопрос про последовательность действий внутри
визита, а не про количество, — например, какой путь прошёл человек перед
уходом.
